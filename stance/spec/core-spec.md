# Stance — 매매 판단 공개 프로토콜

> **Stance** · `stance/1` · Draft
> 시스템 트레이딩의 판단을 위조 불가능하게 기록하고 비교하기 위한 개방형 표준

---

## 한 문장

> **실적을 신고받지 말고, 판단을 미리 선언받아라. 성과는 서버가 계산한다.**

---

## 1. 왜 필요한가

시스템 트레이딩을 돌리는 사람은 많은데, **누구 시스템이 더 나은지 비교할 방법이 없다.**

수익률 인증은 의미가 없다. 스크린샷은 편집되고, 계좌 화면은 연출되고,
잘된 계좌만 골라 보여주면 그만이다. 검증하려면 계좌를 통째로 열어야 하는데
아무도 그러고 싶어 하지 않는다. 그래서 대부분의 "수익률 자랑"은 검증 불가능한 채로 남는다.

Stance는 문제를 뒤집는다.

> **결과를 나중에 보고받는 대신, 판단을 미리 선언받는다.**

"어제 이걸로 30% 벌었다"는 조작할 수 있다.
그러나 **"지금 이걸 산다"** 는 조작할 수 없다. 이미 말했고, 그 시각이 서버에 박혔기 때문이다.
그 다음에 가격이 어떻게 됐는지는 시장이 알아서 정해준다. 참여자가 개입할 여지가 없다.

이 구조에서는 **계좌를 공개할 필요가 없다.** 잔고도, 계좌번호도, 증권사 API 키도 필요 없다.
서버는 "무엇을 언제 사기로 했는가"만 알면 성과를 스스로 계산할 수 있다.

---

## 2. 코어 개념 3개

이게 전부다. 이 셋만 이해하면 Stance를 구현할 수 있다.

### ① 선언 (Stance)

**"이 종목을 내 자산의 몇 %로 만들겠다"** 는 한 줄의 통보.

```json
{ "symbol": "005930", "target_weight": 0.10 }
```

삼성전자를 전체 자산의 10%로 만들겠다는 뜻이다. 이게 매수 선언이다.

### ② 접수시각 (Receipt Time)

서버가 선언을 받은 시각. **데이터베이스가 직접 찍으며 참여자는 건드릴 수 없다.**

**이것이 위조 방지의 전부다.** 다른 장치는 없어도 된다.
접수시각보다 앞선 가격은 절대 인정되지 않으므로, "쌀 때 샀다고 우기기"가 원천적으로 불가능하다.

### ③ 재구성 (Replay)

서버는 선언들을 시간 순서대로 다시 읽어 **보유 현황과 자산 추이를 스스로 만들어낸다.**

참여자는 수익률도, 평균단가도, 잔고도 보내지 않는다. 보내도 쓰이지 않는다.
전부 선언만으로 계산되기 때문이다.

## 3. 메시지는 2개뿐이다

### `set` — 목표 비중을 정한다

```json
{ "protocol": "stance/1", "strategy": "my-strategy", "seq": 42,
  "symbol": "005930", "target_weight": 0.10 }
```

이 한 줄이 **모든 매매를 표현한다.**

| 하고 싶은 것 | 보내는 값 |
|---|---|
| 신규 매수 | `target_weight: 0.10` |
| 비중 늘리기 | `target_weight: 0.15` |
| 비중 줄이기 | `target_weight: 0.05` |
| 전량 청산 | `target_weight: 0` |

**"매수"와 "매도"라는 구분이 없다.** 목표 비중이 지금보다 크면 사는 것이고, 작으면 파는 것이다.
서버가 알아서 판단한다. 분할 매수도 그냥 `set`을 여러 번 보내면 된다.

### `hold` — 오늘은 아무것도 안 한다

```json
{ "protocol": "stance/1", "strategy": "my-strategy", "seq": 43, "action": "hold" }
```

**"판단해서 쉬었다"** 와 **"시스템이 죽어서 못 보냈다"** 를 구분하기 위해 존재한다.
이게 없으면 매매를 자주 안 하는 좋은 전략과 방치된 전략을 구별할 수 없다.

### 선택 신호 — `pause` / `resume`

점검·휴가로 당분간 판단하지 않을 때 밝힌다. **장부를 전혀 건드리지 않는다.**
보내지 않아도 프로토콜은 성립하므로 코어 메시지로 세지 않는다.

```json
{ "protocol": "stance/1", "strategy": "my-strategy", "seq": 44, "kind": "pause" }
```

중단 기간은 **제출률 집계에서만 빠진다. 자산 추이는 그대로 계산된다.**
수익까지 면제하면 하락장에 `pause` 를 걸어 손실을 피하는 공짜 보험이 되기 때문이다.
다음 선언이 들어오면 중단은 자동으로 풀린다.

### 필드 설명

| 필드 | 뜻 |
|---|---|
| `protocol` | 버전. `stance/1` |
| `strategy` | 전략 ID |
| `seq` | 몇 번째 선언인지. 빠진 선언을 감지하는 용도 |
| `symbol` | 종목 코드 |
| `target_weight` | 목표 비중. 0 이상 1 이하 |
| `reason` | (선택) 판단 이유. 자유 텍스트 |

**끝이다.** 가격도, 수량도, 금액도, 시각도 보내지 않는다.

## 3-1. 목표 비중이 정확히 무슨 뜻인가

> **이 절만 제대로 읽으면 된다.** 여기를 오해하면 기록이 전부 어긋난다.

`target_weight` 는 **지금 이 종목의 평가액이 내 총자산에서 차지하는 비율**이다.
**내가 얼마를 투입했는지(원가)가 아니다.** 주가가 움직이면 이 둘은 벌어진다.

### 왜 헷갈리는지 — 예시

자산 1.0으로 시작해 하이닉스를 `target_weight: 0.1` 로 잡았다. 0.1어치 사고 현금은 0.9가 된다.

주가가 2배가 되면 이렇게 된다.

| | 값 |
|---|---|
| 평가액 | 0.2 |
| 현금 | 0.9 |
| **총자산** | **1.1** |
| **이 종목의 비중** | **0.2 / 1.1 = 18.18%** |

**비중이 20%가 아니라 18.18%다.** 분모인 총자산도 같이 커졌기 때문이다.

여기서 "한 칸 더 사자"는 생각으로 `0.2` 를 보내면 어떻게 될까.
서버는 "자산 1.1의 20%, 즉 0.22로 만들어라"로 읽는다. 지금이 0.2이므로 **0.02만 산다.**
의도한 것이 0.11어치였다면 **5분의 1만 반영된 것이다.**

정답은 `0.2818` 이다. (18.18% + 10%)

### 자기 시스템의 방식을 목표 비중으로 바꾸기

시스템마다 포지션 크기를 정하는 방식이 다르다. 전부 한 줄로 변환된다.

| 내 시스템이 이렇게 생각한다면 | 이렇게 보낸다 |
|---|---|
| **N등분 슬랏** — "한 칸 더 산다" | `현재 비중 + (추가 칸 수 / 전체 칸 수)` |
| **목표 배분** — "이 종목은 15%" | `0.15` — 변환이 필요 없다 |
| **금액** — "500만원어치 산다" | `현재 비중 + 500만원 / 총자산` |
| **부분 익절** — "절반 판다" | `현재 비중 × 0.5` |
| **전량 청산** | `0` |

**전부 자기 시스템이 이미 아는 값으로 계산된다.** 서버에 물어볼 필요가 없다.
모든 트레이딩 시스템은 자기 포지션의 평가액과 총자산을 알고 있고, 그 나눗셈이 곧 현재 비중이기 때문이다.

### 왜 "얼마 더 넣는다"가 아니라 "몇 %로 만든다"인가

증분 방식(`0.1만큼 추가`)이 더 직관적으로 보이지만, 목표 방식이 두 가지 면에서 낫다.

**오차가 쌓이지 않는다.** 증분 방식은 한 번 어긋나면 그 오차가 영원히 따라온다.
목표 방식은 절대값이라, 서버 장부가 15%인데 내가 18%로 알고 있었더라도
`0.28` 을 보내는 순간 **양쪽 다 28%가 된다.** 과거 오차가 그 자리에서 지워진다.

**비교 가능한 단위가 된다.** "슬랏 2개"는 시스템마다 뜻이 다르지만
"자산의 28%"는 누구에게나 같은 뜻이다. 이기는 종목에 계속 더 붓는 전략이
`0.1 → 0.28 → 0.45` 로 올라가는 기록은, "한 칸씩 추가" 세 번보다
**확신의 크기를 훨씬 분명하게 보여준다.**

## 4. 규칙 5개

### ① 가격은 서버가 정한다

참여자는 가격을 보낼 수 없다. 서버가 선언을 받은 직후 직접 시세를 찍어 그것으로 체결을 확정한다.

가격을 받으면 어떻게든 유리하게 적어내려는 유인이 생긴다.
**애초에 받지 않으면 그 유인이 존재하지 않는다.**

### ② 자산은 모두 1.0에서 시작한다

실제 계좌가 500만원이든 50억이든, 서버 안에서는 모든 전략이 **1.0**에서 출발한다.

그래서 자금 규모를 밝힐 필요가 없고, 규모가 다른 전략끼리도 공정하게 비교된다.
`target_weight: 0.10`은 누구에게나 "자산의 10%"라는 같은 의미다.

### ③ 빚을 낼 수 없다

모든 종목의 목표 비중 합이 1.0을 넘을 수 없다. 넘으면 가능한 만큼만 반영된다.

이 규칙이 없으면 누군가 `target_weight: 10.0`으로 10배 레버리지를 선언해 순위표를 장악한다.

### ④ 한 번 기록되면 고치거나 지울 수 없다

선언은 오직 추가만 된다. 수정도 삭제도 불가능하며, 이는 데이터베이스 차원에서 강제된다.

전략도 삭제할 수 없다. **여러 개 등록해 놓고 잘된 것만 홍보하는 것**을 막는 유일한 방법이다.
여러 전략을 돌리는 건 자유지만, 감출 수는 없다.

### ⑤ 현실에서 불가능한 체결은 인정하지 않는다

상한가에 잠겨 파는 사람이 없거나, 거래가 정지된 종목은 **실제로 살 수 없다.**
이런 선언은 거부된다.

이걸 막지 않으면 매일 상한가 종목만 담는 전략이,
현실에서는 한 주도 못 사면서 순위표에서는 1등을 한다.

## 5. 서버가 하는 일

참여자가 안 하는 모든 것을 서버가 한다.

- 선언 접수 시각 기록
- 그 시점 시세 실측 및 체결 확정
- 보유 현황·평균단가 계산
- 자산 추이 계산
- 거래비용 차감
- 액면분할·배당 등 기업행위 반영
- 성과 지표 산출 및 순위 매기기

**참여자가 계산할 것은 목표 비중 하나뿐이다.** 나눗셈 한 번이면 나온다.

### 서버가 실수하면 참여자가 아니라 서버가 책임진다

시세 소스가 죽어 가격을 못 구하면 그 선언은 **거부되지 않고 보류**된다.
재시도하고, 끝내 실패하면 다음 정규장 시가로 확정한다.
**서버 사정으로 참여자의 판단 기록이 사라지면 안 된다.**

보류 건수는 전략 카드에 표시되지만 성적에는 영향을 주지 않는다.

### 종목 표기는 서버가 맞춘다

`005930` · `A005930` · `005930.KS` 는 전부 같은 종목이다.
표기가 달라 포지션이 둘로 갈리지 않도록 서버가 정규화한다. 참여자가 신경 쓸 필요가 없다.

## 6. 코어 밖의 것들 — 레이어 구조

여기가 이 표준의 핵심 설계다.

MCP가 "도구·리소스·프롬프트" 세 개만 코어로 두고 나머지를 전부 선택 레이어로 밀어냈듯이,
Stance도 **바뀔 수 있는 것을 코어에서 뺀다.**

```
┌─────────────────────────────────────────────┐
│  Layer 2 — 리더보드 (구현체)                 │
│  누구나 자기 리더보드를 운영할 수 있다        │
├─────────────────────────────────────────────┤
│  Layer 1 — 채점 프로파일 (교체 가능)         │
│  어떤 지표로 순위를 매길지. 버전으로 관리     │
├─────────────────────────────────────────────┤
│  Layer 0 — 선언 프로토콜  ★코어★             │
│  메시지 2개 + 규칙 5개. 이것만 표준이다       │
└─────────────────────────────────────────────┘
```

### 왜 채점을 코어에서 빼는가

**"어떤 지표가 좋은 전략을 가려내는가"에는 정답이 없기 때문이다.**

실제로 검토해 보면 이렇다. 수익을 위험으로 나누는 방식은 **현금을 많이 들고 있는 전략을 구조적으로 우대**한다.
변동성이 작아 분모가 작아지기 때문이다. 반대로 시장 대비 초과 수익으로 재면
**상승장에서는 공격적인 전략이, 하락장에서는 방어적인 전략이** 자동으로 유리해진다.

노출 5%짜리 전략과 85%짜리 전략을 하나의 숫자로 줄 세우려면
**낮은 노출이 좋은지 높은 노출이 좋은지를 미리 정해야 한다.** 그 결정 자체가 편향이다.

그러니 정답을 하나 고르려 애쓰는 대신, **바꿔 끼울 수 있게 만든다.**

- 채점 프로파일은 `stance-score/1` 처럼 버전을 갖는다
- 같은 선언 데이터를 서로 다른 프로파일로 채점할 수 있다
- 프로파일이 바뀌어도 **코어는 그대로다**
- 누가 자기만의 순위 기준을 만들어도 표준은 깨지지 않는다

이것이 표준으로서 오래 살아남는 방법이다.
채점 방식은 앞으로 계속 논쟁될 것이고, 그 논쟁이 프로토콜을 흔들면 안 된다.

### 마찬가지로 코어 밖인 것들

기업행위 처리, 거래비용 상수, 무결성 봉인 방식, 인증 방식, 리더보드 UI —
전부 구현 세부사항이며 코어 스펙에 들어가지 않는다.

## 7. 누가 올린 전략인가 — 신원

> 신원은 **코어가 아니라 리더보드(Layer 2)의 문제**다.
> 프로토콜 자체는 `strategy` 필드 하나만 알면 되고, 그 전략이 누구 것인지는 리더보드가 관리한다.
> 그래서 다른 리더보드가 각자 다른 신원 정책(완전 익명, 실명 인증 등)을 써도 프로토콜은 그대로 간다.

### 신원이 필요한 이유는 하나뿐이다

**한 사람이 여러 개를 등록해 놓고 잘된 것만 홍보하는 것을 막는 것.**

더 교묘하게는, 정반대로 판단하는 전략 두 개를 등록하면 **하나는 반드시 이긴다.**
금융 사기에서 오래된 수법이다. "전략 삭제 불가" 규칙만으로는 이걸 막지 못한다.
같은 사람이 등록했다는 사실을 아무도 알 수 없기 때문이다.

여기서 핵심은 **묶는 것과 실명을 확인하는 것은 전혀 다른 문제**라는 점이다.
여러 전략을 한 주체로 묶으려면 **위조할 수 없고 계속 유지되는 식별자**만 있으면 된다.
그게 실제로 누구인지는 알 필요가 없다.

### 그래서 이렇게 한다

- **계정**이 사람 단위다. 핸들(`@dragon1086`)은 고유하며 바꿀 수 없다.
- **표시 이름은 자유**다. 닉네임이든 뭐든 상관없다.
- **한 계정의 모든 전략이 계정 페이지에 강제로 노출된다.** 감출 수 없다.
- **익명 참여를 허용한다.** 자기 전략을 드러내기 싫은 사람도 이력은 똑같이 쌓인다.

여러 전략을 돌리는 것 자체는 막지 않는다. 정당한 실험이다. **다만 감출 수 없게 만든다.**

### 사칭은 문제가 되지 않는다

누군가 "PRISM 공식" 같은 이름으로 계정을 만들 수는 있다. 그러나 **얻는 것이 없다.**

리더보드에서 가치를 갖는 것은 **이름이 아니라 이력**이다.
60거래일 넘게 실시간으로 접수된 선언 기록. 그것은 복사할 수도, 옮겨올 수도, 나중에 만들어낼 수도 없다.
새 계정의 이력은 0이고, 0은 아무것도 증명하지 못한다.

일반적인 서비스에서 사칭이 문제가 되는 것은 **이름 자체가 신뢰를 운반하기 때문**이다.
Stance에서는 이력이 신뢰를 운반한다. 그래서 이름을 훔쳐도 훔칠 것이 없다.

혼동만 줄이면 되므로 두 가지로 충분하다.

- 표시할 때 **항상 핸들을 함께 적는다** — `PRISM (@dragon1086)`
- 원하는 사람만 **GitHub 계정이나 도메인을 연결해 인증 뱃지**를 받는다 (강제하지 않는다)

강제하면 진입 장벽이 올라가고, 코어를 최소로 유지한다는 원칙에도 어긋난다.

### 계정을 여러 개 만들면

막지 못한다. 그러나 **시간이 막아준다.**

참가 요건이 60거래일 이상 · 청산 20건 이상 · 제출률 70% 이상이다.
계정 하나를 순위표에 올리는 데만 **3개월**이 걸린다.
여러 개를 나란히 돌리는 것이 불가능하지는 않지만, 3개월을 들여 얻는 것이 순위표 한 자리뿐이다.

애초에 이것은 완벽하게 막아야 하는 종류의 문제가 아니다.
감시로 막으려 들면 코어가 무거워지고 참여 장벽만 올라간다.
**마찰은 최소로 두되, 여러 전략을 감출 수는 없게 만드는 선에서 끊는다.**

## 8. 붙이는 데 10분

참여자가 작성할 코드는 이게 전부다.

```python
import requests

def declare(symbol, target_weight, reason=None):
    """이 종목을 자산의 target_weight 비율로 만들겠다고 선언한다."""
    requests.post(f"{Stance_URL}/stances",
        headers={"Authorization": f"Bearer {TOKEN}"},
        json={"protocol": "stance/1", "strategy": STRATEGY_ID,
              "seq": next_seq(), "symbol": symbol,
              "target_weight": target_weight, "reason": reason})
```

기존 시스템에 붙이는 방법은 **주문을 내는 자리 바로 옆에 한 줄 추가**하는 것이다.

```python
# 원래 있던 코드
broker.buy(symbol, amount)

# 한 줄 추가
declare(symbol, target_weight=0.10, reason="20일선 눌림목")
```

**주문이 실제로 체결됐는지는 상관없다.** Stance가 기록하는 것은 판단이지 체결이 아니다.
그래서 실계좌 없이 모의로 돌리는 시스템도, 백테스트를 실시간으로 돌리는 시스템도 참여할 수 있다.

> 그렇다고 과거 데이터로 백테스트한 결과를 밀어 넣을 수는 없다.
> 선언은 **실시간으로 접수되어야만** 기록되기 때문이다. 미래를 아는 상태로는 선언할 수 없다.

## 9. 자주 나올 질문

**Q. 실제로 못 샀는데도 성과로 인정되나?**

그렇다. Stance는 **판단**을 기록하는 표준이지 체결을 기록하는 표준이 아니다.

체결은 시스템의 실력이 아니라 환경의 문제다. 자금이 크면 나눠 담아야 하고, 주문이 반만 체결되기도 하고,
증권사 API가 죽기도 한다. 이건 전부 판단의 차이가 아니라 **집행 환경의 차이**다.
그걸 점수에 섞으면 "누가 더 나은 판단을 하는가"라는 원래 질문이 흐려진다.

대신 **현실에서 아예 불가능한 체결**(상한가 잠김, 거래정지)은 규칙 ⑤로 막는다.
판단이 실행 가능한지에 대한 최소한의 기준은 유지한다는 뜻이다.

**Q. 대충 아무 값이나 보내면?**

자기 기록만 부정확해진다. **유리해지는 방향이 없다.**

비중을 부풀리면 합계 1.0 제한에 걸려 잘려 나가고, 줄이면 성과가 축소 기록된다.
가격은 애초에 보낼 수 없다. 이득을 볼 경로가 설계상 존재하지 않으므로 감시할 필요도 없다.

**Q. 실계좌 연동도 안 하면서 수수료는 왜 떼나?**

수수료가 "집행"이 아니라 **"거래하기로 한 판단의 불가피한 산술적 결과"** 이기 때문이다.

빼면 어떻게 되는지 보면 명확하다. KRX 거래세만 따져도 연 100회전 전략은 18%p,
3회전 전략은 0.5%p를 부담한다. 반영하지 않으면 **고회전 전략에게 17%p를 공짜로 주는 것**이다.
그런데 "얼마나 자주 거래할 것인가" 는 증권사의 성격이 아니라 **전략의 성격**이다.
빼면 판단 리더보드가 오히려 판단의 한 축을 못 보게 된다.

같은 기준으로 **호가 스프레드와 시장충격은 뺀다.** 그것들은 주문 크기·유동성·집행 실력에 따라
사람마다 달라지기 때문이다. 그리고 **증권사 수수료도 뺀다** — 회사마다 다르므로.
경계는 "모두에게 동일한가" 하나다.

**Q. 우리 시스템은 매일 돌지 않는데?**

등록할 때 주기(`daily`/`weekly`/`monthly`/`event`)를 밝히면 제출률이 그 기준으로 계산된다.
그리고 제출률은 **애초에 참가 요건이 아니다.** §10 참조.

**Q. 우리 시스템이 며칠 죽어 있었다면?**

성적에는 아무 영향이 없다. 선언이 없는 날은 직전 보유가 유지된 것으로 계산될 뿐이다.
점검이 예정되어 있다면 `pause` 를 보내면 제출률 집계에서도 빠진다.
다만 **자산 추이는 중단 중에도 그대로 계산된다** — 그렇지 않으면
하락장에 중단을 걸어 손실을 피하는 공짜 보험이 되기 때문이다.

**Q. 계좌를 공개해야 하나?**

아니다. 잔고·계좌번호·증권사 키는 프로토콜에 **존재하지 않는다.**
보낼 방법 자체가 없다. 모든 전략은 자산 1.0으로 정규화되므로 자금 규모도 드러나지 않는다.

**Q. 손해 본 날만 빼고 보내면?**

선언이 없는 날은 **직전 보유가 그대로 유지된 것**으로 계산된다. 성과에서 빠지지 않는다.
그리고 `hold`를 포함해 며칠이나 성실하게 보고했는지가 **제출률**로 항상 함께 표시된다.

**Q. PRISM 전용인가?**

아니다. PRISM은 첫 번째 참여자일 뿐이고, 코어 스펙에 PRISM 고유 개념은 하나도 들어가지 않는다.
어떤 언어, 어떤 시스템이든 **HTTP 요청 하나**면 참여할 수 있다.

**Q. 운영자가 데이터를 조작하면?**

선언·시세·기업행위 원본은 전부 공개되며, 서로 해시로 묶여 있다.
따라서 **누구든 원본을 받아 순위 전체를 독립적으로 다시 계산할 수 있다.**
운영자가 순위를 건드리면 재계산 결과와 어긋나서 즉시 드러난다.

## 10. 기본 채점 프로파일 `stance-score/1`

> **주의: 이 절은 코어가 아니다.** 참조 구현으로 제공되는 기본값이며, 언제든 교체된다.

- 모든 전략은 자산 1.0에서 시작
- 액면분할·배당은 발생 시점에 반영 (과거를 소급해 고치지 않는다)
- 성과는 **하나의 숫자로 줄이지 않고 여러 항목을 나란히 보여준다**

  누적 수익 · 하락위험 대비 수익 · 최대낙폭 · 시장 대비 초과수익 · 최근 3개월 · 생존 기간

- 모든 전략 카드에 **평균 투자비중**과 **제출률**을 항상 함께 표시한다

마지막 줄이 중요하다. 현금을 많이 들고 있는 전략은 위험 지표가 좋게 나오는데,
투자비중을 같이 보여주면 **"노출 5%로 낸 점수"** 라는 게 한눈에 보인다.
편향을 없애려 애쓰는 것보다 **드러내는 편이 정직하고 효과적이다.**

### 거래비용 — 무엇을 반영하고 무엇을 빼는가

기준은 하나다. **모두에게 똑같이 적용되는 것만 반영하고, 사람마다 다른 것은 뺀다.**

**반영한다 — 법정 거래세.** 누가 어느 증권사에서 팔든 세율은 같다.
그리고 *"얼마나 자주 거래할 것인가"* 는 집행이 아니라 **판단**이다.
반영하지 않으면 연 100회전 전략에게 **18%p를 공짜로 주는 셈**이 된다.

**뺀다 — 증권사 수수료**(회사마다 다르다)**와 호가 스프레드·시장충격**
(주문 크기·유동성·집행 실력에 따라 달라진다). 상수로 근사하면 새로운 왜곡이 생긴다.

빠진 비용은 고회전 전략에 유리하게 작용하므로 **회전율을 카드에 항상 노출**해 해석 가능하게 한다.

> 세율은 시기와 시장에 따라 바뀐다. 값은 채점 프로파일 버전에 함께 기록하며,
> 운영 전에 반드시 확인해야 한다.

### 참가 요건은 둘뿐이다

**운영 60거래일 이상 · 청산 완료 거래 20건 이상.** 그게 전부다.

**제출률은 요건이 아니다.** 두 가지 이유다.
제출률이 막으려던 조작(*"지는 날은 선언을 생략한다"*)이 목표 비중 방식에서는
**구조적으로 불가능하다.** 선언을 생략하면 포지션이 그대로 유지되어 손실이 온전히 반영된다.
피할 방법이 없으므로 막을 것도 없다.
게다가 요건으로 삼으면 **매일 실행되지 않는 시스템이 전멸한다** — 주간 리밸런싱은 20%,
월간은 5%가 나온다. 그들은 `hold` 조차 매일 보낼 수 없다.

**투자비중도 요건이 아니다.** 하락장에서 현금으로 빠지는 것은 오답을 피한 게 아니라
정답을 고른 것이다. 판단 리더보드가 특정 판단을 금지하면 자기모순이다.

둘 다 요건이 아니라 **카드에 항상 표시되는 항목**이다. 게이트가 아니라 가시성으로 다룬다.

미달 전략은 감추지 않고 **예선**으로 따로 보여준다. 감추면 실패한 전략이 사라져 전체가 부풀려진다.

### 제출 주기는 각자 밝힌다

등록 시 `daily` · `weekly` · `monthly` · `event` 중 하나를 고른다.
제출률은 **그 주기 대비**로 계산되므로, 월 1회 도는 시스템이 매일 도는 시스템보다 불리해지지 않는다.
`event`(신호가 나올 때만)는 기대 주기가 없으므로 이 지표로 성실성을 재지 않는다.

## 11. 로드맵

**Phase 0 — 자가 대결.** 같은 코드에서 판단 모델만 바꾼 여러 인스턴스를 등록한다.
사람이 섞이면 변수가 오염되지만, 모델만 다른 동일 코드는 비교가 깨끗하다.
외부 참여자 없이도 검증이 성립한다.

**Phase 1 — 데이터 축적.** 몇 달 돌려 순위표에 실제 이력을 채운다.
빈 리더보드에는 아무도 오지 않는다. **콘텐츠가 먼저, 사람이 나중이다.**

**Phase 2 — 개방.** 쌓인 이력을 보여주며 참여를 유도한다.
이때 PRISM과 프로토콜을 완전히 분리한다.

**Phase 3 — 표준화.** 스펙 문서 공개, 참조 구현 오픈소스화, 원본 데이터 공개.
여러 리더보드가 같은 데이터를 각자의 방식으로 채점하기 시작하면 표준으로 자리 잡은 것이다.

{ "protocol":"stance/1", "strategy":"my-strategy", "seq":42,

선택 신호 (보내지 않아도 된다)

가격 · 수량 · 금액 · 시각 · 수익률 · 잔고 · 평균단가 · 계좌 정보

1. 가격은 서버가 정한다
2. 자산은 1.0에서 시작한다
3. 비중 합은 1.0을 넘을 수 없다
4. 기록은 고치거나 지울 수 없다
5. 현실에서 불가능한 체결은 인정하지 않는다

**코어가 아닌 것**

채점 방식 · 리더보드 · 기업행위 처리 · 거래비용 · 인증 방식
