# BTC 생명주기 증거 연결과 정책 고정 작업

## 범위와 우선순위

사용자가 2026-10-05 주간 점검의 다음 세 작업을 지금 진행하도록 요청했다.
기준선은 `3a0290bdd4d1b0548c3d871c528c7d0991f7c0f7`이다.
이번 작업은 M0.1/M0.2·M1.1·M3의 **관측·증거 연결**과 M2/M5의 사전 고정 기록이다.
매매 판단·프롬프트·위험 한도·주문 정책·모델·스케줄은 바꾸지 않는다.

진행 순서:
1. 같은 채팅의 주간 실행 기록을 확인하고 기존 읽기 전용 Packet으로 기준 상태를 고정한다.
2. 종료 거래와 진행 중 거래를 구분하고 정확한 intent/order/exec/정산/공지 ID를 연결한다.
3. 기존 루프가 이미 받은 금융·펀딩 자료, 당시 판단/실행 코드, 정산 확인 시각을 선택적 관측으로 보존한다.
4. 과거 자료는 실제로 남은 근거만 검증하며, 없던 당시 시각·버전·원본을 사후에 만들어 넣지 않는다.
5. 최신 운영 요약과 남은 작업을 로드맵에 반영하고, 현재 판단 정책을 고정한 전진 관측 시작점을 기록한다.

## 관측 경계

- 거래 호출 중에는 크기/개수 제한 버퍼에만 보존한다. 별도 DB 저장은 거래 잠금 밖에서 수행한다.
- audit 저장·해시·직렬화 실패는 주문·보호·정산 결과를 바꾸지 않는다. audit 목적의 거래 연결
  commit/rollback, 대기·재시도, 추가 거래소 API 호출을 넣지 않는다.
- 프로세스 종료 전에 버퍼가 저장되지 않으면 증거 누락이다. 기존 영속 주문 intent를 대체하지 않는다.
- 판단 입력/승인 intent와 실제 주문 호출의 버전을 분리한다. 이후 버전에서 복구된 오래된 주문의
  원래 판단 버전을 새 버전으로 덮어쓰지 않는다.
- 실제 로드된 코드와 디스크/배포 버전을 확인할 수 없으면 UNKNOWN/MIXED로 남긴다.
  exporter의 버전이나 지금의 HEAD를 과거 매매 버전으로 쓰지 않는다.
- 판단과 실행 코드의 검증 상태를 분리한다. 보호 전용 실행에서 사용하지 않은 판단
  모듈을 강제로 로드하거나 검증 성공으로 만들지 않는다. 판단 이벤트는 판단 상태,
  주문·금융·정산 이벤트는 실행 상태를 사용하며 누락된 상태는 UNKNOWN이다.

## 정확한 연결

- 판단: slot + input_id + 원본 snapshot/context hash.
- 승인 계획: action/intent/scenario ID + 최종 payload hash + 당시 2% 위험과 미체결 예약.
- 주문: 기존 변경 호출의 method/request/응답·시각. ACK는 체결이 아니다.
- 금융: 같은 시나리오의 raw execution/transaction, owned order, 관측 계좌, 펀딩 일정/원본/간격/다음 시각.
- 정산: 새 정산 행이 실제 기록된 host 시각. 마지막 청산 체결 시각과 분리한다.
- 공지: broker_notices.scenario_id → event_id → outbox.event_id → SENT와 실제 message_id.
  SENDING/UNKNOWN은 전송 확인이 아니며 과거 메시지를 다시 보내지 않는다.

기존 원자료로 gross/fee/funding/net을 재검증한 범위와 단순 저장 정산값을 분리한다.
진행 중인 거래를 완료 실적에 넣지 않고, 과거 결측을 시각 근접 매칭이나 현재 자료로 채우지 않는다.
새 관측 표가 없는 과거 DB도 기존 Packet을 생성할 수 있어야 한다.

## 정책 고정

- 전체 배포 버전, 판단 정책 hash, 실행/위험 hash를 분리한다.
- 판단 fingerprint는 프롬프트만이 아니라 모델·응답 계약·시세 특징·지표·계좌/과거 판단 문맥의
  실제 구성 경로를 포함한다. 기록 방법·원본 구성 요소·환경 버전도 보존한다.
- 정책 변경은 새 검증 구간으로 구분한다. 실행 안전 수정도 별도 실행 버전으로 표시한다.
  알림 문구만 바뀌었다고 판단 정책 표본을 임의로 바꾸거나 합치지 않는다.
- 모델 별칭/설정 고정은 공급자의 비공개 모델 가중치나 결정의 동일성을 보장하지 않는다.
- 시작 시 이미 보유 중인 거래는 carry-in이다. 새 관측 이전 생명주기까지 검증된 것으로 세지 않는다.
- 이번 작업 이후 판단 정책 튜닝은 새로운 사용자 승인/새 구간으로 구분한다. 새 상주 배치나 예약은 만들지 않는다.

## 검증·완료 기준

기존 테스트를 먼저 통과시키고 누락/오류/중복/다른 시나리오/DB 잠금/버퍼 초과 회귀를 추가한다.
audit 실패에도 실제 fake broker 호출 횟수·순서·결과가 동일해야 한다.
소스 DB는 읽기 전용으로 검사하고 Packet은 비식별 ID·정확한 범위·결측 사유를 내보낸다.
원본 API 자료·계좌 식별자·자격증명·전체 프롬프트는 공개 Packet이나 저장소에 넣지 않는다.

구현, 격리 테스트, CI, 배포, 정규 실행, 실제 종료 생명주기, 수익성 입증을 분리한다.
종료를 기다려야 하는 항목은 남겨 두고 강제 청산이나 시험 주문으로 완료 표본을 만들지 않는다.
표본·당시 자료가 부족하면 INSUFFICIENT/MISSING을 유지한다.

## 10월 5일 사후 금융 대조

기준 Packet `e18cce0c67feb43a83253fc60642f9ca1a046601446ecb04ed2f97dd758287fc`은
종료·정산 3건, 진행 중 1건, 무체결 취소 2건이다. 종료 3건은 정확한 전체 execution ID
집합으로 이미 보존된 금융 자료에 연결했다. 별도 Decimal 평균원가 산식으로 gross/수수료와
시점별 잔량을 계산하고, 새로 조회한 공개 과거 펀딩률로 펀딩을 대조했다.

- 종료 순손익: `+46.15235860`, `-29.006568`, `-11.70722073` USDT.
- 합계: `+5.43856987` USDT. 진행 거래의 부분실현·평가손익은 포함하지 않는다.
- 금액 대조 허용 오차: `0.00000001` USDT. 공개 가격/펀딩률 정밀도에 따른 차이가
  있으므로 원시 산식의 무조건 완전 일치로 표현하지 않는다.
- 공개 펀딩은 **지금 수신한 과거 사실 대조**다. 봇이 당시 받은 응답을 복원한 것이 아니다.
  과거 펀딩 간격은 연속 공개 이력과 현재 instrument 간격으로 대조했다.
- 과거 정책 버전·실제 정산 확인 시각은 여전히 미보존이다. 과거 DB에 소급 입력하지 않는다.

## 새 전진 구간의 사전 규칙

1. 시작점은 이 관측 보완의 검증된 배포 시각이다. 배포 receipt와 최초 자연 실행의
   manifest를 별도 보존한다. 작성 시점의 SHA를 과거 거래 버전으로 대체하지 않는다.
2. 시작 전부터 진행 중인 거래는 carry-in으로 표시한다. 전진 표본은 시작 이후 승인된
   OPEN부터 자연 종료·정산까지 해당 증거가 있는 거래만 별도 집계한다.
3. 정책 AST hash, 실행 AST hash, Python/pandas/numpy 환경을 함께 구분한다.
   검증 범위는 선택한 함수·literal 설정이며 collector/OAuth/control/locking을 포함한
   전체 전이 의존 경로가 고정됐다는 보증은 아니다. Git은 관측 checkout 값이다.
4. 손실 거래·실패·미체결 취소·결측을 숨기거나 유리한 구간만 선택하지 않는다.
   종료 순손익과 진행 평가손익, 수수료/펀딩을 분리하고 결측률도 함께 보고한다.
5. 큰 추세 포착과 증액 효율은 진입/증액 시점·위험·추가 수량과 이후 실제 체결/비용을
   연결해 평가한다. 이 구현은 해당 성과가 개선됐다는 분석 결과가 아니다.
6. 기존 주간 점검에서 수집 상태를 검토한다. 새 스케줄·상주 배치를 추가하지 않는다.
   정해진 표본 수에 도달했다는 이유만으로 수익성 입증이나 실계좌 승격을 자동 처리하지 않는다.

## 구현의 남은 한계

- 감사 저장은 best-effort다. 프로세스 종료·DB 경합·크기 초과 시 증거가 빠질 수 있다.
  주문 보호보다 감사 저장을 우선하지 않으며, 누락을 성공으로 표시하지 않는다.
- Packet의 `SOURCE_RECONCILIATION_VERIFIED`는 생산 순수 정산 함수의 원본 재검증이다.
  별도 사후 산식 대조와 구분하며 `independent_accounting_complete=False`를 유지한다.
- 전체 실행의 연속성까지 증명하는 coverage가 아직 없으므로 `COMPLETE`가 아니라
  `PARTIAL`이다. 자연 종료 전에는 생명주기 완료를 주장하지 않는다.
- 과거 SENDING/UNKNOWN 및 누락된 종료 공지는 임의 재전송하지 않는다.

읽기 전용 공지 연결에서는 6개 시나리오에 36개 이벤트를 정확히 연결했고, 그중
35개는 SENT와 양의 message_id가 있다. 1개 SENDING은 전달 미확정이다.
종료 3건 중 2건의 CLOSED 영수증을 확인했으며 나머지 1건은 누락 상태를 유지한다.
이 집계는 조회 시점의 과거 기록이며 새로운 공지를 발송한 결과가 아니다.
