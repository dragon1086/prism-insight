# BTC 상태 재공지 금지와 미완료 후속

## 사용자 요청 대조

PR #892~#894(`c10b7e57`)에서 기존 포지션 여부 대조, 간결한 알림, 공개 시세 10006
재조회·후모델 잠금 대기, 판단/보호를 나눈 경보를 구현·배포했다.
그러나 기존 포지션의 '최초 확인'을 새 제목으로 다시 보내는 것은 사용자 요구를 충족하지
못했다. 이번 우선 규칙은 **실제 체결이나 검증된 포지션·TP/SL 변화가 없으면 재공지하지 않는다**다.

## 수정 계획과 범위

M3 알림 의미·중복 방지와 M0 실행 관측 보완이다. 전략·LLM 프롬프트·위험 한도·계좌·
cron은 그대로 유지한다. 기존 동작의 반례를 먼저 테스트하고 아래 세 경계만 수정한다.

1. 최초 스냅샷은 조용히 비교 기준만 저장한다. 첫 체결·추가 체결·청산은 기존 체결 근거로
   알리고, 이후 실제 TP/SL·수량·평단 변화는 전후 비교로 한 번 알린다. 시각·증거금·순자산·
   주문 ID 변화만으로 알리지 않는다. 원장을 삭제하거나 과거 공지를 재발송하지 않는다.
2. 초기화의 알려진 LockBusy는 실패나 복구가 아닌 건너뜀으로 구분한다. 이 경로에서
   모델·주문·알림을 실행하지 않는다. 다른 초기화 오류는 fail-closed를 유지하고 고정 단계와
   허용된 예외 종류만 기록한다. 원시 예외·자격증명은 출력하지 않는다.
3. Telegram 전송 뒤 영수증 저장은 이미 소유한 SENDING 이벤트만 SQLite 조건부 갱신한다.
   이 메타데이터 작업에 거래 잠금을 다시 요구해 알려진 영수증을 잃지 않게 한다.
   실제 DB 기록 실패는 성공으로 꾸미지 않으며, 네트워크 전송은 재시도하지 않는다.

## 과거 이력의 제한

2026-10-04 01:28 KST 읽기 전용 점검에서 수신 영수증 미확정 SENDING은 총 3건이었다.
10/03 14:15:15, 10/04 00:00:16, 01:00:07의 PENDING으로, 모두 운영자용 경보다.
공개 매매 알림의 중복 진입 체결이 아니다. 이 3건은 실제 전달 여부를 소급 확정할 수
없으므로 SENT로 바꾸거나 재전송하지 않는다. 새 코드 보완과 옛 수신 확정은 별개다.

이번 배포 전 점검에서 출처가 확인된 initial_protection은 기존 SENT 한 건이며,
broker backlog 및 QUEUED initial_protection은 0건이었다. 현재 운영 데이터에는
과거 대기 재공지를 정리하는 별도 마이그레이션이 필요하지 않다.
임의 제목 문자열로 다른 실제 보호 변경을 삭제·차단하지 않는다.

## 검증 기준

- 이미 공지된 체결 뒤 첫 기준 저장·동일 관측·재시작은 새 공개 메시지 0건.
- 진짜 첫/추가 체결·부분/전량 청산 및 TP만 변경한 사례는 필요한 알림 유지.
- 생성자 잠금 경합은 skipped heartbeat, 실제 DB/초기화 오류는 blocked 및 안전한 진단.
- 별도 프로세스가 거래 잠금을 보유한 중에도 전송 영수증 저장, 정확히 1회 전송.
- 수신 미확인·DB 기록 실패·동시 flush·상태 변경에서 허위 SENT나 자동 재발송 금지.
- 전체 격리 테스트, exact head CI, 운영 Python 격리 검증 후 clean/ff-only 배포.
- 운영에서 수동 매매/알림 테스트 없이 자연 실행과 대기열을 읽기 전용 확인한다.
  실제 새 체결/새 Telegram 영수증이 없으면 미관측으로 명시한다.
