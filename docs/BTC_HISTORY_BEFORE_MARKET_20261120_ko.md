# BTC 과거 조회 뒤 새 시세 수집 — 2026-11-20

M0 입력 신선도 결함 수리입니다. 매매 프롬프트·위험 한도·주문 정책을 바꾸지 않습니다.

## 문제와 최소 변경

실제11/20 두 회차에서 시장 입력 생성부터 문맥 준비까지63.238초·69.030초가 지났습니다. 기존 `_tick`은 계좌 확인 → 공개 시세 수집 → 과거 정산 조회 → 입력 저장 → 판단 순서였습니다. 과거 조회가 시세 수집 뒤에 있어 그 시간이 입력의120초 유효 시간을 소모했습니다. 운영 EXPLAIN은 감사 테이블 전체 SCAN을 확인했으나 그것이 과거 지연 전부의 원인이었다고 단정하지 않습니다.

과거 정산 조회를 기존 실행 mutex 밖에서 먼저 끝내고 실제 공개 시세를 새로 수집합니다. 기록된 시각을 고쳐 신선하게 보이게 하지 않습니다. 공급자의 as_of를 그대로 사용하며, 최초 계좌 관측 시각도 그대로 남깁니다. 조회 자체를 빠르게 하는 변경은 아닙니다.

## 지키는 계약

- 최초 계좌가120초를 넘으면 신선한 시세가 있어도 모델을 호출하지 않습니다. 지연 없는 구형 호출의 기존 계좌 계약도 유지합니다.
- 시세120초·검토75초·응답 유효기간·같은 slot·상태 버전·completed_ids·실제 잔량·정산·보호·실행 권한을 그대로 검사합니다.
- 과거 조회 중 다른 프로세스의 보호 작업을 막지 않습니다. 상태가 달라지면 새 시세가 있어도 결정을 폐기합니다.
- 과거 정산의 중복·일치 검사를 생략하지 않습니다. 운영 DB 인덱스 생성·복사·VACUUM·데이터·설정·예약 변경은 없습니다.

## 검증 근거

65초 과거 조회 뒤60초 판단을 수행하는 회귀는 수정 전 낡은 입력으로 실패했습니다. 수정 뒤에는 조회 종료 후 snapshot 콜백이 반환한 실제 새 시각을 사용하며, 원 계좌 시각과120초 제한은 유지합니다.121초 계좌 만료와 동시 상태 변경은 계속 차단합니다. 과거 조회 중 실제 별도 프로세스가 보호 mutex를 잡을 수 있는지 검사합니다. 기존 snapshot 잠금·보유 문맥·runtime·정확 fresh/frozen 파이프라인도 대조합니다.

기존 main에서도 실패하는 폐기 주기 fixture2건을 재현했습니다.15분은 현재 분석 주기이므로 폐기해야 한다던 fixture를5분으로 바로잡고,15분 의견은 유지되는 반례도 추가했습니다. 운영 시간프레임 코드는 바꾸지 않았습니다. 해당 문맥 검사를 CI의 기존 BTC 안전 목록에 연결합니다.

이 문서는 수리의 범위와 검증 계약입니다. 정확한 head의 전체 CI, 서버 반영, 최초 정기 실행, 이후 자연 주문과 수익성은 각각 실제 영수증으로 확인합니다. 본 수리만으로 승률·수익 개선을 주장하지 않습니다.
