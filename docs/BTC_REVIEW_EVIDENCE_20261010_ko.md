# BTC 재평가 등록 영수증과 MA 참조 보완

## 범위와 선행 근거

사용자는 10/10 최근3연속 손실 복기 후 수정·검증·데모 반영을 승인했다. 이번 단계는
M3 기록/설명 정합성과 그 입력을 이용하는 M4 판단 근거 보완이다. 마지막 실제 거래의
16:20 조건82595가3개 슬롯 때문에 추가되지 않았고 다음입력에는capacity_retained만 있었다.
또 실제12h 확정MA10=84056.08을MA35로 부른 설명을 확인했다. 숫자 계산이나 SL 실행 오류와 구분한다.

단일 손실에 맞춰 진입/청산 임계값을 바꾸지 않는다. 10배·위험 한도·회복 단계·5분 판단/1분 보호,
15분 최소/30분·1시간 우선 및 상위 프레임 참고를 유지한다. 새 공개 알림·상주 하네스는 만들지 않는다.

## 데이터·권한 흐름

실제 시장/계좌 입력 → `engine/scenario_ma_context.py`의 안정된 level ID와 label →
`live/scenario_llm.py`의 조립 프롬프트 → 기존 wire/가격/위험 검증 →
`live/scenario_review_memory.py::apply_review`의 보조 기록 → runtime의 상태/결과 보존 순서다.
보조 메타데이터는 주문 허가가 아니다. 잘못된 메타 때문에 검증된 EXIT/보호 변경을 차단하지 않는다.
신규 보조 기록은 다음 모델 문맥과 원래 결정 이력으로 연결하고 거래소 체결로 표현하지 않는다.

## 변경 계약

- 최근 한 번의 bounded `review_update_receipt`를 저장한다. 최대3조건·3ACK에 대해
  ADDED/ALREADY_RETAINED/NOT_ADDED_CAPACITY와 정확한 host ID, ACK 결과, 남은 슬롯을 표시한다.
- 모든 ACK ID와 새 도달 시각 일치부터 검증한다. 기존 조건은 자동 삭제하지 않는다.
  replace+정확한 ID로 명시적으로 공간을 만든 경우에만 새 조건을 추가한다.
- 기존 부분 수용 의미를 유지한다. full 이후 요청한 조건도 실제 이미 저장된 조건인지 구분하되
  추가를 강제하거나3개 한도를 늘리지 않는다. 누락/잘못된 메타·오래된 상태·재시작을 안전하게 처리한다.
- 영수증에는 잘못된 원문/긴 rationale를 복사하지 않고 메모리 등록과 주문/체결을 명시적으로 구분한다.
  정상 trade 공지를 늘리지 않는다. 다음 모델이 제안했다는 이유만으로 등록됐다고 말하지 않게 한다.
- 각 기존 MA level에 호스트가 만든 짧은 canonical label을 추가한다(예:12h MA10 confirmed).
  중요한 MA를 인용할 때 안정된level ID와 그 항목의 값을 함께 사용하도록 한다. 숫자나 MA 계산은 유지한다.
- 자유문장 전체를 취약한 정규식으로 판정하거나 그 문장 때문에 EXIT를 거부하지 않는다.
  canonical label은 혼동을 줄이기 위한 입력 보완이지 모든 생성 설명의 정확성을 보장하는 장치가 아니다.

## 고정 검증

1. 실제16:20원래메타를 재현하여 기존3개 보존/82595미등록을 개별영수증으로 표시한다.
   같은 입력에서 올바른replace를 사용하는 대조를 시험하되 운영 상태를 수정하지 않는다.
2. 다중ACK 중 뒤의잘못된ID·fresh-hit경합·같은조건재제안·빈배열·미등록후재시작·oldstate·invalidmemory,
   양방향조건·보조메타오류인EXIT/보호ADJUST를 검사한다. core실패는 영수증수락을 만들지 않는다.
3. 12h MA10/35 확정/형성 값과 label/id 연결, 원래 숫자/시간/위험 사실 보존,100KB상한을 검사한다.
4. 실제latest거래15:40/15:55/16:20/16:25 입력4개에서 기존/후보 각1회, **총8회** 주문 없는OAuth
   비교를 사전에 고정한다. 후보16:25문맥에는 실제직전16:20요청의 새호스트 처리영수증만 추가한다.
   이는 원래같은 시장/계좌에 검증된추가기록을 제공하는 비교이며 바이트까지같은입력 비교는 아니다.
   모델 응답을 원하는 방향으로 만들기 위한 재호출은 하지 않는다. 유효응답·거절·불명확 설명을 모두 보존한다.
5. 실제 응답의 label인용 정확도/조건 교체 제안/기록 일치를 살피되 행동 변화나 손실 회피를 강요하지 않는다.
   기존 입력에 가까운 고점·비용 사실이 있어도 이를 쓰는지 별도 관측한다. 이 비교로 수익률을 생성하지 않는다.

## 승인·배포·롤백

회귀 먼저, 독립 검토, 전체/서버격리/최종head CI 후 clean·ff-only로 demo서버에만 반영한다.
스모크와 첫 정규 실행을 구분한다. 기존진행시나리오는carry-in으로 기록한다. 위험/주문 변경 없이
state에 보조영수증을 추가하므로 이전state도 읽을 수 있어야 한다. 문제시 새커밋으로 이 보완만
되돌리고 운영DB/주문/원장을 삭제하지 않는다. 기록 개선·생성 설명·성과 입증은 별도 판정한다.
