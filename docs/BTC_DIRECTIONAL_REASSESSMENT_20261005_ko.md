# BTC 양방향·미체결 재평가

## 1. 유형·승인·범위

2026-10-05 사용자가 롱·숏을 함께 비교하고 미체결 주문도 재평가하도록 요청했다.
기준선은 `9af851bacdffc2c328298028c082b1af0d487a42`이다. M4의 **경제적 판단 프롬프트 변경**이며
추격 엔진의 오류 수정이나 수익 향상 입증이 아니다. #923에서 시작한 고정 정책 구간과 별도의 새 정책 구간으로 기록한다.

BTC demo MAIN의 시스템 프롬프트·회귀·검토 문서만 바꾼다. 모델, 출력 스키마, 시세 입력,
위험 한도, 거래 실행기, 마디가격, 기존 주문, 스케줄, 공지 형식은 유지한다. 새 반등 확인 주문이나
자동 방향 전환 기능을 만들지 않는다.

## 2. 근거·가설·반례

13:30 숏은 반등 지정가·추격0으로 제출되어 미체결 만료됐다. 롱·숏 추격 엔진의 대칭 검사는
통과했다. 무포지션의 이전 회복 대기 문맥이 다시 들어가고, 일부 모델 사유가 하락을 롱 진입
부적합으로만 설명했다. 방향 선택과 진입 방식 선택을 분리하면 이러한 누락을 줄일 수 있다는 가설이다.

그러나 단기 하락이 항상 유리한 숏은 아니다. 이미 멀어진 가격을 같은 TP/SL로 추격하면
보상/위험이 악화된다. 기존 표본에서도 가격 거리 비율이1.74→0.58로 줄었다. 약한 근거·비용·
불리한 무효화에서는 WAIT가 정답일 수 있다. 숏이나 추격 횟수를 성공 지표로 삼지 않는다.

## 3. 실제 흐름·호환성·모순 정리

입력: `scenario_snapshot`의 진행 봉과30분/1시간 주요 프레임, `ScenarioRuntime._context()`의
확인된 계좌·current_plan·pending_entries·recent_waits를 `scenario_llm.propose()`에 전달한다.
모델 출력은 strict wire → 최신 재조정 → 가격 보정 → 경제 validator → 영속 intent → 실행기로 이어진다.

- 무포지션: LONG/SHORT/WAIT를 각각 근거·무효화·비용 후 손익비·진입 가능성으로 비교한다.
  롱 근거 부족을 곧 숏 근거로 삼지 않으며 반대도 같다. 상위봉은 참고이지 거부권이 아니다.
- 활성 시나리오: 같은 방향의 WAIT/ADJUST/EXIT만 가능하다. 더 나은 반대 방향을 생각하더라도
  기존 노출·미체결을 확인하고 완전히 정산된 flat 이후 별도 OPEN을 판단한다. 헤지·즉시 뒤집기 없음.
- 미체결: 고정 반등 주문 유지, 가격/TP/SL/수량 재계획, 취소를 비교한다. 수량·손절을 위험
  한도에 끼워 맞추거나 추격을 의무화하지 않는다. 추격 시 같은 목표·손절의 손익비 악화도 고려한다.
- 기존 주문 유지: WAIT. 취소만: WAIT+현재 pending ID. 대체: ADJUST+새 증분 주문 ID와
  명시적 취소, 또는 예산상 필요하면 먼저 취소하고 새 확인 문맥에서 재계획한다.
- ADJUST는 전체 의도한 출구 계획을 포함한다. 실제 취소 전에는 기존 예약 위험을 빼지 않는다.
  이미 체결된 TP를 복원하거나 새 시나리오 이름으로 예산을 초기화하지 않는다.
- chase는 최신 intent의 새 entries에만 적용된다. ADJUST의 entries가 비어 있으면 과거 주문을
  추격시키지 않는다. 기존 최대50bps·3회·60초·확인 취소·재위험 검사를 유지한다.
- 가격에 닿는 지정가는 반등 확인 후 진입이 아니다. 추가 확인을 원하면 WAIT에서 관측 조건을
  설명한 뒤 다음 실제 입력으로 판단한다. Limit 주문을 미래 확인 트리거라고 설명하지 않는다.
- 이전 WAIT는 평가 대상이지 지시가 아니다. 지금도 유효한지 재평가하고 방향이 다른 회복 조건을
  양방향 진입의 공통 필수 조건으로 만들지 않는다. 이 작업에서 이력 조회 방식은 바꾸지 않는다.
- 2% 원래 시나리오 예산·10배·미체결 예약·손절 완화 금지·일/연속 손실 차단은 그대로다.

사용자가 양방향과 재평가 방향을 선택했으므로 이 범위를 구현한다. 강제 추격·새 위험 예산·
다른 주문 유형 같은 별도 경제적 선택은 추가하지 않는다.

## 4. 사전 고정 검증

1. 기존 테스트 통과와 새 요구 회귀의 RED를 확인한 뒤 가장 좁은 프롬프트 층만 변경한다.
2. 실제 wire/validator·fake broker에서 양방향 유효 진입, 활성 반대 방향 거부, 위험 초과,
   취소 전 예약 유지, 미체결 대체, 추격0/양수, 불확실 취소 중복 금지를 확인한다.
3. 같은 보존 입력으로 기존/후보 OAuth 모델 제안을 비교한다.13:30 flat,13:45 flat,
   13:35 SHORT 미체결,13:35 입력에 신규 위험 차단만 추가한 합성 반례를 사전 고정한다.
   조건4개×기존/후보×2회=16개. 시간·가격·계좌 입력은 같고 프롬프트만 다르게 한다.
4. 모든 응답·오류·거절을 남긴다. 주문·운영 DB·텔레그램 발송을 연결하지 않는다.
   합성 위험 차단은 실제 당시 상태가 아니며 별도로 표시한다.
5. 이16개는 작은 계약·의도 점검이다. 더 많은 진입·추격을 성공으로 채점하지 않고,
   수익성·일반적 인과효과·모델 편향 해소를 입증했다고 표현하지 않는다.
6. 별도 미래 입력은 holdout으로 남긴다. 과거 하락 구간에서 수익이 나는 답을 맞추도록
   반복 튜닝하지 않는다. 안전 제약 위반·기존 주문 복제·필수 숏/추격 오해가 보이면 보류한다.

## 5. 배포·관측·복귀

전체 격리 테스트, 독립 논리 검토, 정확한 head의 CI가 통과하면 정상 PR/ff-only 절차를 따른다.
배포·운영 스모크·첫 자연5분 판단·실제 체결·수익성을 구분한다. 새 정책/실행/환경 hash를
기존 증거 기록에서 확인하고, 이전 정책 구간과 손익 표본을 섞지 않는다.

일주일 후 기존 주간 점검에서 대기 사유·미체결 유지/변경·실제 취소/체결·비용을 검토한다.
표본이 작으면 INSUFFICIENT를 유지한다. 새 예약·상주 모니터링은 만들지 않는다.
위험 우회·방향 강제·과도한 주문 교체가 확인되면 검증된 소스 되돌림으로 프롬프트만 복귀한다.
이미 승인된 intent나 보호 주문을 수동 삭제·재실행하지 않는다.

## 6. 사전 고정 비교와 구현 검증 결과

기존 관련120개 테스트를 먼저 통과시키고 새 프레이밍 회귀2개의 RED를 확인했다.
후보에서 wire·validator·fake broker·모델 파서 관련175개가 통과했다. 전체 BTC 검증은
로컬3,184개 통과/12개 skip, 서버 Python3.11 격리3,195개 통과/1개 skip이며 네트워크 시도0이다.
실행 코드 AST에서 SYSTEM_PROMPT를 제외한 부분은 기준선과 동일함을 확인했다.

사전 고정 A/B16개는 모두 wire·경제 validator를 통과했으며 **기존8 WAIT / 후보8 WAIT**였다.
후보의 일부 flat 설명은 롱 회복과 숏 하방 지속 조건을 구분했다. 미체결 사례는 두 정책 모두
기존 반등 지정가를 유지했고, 합성 위험 차단 사례에는 새 진입이 없었다. 대기 자체가 틀렸다는
정답을 넣지 않았으며 신규 진입·추격·수익이 개선됐다고 해석하지 않는다.

이 비교는 실제 두 flat 시점과 한 pending 시점, 한 합성 위험 차단 조건의 작은 표본이다.
원응답은 사후 생성됐고 실제 과거 결정을 대체하지 않는다. 후보가 반복 대기를 일반적으로
해소하거나 모든 내부 판단을 대칭화했다는 보증이 아니다. 더 많은 거래가 나오도록 재튜닝하지 않았다.

소스 검토에서 “확인 대기→WAIT”가 기존 지정가를 남겨 먼저 체결될 수 있는 모순을 발견했다.
조건과 양립하지 않는 기존 주문은 WAIT+cancel_entry_ids로 취소 요청하고 정확한 확인을
기다리도록 명시했다. 배포·첫 자연 실행은 PR 운영 receipt에서 별도로 확인한다.
