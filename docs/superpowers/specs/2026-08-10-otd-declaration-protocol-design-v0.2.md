## 0. 이 문서를 읽는 법

v0.1 설계를 검토한 결과 **리더보드를 무의미하게 만드는 구멍 5개**와 **원칙끼리 서로 충돌하는 지점 3개**가 발견되었다.
v0.2는 그것을 메운 판이다. v0.1을 읽지 않아도 이 문서만으로 완결된다.

또한 v0.1은 금융공학 용어를 그대로 썼다. NAV, 드리프트, 폴드, 밴드 같은 말은
**참여자가 잘못 이해하면 그대로 데이터 오염으로 이어진다.** v0.2는 용어를 전부 우리말로 바꿨다.

### 0.1 용어 사전

이 문서에 나오는 모든 개념어다. 이게 전부다.

**운용자산** — 이 전략이 굴리는 돈의 총합. 즉 `남은 현금 + 보유 주식 평가액`.
업계에서는 NAV(Net Asset Value)라 부르지만 이 문서에서는 쓰지 않는다.
가장 중요한 개념이므로 §4.4에서 따로 자세히 다룬다.

**투입비중** — 한 번 살 때 운용자산의 몇 %를 넣었는지. `0.1` = 10%.

**매도비율** — 한 번 팔 때 **그 종목 보유 수량의** 몇 %를 팔았는지. `0.5` = 절반.

**선언** — 참여자가 서버에 보내는 매매 통보 한 건. 이 프로토콜의 유일한 입력.

**원장(Ledger)** — 한 번 기록되면 영원히 수정·삭제되지 않는 사실 기록.
선언, 접수시각, 그 순간 찍은 시세가 여기 들어간다.

**계산장부** — 원장을 처음부터 다시 읽어 만들어낸 결과물. 보유 현황, 자산 추이, 순위가 여기 속한다.
**언제든 지우고 다시 만들 수 있다.** 원장과 계산장부의 분리가 v0.2의 핵심 구조 변경이다.

**장부 재구성** — 원장의 선언들을 시간 순서대로 다시 재생해서 현재 상태를 만들어내는 것.
v0.1의 "fold"를 우리말로 바꾼 것이다.

**접수시각** — 서버가 선언을 받은 시각. 데이터베이스가 직접 찍으며 참여자는 건드릴 수 없다.
**채점에 쓰이는 유일한 권위 시각이다.**

**확정단가** — 서버가 정한 체결 가격. 한 번 정해지면 바뀌지 않는다.

**어긋남** — 참여자의 실제 계좌와 서버가 재구성한 장부가 시간이 지나며 벌어지는 현상.
v0.1의 "드리프트".

**투자비중** — 운용자산 중 실제로 주식에 들어가 있는 비율. 현금만 들고 있으면 0%.
**v0.2에서 새로 추가된 핵심 지표다.** 이유는 §8.3에 있다.

**최대낙폭** — 고점 대비 가장 크게 깨졌던 폭. 업계 용어 MDD.

**하락위험 대비 수익 지수** — 손실 쪽 변동만 위험으로 보고 수익을 나눈 값. 업계 용어 Sortino Ratio.
"까먹을 때 얼마나 덜 까먹으면서 벌었나"를 재는 숫자다.

**낙폭 대비 수익 지수** — 연 수익을 최대낙폭으로 나눈 값. 업계 용어 Calmar Ratio.

### 0.2 v0.1 대비 무엇이 바뀌었나

| # | 변경 | 이유 (상세) |
|---|---|---|
| 1 | **신고 단가(`price`) 필드 삭제** | 공짜 조작 옵션이었다 (§5.1) |
| 2 | **원장과 계산장부를 테이블로 분리** | 무결성 봉인이 채점값을 못 덮고 있었다 (§7.1) |
| 3 | **`hold`(유지 선언) 이벤트 추가** | 저회전 전략이 참가 요건에서 전멸했다 (§4.3) |
| 4 | **기업행위를 이벤트로 처리** | 수정주가 방식은 과거를 고치므로 원장 불변성과 충돌했다 (§6.5) |
| 5 | **현금 부족 시 거부 → 축소 수락** | 매수 거부 한 번이 전략을 영구히 망가뜨렸다 (§6.3) |
| 6 | **참가 요건에 투자비중 추가** | 현금만 들고 있으면 순위 1등이 되는 구멍 (§8.3) |
| 7 | **한 전략 = 한 시장 = 한 통화 강제** | 다중시장 전략의 자산 계산이 정의 불능이었다 (§4.1) |
| 8 | **장 마감 후 선언은 다음 거래일 시가** | 종가 체결은 현실에서 불가능한 가격이다 (§5.4) |
| 9 | **상한가·거래정지 체결 불가 판정** | 못 사는 가격에 샀다고 인정하고 있었다 (§5.5) |
| 10 | **"불변"과 "공개"를 분리** | 개인정보 삭제 요구와 삭제 불가 원칙이 충돌했다 (§7.4) |
| 11 | **`reduce` → `sell_ratio` 개명** | 동사라서 값의 의미가 드러나지 않았다 |
| 12 | **요청 한도 도입** | 지울 수 없는 테이블에 무제한 쓰기가 열려 있었다 (§7.5) |

## 1. 배경과 목적

이슈 #328의 원래 취지는 다음과 같다.

> *"같은 시스템을 돌리더라도 LLM의 확률적인 특성상 다른 종목으로 포트폴리오가 구성되므로,
> 자금의 응집력이 약해서 장기적으로 전략이 생존한다는 걸 증명"*

이를 검증하려면 **여러 전략의 매매 판단을 같은 잣대로 채점**할 수 있어야 한다.
그런데 각자 로컬에서 돌리는 시스템의 **수익률을 신고받는 방식은 100% 위조 가능**하므로 리더보드가 성립하지 않는다.

**OTD(Open Trading Declaration)** 는 이 문제를 한 문장으로 뒤집는다.

> **실적을 신고받지 말고, 판단을 선언받아라. 성과는 서버가 계산한다.**

### 시스템 무관성

OTD는 PRISM-INSIGHT 전용이 아니다. **모든 시스템 트레이딩이 대상**이다.
PRISM은 첫 번째 참여자일 뿐이며, 프로토콜에는 PRISM 고유 개념이 들어가지 않는다.

## 2. 설계 원칙

다섯 문장이 이 설계의 전부다. 원칙 4와 5는 v0.2에서 추가되었다.

1. **계산된 값을 신고받지 않는다.** 수익률·잔고·계좌규모는 받지 않는다. 전부 서버가 계산하거나 애초에 불필요하다.
2. **서버가 받은 시각보다 앞선 가격은 절대 인정하지 않는다.** 이것이 위조 방지의 뿌리다.
3. **상태를 받지 말고 사건을 받아 서버가 재구성한다.** 보유 현황과 자산은 선언을 재생해 만든다.
4. **원장은 절대 고치지 않고, 계산장부는 언제든 다시 만든다.** 이 둘을 섞으면 무결성과 운영이 동시에 무너진다.
5. **조작을 감시로 막지 말고 유인 자체를 없앤다.** 이득을 볼 방법이 없으면 감시가 필요 없다.

원칙 3의 부수 효과로 **분할매수·분할매도가 별도 설계 없이 자동 해결**된다. 그냥 사건이 여러 개일 뿐이다.

### 원칙 4가 새로 추가된 이유

v0.1은 하나의 `declarations` 테이블에 참여자 제출값과 서버 계산값을 함께 담고,
그 테이블에 대해 "수정·삭제 전면 금지"를 걸었다. 여기에 두 가지 문제가 있었다.

첫째, 무결성 해시가 INSERT 시점에 계산되는데 그 시점에 확정단가·상태·자산은 전부 비어 있다.
**즉 채점을 실제로 좌우하는 값들이 봉인 바깥에 있었다.**

둘째, 채점 로직에 버그가 발견되어 전체를 다시 계산해야 할 때,
수정이 금지된 테이블 안에 계산 결과가 들어 있으면 손댈 방법이 없다.

원장(고칠 수 없음)과 계산장부(언제든 재생성)를 분리하면 두 문제가 동시에 사라진다.

### 원칙 5가 새로 추가된 이유

v0.1은 §4.3 전체를 "참여자가 잘못 계산하는 것을 어떻게 막나"에 할애하고
결론적으로 "막지 않는다. 자기만 손해다"로 정리했다. 그 판단은 옳다.

문제는 **자기만 손해가 아닌 경로가 실제로 존재했다는 것**이다.
신고 단가 허용오차(§5.1)와 현금 파킹(§8.3)이 그렇다. 둘 다 v0.2에서 유인 자체를 제거했다.

## 3. 범위

### 포함

- 전략 등록 / 선언 수신 / 무결성 봉인
- 서버측 보유현황·자산 재구성 및 채점
- 리더보드 산출

### 명시적 비포함 (Non-goals)

이것은 **판단 리더보드**이지 **실계좌 성과 리더보드**가 아니다.

| 제외 항목 | 이유 |
|---|---|
| **미체결 처리** | 서버가 접수 시점 시세로 체결을 확정하므로 미체결 개념이 없다 |
| **지정가·예약주문** | "산다 했제"만 받는다. 주문 유형은 판단이 아니라 집행의 문제다 |
| **계좌 규모·잔고** | 모든 전략을 운용자산 1.0으로 정규화하므로 받을 이유가 없다 |
| **보유종목 수 제한** | 투입비중 기반이므로 10종목이든 20종목이든 자동 비교된다 |
| **브로커 연동·API 키** | 참여자 로컬을 절대 떠나지 않는다. 프로토콜은 이를 알지 못한다 |
| **레버리지·공매도** | v0.2에서도 금지 |
| **호가 스프레드(체결 오차)** | 아래 별도 설명 |

**체결 오차를 왜 빼는가 (v0.2에서 명시)**

실제 계좌에서는 사자·팔자 호가 사이의 간격 때문에 화면 가격보다 약간 불리하게 체결된다.
서버는 이를 반영하지 않고 시세 그대로 체결한다. 즉 **모든 전략이 똑같이 유리하게 계산된다.**

이는 회전율이 높은 전략에 유리하게 작용한다. 다만 거래비용(§6.4)이 회전율을 이미 벌하고 있고,
호가 간격은 종목·시각마다 달라 상수로 근사하면 오히려 새로운 왜곡이 생긴다.
따라서 **반영하지 않되, 회전율을 전략 카드에 상시 노출**해 해석 가능하게 만든다(§8.6).

### 비포함으로 하고 싶지만 반드시 포함해야 하는 3가지

단순화 욕심에 빼면 리더보드가 무의미해지는 항목들이다.

1. **기업행위 처리 (분할·배당)** — 빼면 버그다. 액면분할 한 번에 -50%가 찍히고 이는 판단과 무관하다.
2. **레버리지 차단** — 안 걸면 누군가 투입비중 10.0으로 10배 레버리지를 선언해 리더보드를 장악한다.
3. **거래비용** — KR 거래세 0.18%만으로도 월 100회전 전략과 3회전 전략 사이에 **18%p 차이**가 난다.
   단, 복잡할 필요 없이 **시장별 상수 하나**로 충분하다.

## 4. 프로토콜 명세

### 4.1 전략 등록 (전략당 1회)

```json
{
  "strategy_id":   "prism-kr-gpt5",
  "display_name":  "PRISM KR (GPT-5)",
  "author":        "dragon1086",
  "author_proof":  "github:dragon1086",
  "description":   "오닐 추세추종 + 매크로 국면 기반 스윙",
  "market":        "KRX",
  "currency":      "KRW"
}
```

등록 시 **전략 전용 인증키**가 발급된다. 이 키로만 해당 전략에 선언을 쓸 수 있다.

**전략은 삭제할 수 없다.** 등록 시점부터의 전 이력이 영구히 남는다.
이는 "여러 전략을 등록해 놓고 잘된 것만 홍보"하는 조작을 막는 장치다.

#### v0.1에서 바뀐 것 ①: `started_at` 삭제

v0.1은 참여자가 `started_at`을 직접 적어 보내게 했다. **이것은 위조 가능한 값이다.**
과거 날짜를 적어 넣으면 백테스트 기간을 실전 트랙레코드로 위장할 수 있다.

v0.2에서 트랙레코드의 시작은 **서버가 찍은 등록 시각**이며, 채점은 **첫 선언이 접수된 거래일**부터 시작한다.
참여자가 시작 시점에 개입할 방법은 없다.

#### v0.1에서 바뀐 것 ②: `markets` 배열 → `market` 단수

v0.1은 한 전략이 여러 시장을 다룰 수 있게 하고, 리더보드에서는 "시장별로 분해해 각 보드에 올린다"고 했다.
**이것은 계산이 불가능하다.**

운용자산은 하나인데 현금은 시장 간에 공유된다. KRX 종목을 팔아 만든 현금으로 나스닥 종목을 사면
그 수익은 어느 시장의 성과인가? 분해할 방법이 원리적으로 없다.
게다가 원화와 달러가 섞이면 환율 변동이 자산에 섞여 들어오는데, v0.1에는 기준통화 개념 자체가 없었다.

v0.2는 **한 전략 = 한 시장 = 한 통화**로 못 박는다.
KRX와 나스닥을 모두 운용한다면 전략을 두 개 등록한다. 각각 독립적으로 자산 1.0에서 시작한다.
계산이 명확해지고, 시장별 보드 분리(§8.5)도 자연히 성립한다.

#### v0.1에서 바뀐 것 ③: `author_proof` 추가

v0.1의 `author`는 자기신고 문자열이었다. 그러면 **한 사람이 20개 전략을 서로 다른 이름으로 등록**하고
그중 잘된 하나만 홍보하는 것을 막을 수 없다. "전략 삭제 불가"는 이 경우 무력하다.
같은 사람이 등록했다는 사실을 아무도 알 수 없기 때문이다.

더 교묘한 형태도 있다. **정반대 판단을 하는 전략 두 개를 등록하면 하나는 반드시 이긴다.**
이는 금융 사기에서 오래된 수법이다.

v0.2는 GitHub 계정 인증을 요구하고, **같은 계정의 전 전략 목록을 각 전략 카드에 강제 노출**한다.
등록 자체를 제한하지는 않는다. 여러 전략을 돌리는 건 정당한 실험이다.
다만 **감출 수는 없게** 만든다.

### 4.2 선언 — 참여자가 보내는 유일한 메시지

```json
{
  "protocol":    "otd/0.2",
  "strategy_id": "prism-kr-gpt5",
  "seq":         42,
  "market":      "KRX",
  "symbol":      "005930",
  "action":      "buy",
  "weight":      0.10,
  "reason":      "20일선 눌림목, 거래량 회복",
  "meta":        { "final_score": 0.83 }
}
```

| 필드 | 필수 | 설명 |
|---|:---:|---|
| `protocol` | ✅ | 프로토콜 버전 |
| `strategy_id` | ✅ | 등록된 전략 ID |
| `seq` | ✅ | 전략별 일련번호(단조증가). 누락·중복 감지용 |
| `market` | ✅ | 등록된 시장과 일치해야 함 |
| `symbol` | ✅ | 종목 코드 |
| `action` | ✅ | `buy` \| `sell` \| `hold` |
| `weight` | buy만 | 투입비중. 운용자산 대비 (0 < w ≤ 1) |
| `sell_ratio` | sell만 | 매도비율. 보유 수량 대비 (0 < r ≤ 1, `1.0` = 전량) |
| `reason` | ⬜ | 자유 텍스트, 최대 500자. 채점에 영향 없음 |
| `meta` | ⬜ | 시스템별 자유 필드. 최대 4KB |

**분할매수** = `buy` 여러 번. **분할매도** = `sell_ratio: 0.3` 세 번.
프로토콜에 분할 개념이 따로 없다.

#### v0.1에서 바뀐 것 ④: `price` 필드 삭제 — 가장 중요한 변경

v0.1은 참여자가 신고한 단가가 서버 실측가의 ±1% 안이면 **그 신고가를 체결가로 인정**하고,
벗어나면 조용히 실측가로 대체했다. **벗어난 데 대한 벌칙은 없었다.**

이 구조에서 최적 전략은 자명하다.

> 매수할 때는 항상 실측가보다 0.9% **낮게** 신고한다.
> 허용오차 안에 들면 그 가격에 산 것으로 인정받고, 벗어나면 실측가로 원복될 뿐 손해가 없다.

매도는 반대로 하면 된다. **왕복 1.8%를 공짜로 얻는 비대칭 옵션**이었다.
v0.1 스스로 §3에서 *"거래세 0.18%만으로 18%p 차이가 나 순위가 뒤집힌다"*고 강조했는데,
이 구멍은 그것의 **10배**다. 그럼에도 v0.1 §7의 무결성 표는
"저점 매수가를 사후에 적어냄 → 잔여 리스크 **없음**"이라고 적고 있었다.

**v0.2의 해결: 신고 단가를 아예 받지 않는다.** 체결가는 언제나 서버 실측가다.
허용오차라는 개념 자체가 사라지므로 그 안에서 이득을 볼 방법도 사라진다(원칙 5).

부수 효과로 **개념적 모순 하나가 함께 해소된다.** v0.1은 §1에서 "판단을 **사전에** 선언받는다"고 선언해 놓고,
§4.2의 `price`를 "**신고 체결가**"라고 정의했다. 체결가가 있다는 건 이미 체결됐다는 뜻이므로 사후 보고다.
사전 선언과 사후 보고가 한 문서 안에 공존했던 것이다.
단가를 없애면 **선언은 순수하게 사전 통보**가 되고, 이것이 이 프로토콜의 원래 취지에 정확히 부합한다.

#### v0.1에서 바뀐 것 ⑤: `ts`(참여자 시각) 삭제

v0.1은 참여자 시각을 받되 "참고용일 뿐 채점에 쓰이지 않는다"고 명시했다.
**채점에 안 쓰는 값을 받으면 참여자는 그것이 의미 있다고 오해한다.**
받지 않는 편이 정직하다. 지연 진단이 필요하면 참여자 로컬 로그로 충분하다.

#### v0.1에서 바뀐 것 ⑥: `reduce` → `sell_ratio`

`reduce`는 동사여서 값이 무엇의 비율인지 이름에서 드러나지 않았다.
v0.1이 §4.3에 오류 사례를 5줄이나 적어야 했던 것 자체가 이름이 나빴다는 증거다.
아직 배포 전이므로 지금이 바꿀 수 있는 유일한 시점이다.

### 4.3 `hold` — 유지 선언 (v0.2 신규)

```json
{ "protocol":"otd/0.2", "strategy_id":"prism-kr-gpt5", "seq":43,
  "market":"KRX", "action":"hold", "reason":"관망" }
```

**"오늘은 매매하지 않기로 판단했다"를 명시적으로 기록하는 선언이다.** 보유 현황을 바꾸지 않는다.

#### 왜 필요한가 — v0.1에서 저회전 전략이 전멸했다

v0.1은 참가 요건으로 **제출 커버리지 70%** 를 요구했다.
커버리지 = 선언이 1건 이상 있던 거래일 ÷ 총 거래일. 목적은 "지는 날엔 안 보내기" 조작 차단이었다.

그런데 **좋은 스윙 전략은 매매를 자주 하지 않는다.**
3개월에 8번 매매하는 전략의 커버리지는 8/60 = **13%**. 참가 요건 탈락이다.

더 나쁜 것은 v0.1 스스로 §9.5에서 "회전율"을 과매매 탐지 지표로 병기한다는 점이다.
**커버리지 70% 요건은 정확히 그 반대로 고회전을 강제한다.** 두 지표가 서로 싸우고 있었다.

근본 원인은 프로토콜에 **"매매 안 함"을 표현할 방법이 없다**는 것이다.
`buy`와 `sell`밖에 없으니 "판단해서 쉬었다"와 "시스템이 죽어서 못 보냈다"가 구분되지 않는다.

`hold`를 도입하면 커버리지는 **"성실하게 보고했는가"** 만 재는 정직한 지표가 되고,
매매 빈도와 완전히 분리된다. 매일 `hold`만 보내는 전략도 커버리지 100%를 받는다.
그래도 무방하다 — 커버리지는 성실성 지표이지 실력 지표가 아니기 때문이다.

### 4.4 참여자가 계산할 값은 딱 2개다

> **이 절이 프로토콜에서 가장 자주 깨지는 지점이다.**
> 참여자마다 계산 기준이 다르면 리더보드 전체가 무의미해진다.

| 값 | 언제 | 공식 |
|---|---|---|
| `weight` (투입비중) | 매수할 때 | `이번에 넣은 돈 ÷ 운용자산` |
| `sell_ratio` (매도비율) | 매도할 때 | `이번에 판 수량 ÷ 팔기 직전 보유 수량` |

**둘 다 나눗셈 한 번이다.** 평단·손익·수익률을 계산할 필요가 전혀 없다.

#### 절대 계산하면 안 되는 값

수익률 · 실현손익 · 평균단가 · 최대낙폭 · 승률 — **전부 서버가 계산한다.**
보내더라도 채점에 사용되지 않는다 (원칙 1).

#### 운용자산의 정의 — 가장 중요

> **운용자산 = 이 전략이 굴리는 현금 + 이 전략이 들고 있는 모든 종목의 현재 평가액**

두 가지를 반드시 지켜야 한다.

1. **현금만 세면 안 된다.** 들고 있는 주식의 평가액을 포함한 총액이 분모다.
2. **이 전략 몫만 센다.** 같은 계좌에 다른 목적의 돈이 섞여 있으면 빼야 한다.
   계좌 1억 중 5천만원만 이 전략이 굴린다면 운용자산은 5천만원이다.

#### 흔한 오류

| ❌ 잘못된 계산 | 무슨 일이 벌어지나 |
|---|---|
| `투입금액 ÷ 예수금` | 분모가 작아 비중이 부풀려짐. 주식을 많이 들고 있을수록 심해짐 |
| `투입금액` (절대금액) | 스케일 붕괴. 5,000,000 같은 값이 들어와 즉시 거부 |
| `투입금액 ÷ 계좌 전체` (남의 돈 포함) | 비중이 축소됨. 실제보다 소극적인 전략으로 기록됨 |
| `매도금액 ÷ 총자산` | 완전히 다른 의미. 거의 항상 지나치게 작은 값 |
| `매도수량 ÷ 최초 매수수량` | 이미 나눠 팔았다면 틀림. **분모는 언제나 "팔기 직전" 수량** |

#### 부분 체결은 어떻게 하나 (v0.2에서 명시)

주문 하나가 여러 가격에 나눠 체결되는 경우, **주문 단위로 한 번만 선언한다.**
체결이 끝날 때까지 기다릴 필요는 없다 — 어차피 서버는 접수 시점 시세로 체결가를 정하므로
실제 체결 결과를 기다려도 얻는 것이 없다.

권장 순서는 **주문을 넣은 직후 즉시 선언**이다. 체결 확인 후로 미루면 그만큼 시세가 움직여
서버 장부와 실계좌의 어긋남만 커진다.

#### 부정확하게 보내는 참여자는 어떻게 막나

**막지 않는다. 막을 수 없고, 막을 필요도 없다.**

v0.2에서 조작으로 이득을 볼 수 있는 경로는 모두 제거되었다(원칙 5).
부정확하게 보고하면 **자기 전략의 기록만 부정확해진다.**

대신 **틀렸다는 사실을 즉시 알 수 있게** 만든다. 아래 검산 응답이 그 장치다.

#### 서버 검산 결과

장부 재구성이 끝나면 각 선언에 결과가 채워진다.
`GET /portfolio`로 조회해 자기 계좌와 대조할 수 있다.

```json
{ "status": "accepted",
  "fill_price": 20000,
  "position_after": { "symbol": "005930", "avg_cost": 10000, "weight": 0.0909 },
  "total_assets_after": 1.0998,
  "realized_pnl": 0.0498 }
```

**계산을 참여자가 하지 않고 서버가 해서 돌려준다.** 이것이 기준 불일치를 없애는 핵심 장치다.

> 이 응답은 **비동기**다. 접수 직후에는 `pending`이며, 처리기가 시세를 찍고 장부를 재구성한 뒤 채워진다.
> 다만 **거부와 축소만은 즉시 동기 응답으로 알려준다** — 이유는 §6.3에 있다.

#### 어긋남은 누적되지 않는다

매도비율을 부정확하게 보내면 서버 장부의 보유 수량이 실계좌와 벌어진다.
그러나 이 괴리는 **해당 종목을 전량 청산(`sell_ratio: 1.0`)하는 순간 사라진다.**
다음 매수는 투입비중으로 새로 시작하므로 수량 오차가 이월되지 않는다.

즉 어긋남은 **종목 단위로 격리**되며 전략 전체로 번지지 않는다.

> **단, 이 성질은 매수가 거부될 때는 성립하지 않는다.**
> v0.1의 심각한 결함이었으며 §6.3에서 별도로 다룬다.

#### 서버측 이상 감지

서버는 다음을 감지해 참여자에게 경고한다. **순위에는 반영하지 않는다** — 처벌이 아니라 교정이 목적이다.

| 신호 | 추정 원인 |
|---|---|
| 투자비중이 지속적으로 0.1 미만 | 분모를 계좌 전체로 잡았거나 절대금액 혼동 |
| 축소 수락 비율 20% 초과 | 분모를 예수금으로 잡음 (§6.3) |
| `sell_ratio > 1.0` 시도 | 분모를 최초 매수 수량으로 잡음 |
| 매수만 있고 매도가 없음 | 매도 선언 발행 누락 |
| 30일 이상 선언 없음 | 시스템 중단. 전략을 **휴면**으로 표시 |

마지막 항목은 v0.2 신규다. 등록만 하고 방치된 전략이 예선에 무한정 쌓이는 것을 막는다.

## 5. 체결가 결정

### 5.1 원칙 — 실측가 강제

> 체결가는 **언제나 서버가 접수 직후 직접 찍은 시세**다. 참여자는 개입할 수 없다.

v0.1의 허용오차 구조와 그것이 왜 제거되었는지는 §4.2에 설명되어 있다.

### 5.2 절차

```
① 접수 즉시 접수시각 봉인 (DB가 생성, 참여자 접근 불가)
② 처리기가 해당 종목 현재가를 실측 → 원장에 기록 (이후 수정 불가)
③ 체결 가능 여부 판정 (§5.5)
④ 확정단가 결정 → 이후 수정 불가
```

**과거 분봉 이력이 필요 없다.** 사후에 "그 시각 가격대"를 조회하는 대신 **접수 시점에 서버가 직접 찍는다.**
PRISM의 `cores/kis_market_snapshot.py: fetch_kis_intraday_snapshot`이 이 역할을 그대로 수행할 수 있다.

### 5.3 처리 지연의 상한 (v0.2 신규)

v0.1은 처리기의 지연을 "수 초이며 무해하다"고만 적었다. 근거는
*"조작자가 노리는 것은 접수시각 이전 가격인데 그것은 원천 불가능하다"* 였다. 조작 방어로서는 맞다.

그러나 **공정성 문제가 남는다.** 큐가 밀리면 수 초가 수 분이 될 수 있고,
그 사이 시세는 움직인다. 이는 조작이 아니라 **무작위 잡음**이며, 회전율이 높은 전략일수록 누적된다.

v0.2는 다음을 명시한다.

- 목표 지연 **3초 이내**, 상한 **60초**
- 60초를 초과하면 확정단가에 `delayed: true` 표시. 채점에는 그대로 쓰되 **참여자에게 통보**
- 지연 분포(중앙값·p95)를 리더보드에 **공개 지표로 상시 노출**

운영 품질을 감추지 않는 것이 신뢰의 조건이다.

### 5.4 장 마감 후 · 휴장일 선언 (v0.1에서 수정)

v0.1은 이 경우 **"직전 정규장 종가"** 를 체결가로 썼다.
**이것은 현실에서 존재할 수 없는 체결이다.**

밤 10시에 "삼성전자 매수"를 선언한 참여자가 그날 종가에 살 방법은 없다.
장이 닫혀 있기 때문이다. 종가를 인정하면 **하루치 정보를 이미 알고 있는 상태에서
그 정보가 반영되지 않은 가격으로 사는 것**이 된다. 예컨대 장 마감 후 호재 공시가 뜬 종목을
저녁에 선언하면 공시 이전 가격에 살 수 있다. 명백한 이득이며, 이는 판단 실력이 아니다.

v0.2는 **다음 거래일 시가**로 체결한다.

- 장중(정규장) 접수 → 접수 시점 실측가
- 그 외 모든 시간(장 마감 후·개장 전·휴장일) → **다음 정규장 시가**
- 확정 전까지 상태는 `queued`이며, 시가가 나온 뒤 확정단가가 채워진다

이것이 현실에서 실제로 가능한 유일한 체결이다.

### 5.5 체결 불가 판정 (v0.2 신규)

v0.1에는 이 개념 자체가 없었다. **살 수 없는 상황인데도 샀다고 인정하고 있었다.**

| 상황 | 판정 |
|---|---|
| 상한가이며 매도 잔량 0 | 매수 **거부**. 실제로 살 수 없다 |
| 하한가이며 매수 잔량 0 | 매도 **거부**. 실제로 팔 수 없다 |
| 거래정지 | 매수·매도 모두 **거부**. 평가액은 정지 직전 가격으로 고정 |
| 정리매매 기간 | 매수 **거부**, 매도는 허용 |

상한가에 사겠다는 선언이 무조건 체결되면, 급등주를 매일 상한가에 담는 전략이
현실에서는 한 주도 못 사면서 리더보드에서는 최고 수익을 낸다. 반드시 막아야 한다.

판정에는 호가 정보가 필요하다. KIS 스냅샷 API가 상하한가와 잔량을 함께 제공하므로 추가 비용은 없다.

### 5.6 동시호가 구간 (v0.2 신규)

KRX의 장 시작 동시호가(08:30–09:00)와 장 마감 동시호가(15:20–15:30) 구간에는
**"현재가"가 존재하지 않는다.** 화면에 뜨는 것은 예상체결가이며 실제 체결가가 아니다.

이 구간에 접수된 선언은 **해당 동시호가가 확정된 실제 체결가**로 처리한다.
즉 시가 동시호가 → 그날 시가, 종가 동시호가 → 그날 종가.
확정 전까지 상태는 `queued`다.

### 5.7 시세 소스 장애 (v0.2 신규)

v0.1은 시세 소스를 단일 전제로 삼고 장애를 다루지 않았다.
실측가는 **그 순간에만 존재하는 값**이므로, 놓치면 사후 복구가 불가능하다는 점에서 특히 위험하다.

- 1차 소스 실패 시 **2차 소스로 폴백**하고 원장에 사용 소스를 함께 기록
- 모든 소스 실패 시 상태를 `queued`로 두고 **최대 60분 재시도**
- 그래도 실패하면 **다음 정규장 시가**로 확정 (§5.4와 동일 규칙)
- 어느 경우에도 **선언 자체는 원장에 남는다.** 시세를 못 구한 것은 서버 책임이므로 참여자를 벌하지 않는다

## 6. 채점 규칙

### 6.1 운용자산 정규화

모든 전략은 **운용자산 1.0**에서 시작한다. 실계좌 규모를 받지 않는다.

- `weight: 0.1` = "그 시점 운용자산의 10%를 투입"
- 투자하지 않은 현금은 수익률 0
- 보유 종목 수와 무관하게 자동 비교 가능
- 자금 규모가 노출되지 않는다

### 6.2 보유 현황 관리

- 종목 단위 **평균단가** 방식. 매수마다 평단 갱신.
- `sell_ratio`는 **현 보유 수량 대비 비율**이다.
- 동일 종목 추가 매수 시 투입 비중은 누적된다.

**매도비율이 수량 기준인 이유 — 규모 불변성**

`sell_ratio: 0.5`는 "보유 수량의 50%"이며, 같은 종목이므로 "보유 평가액의 50%"와 동일하다.
"원래 투입 비중의 50%"라는 해석은 **명시적으로 배제한다** (그것은 다른 값이다).

비율을 받는 이유는 규모 불변성 때문이다. 실계좌가 5천만원이든 5억이든,
서버 장부가 1.0이든, "보유 수량의 50%"는 양쪽에서 정확히 같은 의미다.

**워크드 예시 — 2배 상승 후 절반 매도**

| 단계 | 현금 | 평가액 | 원가 | 운용자산 | 종목 비중 |
|---|---|---|---|---|---|
| 시작 | 1.0 | — | — | 1.0 | — |
| ① `buy weight 0.1` @10,000 | 0.9 | 0.1 | 0.1 | 1.0 | 10.00% |
| ② 주가 2배 → 20,000 | 0.9 | 0.2 | 0.1 | **1.1** | **18.18%** |
| ③ `sell_ratio 0.5` @20,000 | 0.9998 | 0.1 | 0.05 | 1.0998 | 9.09% |

②에서 종목 비중이 **0.2가 아니라 18.18%** 인 점에 주의한다. 분모인 운용자산도 함께 커졌기 때문이다.

③ 계산: 수량 절반 매도 → 매도대금 0.1 → 거래비용 0.20% 차감 → 실수령 0.0998.
평단은 10,000원 그대로이므로 잔여 원가는 0.05.
**실현손익 = 0.0998 − 0.05 = +0.0498.**

**목표 비중으로 되돌리려면**

위 예시에서 18.18%를 다시 10%로 줄이려면 `sell_ratio: 0.45`를 보내면 된다.
이 비율을 계산하려면 서버 장부를 알아야 하므로 **`GET /portfolio`** 를 제공한다.

`target_weight` 필드를 두어 서버가 대신 계산하게 하는 방법도 있으나 채택하지 않는다.
서버가 계산한 매도 비율과 참여자가 실제로 판 비율이 어긋나 선언의 충실도가 깨지기 때문이다.

**실계좌와 서버 장부의 어긋남**

거부, 축소 수락, 체결가 차이, 수동 개입 등으로 서버 장부와 실계좌는 시간이 지나며 벌어질 수 있다.
**채점의 기준은 언제나 서버 장부다.** 이는 판단 리더보드로서 의도된 동작이며,
실계좌 성과를 재현하려는 것이 아니다.

### 6.3 거부와 축소 수락

#### v0.1의 심각한 결함: 매수 거부가 전략을 영구히 망가뜨렸다

v0.1은 현금이 부족하면 매수를 **거부**했다. 그리고 §4.3에서
*"어긋남은 전량 청산으로 사라지므로 종목 단위로 격리된다"* 고 안심시켰다.

**매도비율에 대해서는 맞다. 그러나 매수 거부에는 전혀 적용되지 않는다.**

시나리오를 보자.

1. 서버 장부의 운용자산이 실계좌보다 낮아 현금 제약에 걸려 매수가 거부된다
2. 참여자는 실계좌에서 이미 샀다. **그런데 서버 장부에는 그 종목이 존재하지 않는다**
3. 이후 그 종목에 대한 모든 매도는 "보유하지 않은 종목에 매도"로 **연쇄 거부**된다
4. 종목 단위 격리가 아니라 **영구 분기**다

게다가 v0.1의 응답은 비동기였으므로 참여자는 거부 사실을 몇 초 뒤에나 알 수 있었다.
그때는 이미 실계좌 주문이 나간 뒤다.

#### v0.2의 해결: 축소 수락 (clamp)

현금이 부족하면 **거부하지 않고, 가능한 최대 비중으로 줄여서 받아들인다.**

```
요청 투입비중 = 0.30, 가용 현금 = 0.18, 운용자산 = 1.0
→ status: "clamped", 실제 반영 비중 = 0.18
```

- 가용 현금이 0이면 그때만 `rejected`
- 축소된 선언도 원장에 요청값과 반영값이 **모두** 기록된다
- **축소·거부는 접수 즉시 동기 응답으로 반환한다.** 이 판정에는 시세가 필요 없으므로 즉시 가능하다

이렇게 하면 종목이 서버 장부에서 통째로 사라지는 일이 없어지고, 이후 매도가 연쇄 거부되지 않는다.
비중 차이는 남지만 그것은 §4.4의 어긋남 소멸 성질로 흡수된다.

#### 거부 규칙 (축소 불가능한 경우만)

거부된 선언도 원장에는 남으며 삭제되지 않는다. 채점에만 반영되지 않는다.

| 조건 | 사유 |
|---|---|
| 가용 현금이 0 | 축소할 여지 없음 |
| 보유하지 않은 종목에 매도 | 공매도 금지 |
| 투입비중 또는 매도비율이 0 이하 | 유효 범위 위반 |
| 일련번호가 기존 값 이하 | 재전송·역순 |
| 등록되지 않은 종목 / 전략 시장과 불일치 | 검증 불가 |
| 체결 불가 상황 (§5.5) | 현실에서 불가능한 체결 |

#### 레버리지 차단의 정확한 정의

v0.1은 문서 곳곳에서 `Σweight ≤ 1.0`이라 쓰다가 §6.3에서만 정확한 정의로 정정했다.
**두 표현이 공존해 구현자가 잘못된 쪽을 집을 위험이 있었다.** v0.2는 하나로 통일한다.

> **가용 현금 ≥ 투입비중 × 운용자산** 이면 승인. 부족하면 그만큼 축소.

"보유 종목의 현재 평가비중 합이 1.0 이하"로 해석하면 **안 된다.**
보유 종목이 전부 오르면 평가비중 합은 자연히 1.0을 넘는데, 그때 신규 매수를 막는 것은 잘못이다.
현금 기준 정의는 레버리지를 자동으로 차단하면서 수익 중인 포트폴리오의 재투자를 정상 허용한다.

### 6.4 거래비용

**시장별 상수 하나.** 매도할 때만 뗀다.

| 시장 | 매도 시 차감 |
|---|---|
| `KRX` | 0.20% (거래세 0.18% + 수수료 근사) |
| `NASDAQ` / `NYSE` | 0.01% |

참여자가 이 값을 지정할 수 없다.

### 6.5 기업행위 — 이벤트 방식으로 전면 재설계

#### v0.1의 원칙 충돌

v0.1 §6.5는 *"분할·병합·배당은 **수정주가 기준으로** 보유 수량·평단을 조정한다"* 고 했다.

**수정주가는 과거 가격을 소급해서 고쳐 쓰는 방식이다.**
이는 v0.1의 다른 두 원칙과 정면으로 충돌한다.

- 원칙 3(사건을 받아 재구성)과 충돌 — 소급 조정은 사건이 아니라 과거 데이터 수정이다
- append-only 무결성과 충돌 — 이미 확정된 과거 자산 추이가 뒤늦게 바뀐다

액면분할이 일어난 순간 **지난 3개월의 일별 자산 추이가 전부 다시 계산되고,
그에 따라 이미 발표된 순위가 소급해서 바뀐다.** 이는 원장 기반 시스템에서 있을 수 없는 일이다.

#### v0.2의 해결: 기업행위도 원장 이벤트로 만든다

서버가 발행하는 시스템 이벤트로 처리한다. **과거를 건드리지 않는다.**

```json
{ "type": "split", "market": "KRX", "symbol": "005930",
  "ratio": 50, "effective_date": "2026-09-01" }
```

| 유형 | 처리 |
|---|---|
| **액면분할·병합** | 그 시점부터 보유 수량 × 비율, 평단 ÷ 비율. 자산 변동 없음 |
| **현금배당** | 배당락일에 `현금 += 보유수량 × 주당배당금 × (1 − 배당세)` |
| **주식배당·무상증자** | 보유 수량 증가, 평단 희석 |
| **거래정지** | 정지 직전 가격으로 평가 고정. 매매 선언은 거부(§5.5) |
| **상장폐지** | 정리매매 최종가로 강제 청산. 정리매매가 없으면 0원 처리 |

배당세는 시장별 상수로 둔다 (KRX 15.4%, US 15%).

이 방식의 이점은 결정적이다. **과거 자산 추이가 절대 바뀌지 않는다.**
분할은 자산에 영향이 없고(수량과 단가가 정확히 상쇄), 배당은 발생한 날에 현금이 늘 뿐이다.

#### 누가 언제 감지하나 (v0.1에 없던 부분)

v0.1은 §3에서 *"빼면 버그다"* 라고 강조해 놓고 본문은 세 줄이었다.
**감지 주체·데이터 소스·적용 시점이 전부 비어 있었다.** 실무에서 이 항목이 전체 공수의 절반을 먹는다.

- **매 거래일 장 시작 전**, 서버가 전 전략의 보유 종목 전체를 훑어 기업행위를 조회한다
- 선언이 없는 종목도 반드시 포함한다. 기업행위는 참여자 행동과 무관하게 발생한다
- 데이터 소스는 KRX 공시 / KIS API. 조회 실패 시 **해당 종목의 채점을 보류**하고 경보
- 감지된 기업행위는 원장에 시스템 이벤트로 추가되며, 참여자에게 통보된다

**배당 예시 (앞의 워크드 예시 이어서)**

②단계에서 주당 500원 배당이 발생했다고 하자. 보유 수량은 정규화 단위로 1e-5.

```
배당금       = 1e-5 × 500 = 0.005
세후 수령    = 0.005 × (1 − 0.154) = 0.00423
현금         = 0.9 → 0.90423
```

배당락으로 주가가 500원 떨어지므로 평가액은 0.005 감소한다.
결과적으로 운용자산은 세금만큼(0.00077) 줄어든다. **이것이 현실과 정확히 일치하는 처리다.**

### 6.6 미제출일 처리

특정 거래일에 선언이 없으면 **그날은 직전 보유가 유지된 것**으로 본다.

다만 `hold` 선언이 도입되었으므로(§4.3) "판단해서 쉰 날"과 "아무것도 안 보낸 날"이 이제 구분된다.
**제출 커버리지**는 후자만 벌한다.

> 커버리지 = (선언이 1건 이상 있던 거래일) ÷ (첫 선언 이후 총 거래일)

## 7. 무결성 모델

### 7.1 원장과 계산장부의 분리 (v0.2 핵심 구조 변경)

#### v0.1의 구멍

v0.1은 `declarations` 테이블 하나에 참여자 제출값과 서버 계산값을 함께 담고,
`BEFORE INSERT` 트리거에서 해시체인을 계산했다.

**문제는 그 시점에 확정단가·상태·자산이 전부 비어 있다는 것이다.**
이 값들은 처리기가 수 초 뒤에 UPDATE로 채운다.

즉 **채점을 실제로 좌우하는 값들이 해시 봉인 바깥에 있었다.**
v0.1 §7의 무결성 표는 "과거 선언 수정·삭제 → 잔여 리스크 없음"이라 적었지만,
확정단가는 얼마든지 사후에 바꿀 수 있었다.

여기에 두 번째 모순이 겹친다. v0.1 §8.3은
*"UPDATE·DELETE는 **누구도** 할 수 없다"* 를 요구사항으로 못 박았는데,
처리기는 반드시 UPDATE를 해야 한다. 실제 설계는 "처리기만 UPDATE 가능"이었고,
그 순간 무결성은 전적으로 관리자 키 하나에 의존하게 된다.

#### v0.2의 구조

**세 종류의 원장(고칠 수 없음)과, 그로부터 만들어지는 계산장부(언제든 재생성)로 나눈다.**

```
[원장 — INSERT만 가능, 해시체인으로 봉인]
  declarations       참여자가 보낸 선언 원문 + 접수시각 + 즉시 판정(거부/축소)
  price_observations 서버가 그 순간 찍은 시세. 사후 재조회 불가하므로 원장이다
  system_events      기업행위·상장폐지 등 서버 발행 이벤트

           ↓  (전부 다시 읽어서 계산)

[계산장부 — 언제든 지우고 다시 만들 수 있음]
  fills          확정단가와 체결 결과
  positions      보유 현황
  daily_assets   일별 운용자산 추이
  scores         지표와 순위
```

이 분리가 세 가지를 동시에 해결한다.

1. **봉인이 완전해진다.** 채점의 입력이 되는 모든 사실(선언·시세·기업행위)이 원장에 있고 전부 해시로 묶인다.
   확정단가는 이제 봉인 대상이 아니라 **원장으로부터 누구나 재계산할 수 있는 값**이다.
2. **UPDATE 금지가 진짜로 성립한다.** 원장에는 UPDATE가 아예 필요 없다. 처리기도 INSERT만 한다.
3. **재계산이 가능해진다.** 채점 버그가 발견되면 계산장부만 지우고 다시 만들면 된다.
   원장은 손대지 않으므로 무결성이 유지된다.

**시세를 원장에 넣는 것이 특히 중요하다.** 시세는 그 순간에만 존재하며 사후에 다시 조회할 수 없다.
계산장부에 두면 재계산할 때 복원할 방법이 없다.

### 7.2 조작 경로와 대응

| 조작 시나리오 | 대응 | 잔여 위험 |
|---|---|---|
| 수익률을 부풀려 신고 | **수익률을 받지 않는다.** 서버가 계산 | 없음 |
| 유리한 단가를 적어냄 | **단가 필드 자체를 삭제** (§4.2) | 없음 |
| 장 마감 후 정보로 종가 매수 | 다음 거래일 시가 체결 (§5.4) | 없음 |
| 상한가 종목을 담아 수익률 조작 | 체결 불가 판정 (§5.5) | 없음 |
| 여러 전략 등록 후 잘된 것만 홍보 | 계정 인증 + **같은 계정 전 전략 강제 노출** (§4.1) | 낮음 |
| 정반대 전략 2개 등록 | 위와 동일. 둘 다 보인다 | 낮음 |
| 지는 날 선언 생략 | 커버리지 병기 + `hold` 도입으로 지표 정직화 (§4.3) | 낮음 |

| 과거 선언을 수정·삭제 | 원장 INSERT 전용 + 해시체인 (§7.1) | 없음 |
| 레버리지로 순위 조작 | 현금 기준 제약 (§6.3) | 없음 |
| 인증키 유출로 제3자 오염 | 키 교체 + 무효화 이벤트 (§7.3) | 낮음 |
| **운영자가 직접 DB 수정** | 해시체인. 완전 방지는 외부 앵커링 필요 | ⚠️ 아래 |

### 7.3 인증키 유출 대응 (v0.2 신규)

v0.1은 이 시나리오를 다루지 않았다. **삭제 불가 원칙과 정면으로 충돌하는 상황이다.**
키가 유출되면 제3자가 아무 선언이나 밀어 넣을 수 있고, 그것을 지울 방법이 없어
전략이 영구히 오염된다.

v0.2의 처리는 다음과 같다.

- 참여자는 언제든 **키를 교체**할 수 있다
- 유출을 신고하면 **무효화 이벤트**를 원장에 추가한다. 과거를 지우는 것이 아니라
  "이 구간은 무효" 를 **덧붙이는** 방식이므로 원장 불변성이 유지된다
- 무효화 구간은 채점에서 제외되며, **그 사실이 전략 카드에 공개 표시된다**
- 남용 방지를 위해 무효화는 **전략당 1회**로 제한하고 운영자 승인을 거친다

"손해 본 구간을 유출이라 주장하며 지우는" 남용을 완전히는 막을 수 없다.
따라서 무효화 사실 자체를 감추지 않는 것이 유일한 방어다.

### 7.4 "고칠 수 없음"과 "공개함"은 다른 문제다 (v0.2 신규)

v0.1은 이 둘을 하나로 묶었다. 원장은 수정 불가이고, 동시에 전 이력이 공개였다.
`reason` 필드는 길이 제한 없는 자유 텍스트였다.

**여기서 법적 문제가 발생한다.** 참여자가 실수로 개인정보를 `reason`에 적으면
그것은 영구히 공개되고 삭제할 방법이 없다. 개인정보 삭제 요구권과 정면으로 충돌한다.
욕설·스팸·타인 정보도 마찬가지다.

v0.2는 **불변성과 공개 범위를 분리**한다.

- 원장의 원문은 **영원히 보존**된다 (무결성 유지)
- 그러나 **공개 여부는 별도의 정책**이며, 비공개 전환 역시 **덧붙이는 이벤트**로 처리한다
- `reason`은 **최대 500자**, `meta`는 **최대 4KB**로 제한
- 리더보드 렌더링 시 HTML을 무력화한다 (스크립트 삽입 차단)
- 비공개 처리된 항목은 "가려짐"으로 표시된다. **가려졌다는 사실 자체는 감추지 않는다**

이렇게 하면 해시체인은 원문 기준으로 계속 검증 가능하면서, 공개 화면에서는 문제 내용을 내릴 수 있다.

### 7.5 요청 한도 (v0.2 신규)

v0.1은 지울 수 없는 테이블에 **무제한 쓰기**를 열어 두었다.
초당 수천 건을 밀어 넣으면 무료 티어 용량(500MB)이 즉시 소진되고, **지울 수도 없다.**

- 전략당 **분당 30건**, **일 500건**
- 초과분은 429로 거절하며 **원장에 기록하지 않는다** (한도 초과는 사실 기록이 아니라 잡음이다)
- `meta` 4KB, `reason` 500자 제한 (§7.4)

### 7.6 운영자 신뢰 문제

해시체인은 **참여자의 조작**은 막지만 **DB 운영자의 조작**은 원리적으로 막지 못한다.
공개 리더보드로서의 신뢰가 필요해지면 **외부 앵커링**을 추가한다.

> 매일 장 마감 후 그날의 전체 원장에 대한 **머클 루트**를 공개 저장소(GitHub 커밋)에 기록.
> 이후 누구든 로컬에서 재계산해 대조할 수 있다.

v0.2 구조에서는 이 검증이 v0.1보다 **훨씬 강력하다.**
원장(선언 + 시세 + 기업행위)만 공개하면 **제3자가 채점 전체를 독립적으로 재현할 수 있기 때문이다.**
운영자가 순위를 조작하면 즉시 드러난다. 이것이 원장/계산장부 분리의 가장 큰 부수 효과다.

Phase 0에서는 생략하고, 참여자가 늘어나는 시점에 도입한다.

## 8. 리더보드 순위 설계

### 8.1 해결해야 할 문제

| # | 문제 | 방치하면 |
|---|---|---|
| 1 | **선착순 우위** | 먼저 시작한 전략이 복리 기간만으로 영구히 1등 |
| 2 | **위험 무시** | 레버리지·집중투자로 변동성을 키운 전략이 누적수익률 1등 |
| 3 | **운 vs 실력** | 2개월 돌린 고수익 전략이 3년 검증된 전략을 이김 |
| 4 | **표본 부족** | 거래 5건으로 승률 100% 달성 |
| 5 | **시장 베타** | 강세장에 시작한 전략이 자동으로 유리 |
| 6 | **생존편향** | 죽은 전략이 사라지면 전체 평균이 부풀려짐 |
| 7 | **위험 회피 조작** ⭐ | **현금만 들고 있으면 위험지표가 무한대가 됨** |

7번은 v0.2에서 새로 발견된 문제이며, **단일 항목으로는 가장 치명적이다.**

### 8.2 참고한 업계 관행

- 실전 트레이딩 대회는 **4축 동등가중** 평가를 쓴다 — 수익 / 위험관리 / 트랙레코드 일관성 / 검증가능성
- 최소 트랙레코드 벤치마크는 대체로 **3개월 이상 + 50거래 이상**
- 학술 정석은 **Deflated Sharpe Ratio** (Bailey & López de Prado, 2014)

### 8.3 v0.1의 치명적 구멍 — 현금 파킹으로 1등 하기

v0.1의 메인 순위는 **하락위험 대비 수익 지수(Sortino)** 였다.

$$\text{Sortino} = \frac{R_p - R_f}{\sigma_{down}}$$

분모는 **하락 방향 변동성**이다. 여기서 문제가 발생한다.

> **주식을 거의 사지 않으면 자산이 거의 움직이지 않는다.**
> 자산이 움직이지 않으면 하락 변동성이 0에 수렴한다.
> **0으로 나누면 무한대다.**

구체적 공략법은 이렇다.

1. 운용자산의 99%를 현금으로 둔다
2. 투입비중 0.01짜리 매매를 매일 한 건씩 한다
3. 자산은 하루에 0.01% 수준으로만 움직인다 → 하락편차가 극도로 작아진다
4. 아주 약간의 수익만 나도 **지수가 폭발한다**
5. 매일 매매하므로 **커버리지 70%도 충족**한다
6. 소액 매매를 반복하므로 **거래 20건 요건도 충족**한다

**v0.1의 참가 요건 세 개를 전부 통과하면서 1등을 차지할 수 있다.**
더 나쁜 것은 커버리지 요건이 이 조작을 **오히려 장려**한다는 점이다.
매일 소액 매매를 하도록 유도하기 때문이다.

v0.1은 레버리지(과도한 위험)는 막았지만 **과소 위험은 전혀 다루지 않았다.**
실제 헤지펀드 대회에서 흔히 나타나는 공략이다.

#### v0.2의 3중 방어

**① 참가 요건에 투자비중 추가**

> 기간 평균 투자비중 ≥ **30%**

주식을 거의 안 사는 전략은 메인 순위에 오르지 못한다.
30%는 넉넉한 값이다 — 현금 비중이 높은 정상적인 보수 전략도 대부분 통과한다.

**② 하락편차에 하한을 둔다**

> σ_down = max(실측 하락편차, **일 0.2%**)

일 0.2%는 연율로 약 3.2%다. 이 하한이 있으면 연 10% 수익 전략의 지수는 3.1 부근에서 멈춘다.
**분모가 0에 수렴해 무한대가 되는 경로가 원천 차단된다.**

**③ 하락 관측치 최소 개수**

> 손실이 발생한 거래일이 **10일 미만**이면 지수를 산출하지 않고 예선에 둔다

하락 관측치가 3~4개뿐이면 하락편차 추정 자체가 통계적으로 무의미하다.
v0.1은 이 경우를 다루지 않아 **분모가 0이면 그대로 무한대**가 되어 1등을 차지했다.

**④ 거래 건수 요건을 실질화**

> 청산 완료 거래 20건 중 **투입비중 1% 이상인 거래만** 센다

투입비중 0.001짜리 매매를 100번 해서 요건을 채우는 우회를 막는다.

### 8.4 설계 — 3단 구조

```
① 참가 요건 (Qualification Gate)
② 메인 순위 = 롤링 12개월 하락위험 대비 수익 지수
③ 보조 리그 (동등 노출, 단일 순위를 강요하지 않음)
```

#### ① 참가 요건

다섯 조건을 **모두** 만족해야 메인 순위에 오른다. 뒤의 두 개가 v0.2 신규다.

| 조건 | 임계값 | 근거 |
|---|---|---|
| 운영 기간 | 60 거래일 이상 | 업계 관행 "3개월" ≈ 60 거래일 |
| 청산 완료 거래 | 20건 이상 (비중 1% 이상만) | 관행은 50건이나 스윙 전략에 가혹하여 완화 |
| 제출 커버리지 | 70% 이상 | `hold` 도입으로 이제 매매 빈도와 무관 |
| **평균 투자비중** | **30% 이상** | 현금 파킹 조작 차단 (§8.3) |
| **손실 발생일** | **10일 이상** | 하락편차 추정의 통계적 최소 표본 (§8.3) |

미달 전략은 **예선(Provisional)** 으로 별도 표시한다. 숨기지 않는다 — 생존편향 방지.

#### ② 메인 순위

일별 운용자산 수익률 기준. 12개월 미만이면 가용 전 기간을 사용한다.
무위험수익률은 0으로 단순화한다 — 모든 전략에 동일 적용되므로 순위에 영향이 없다.

**표준편차가 아니라 하락편차인 이유**

표준편차 기반 지표(Sharpe)는 **위로 크게 오른 것도 벌점**이다.
큰 수익 몇 번으로 성과를 내는 추세추종 전략은 상방 변동이 클 수밖에 없어 부당하게 불리해진다.
하락편차만 보면 "손실은 짧게, 이익은 길게" 전략과 정합한다.

**롤링 윈도우인 이유**

누적 기준이면 문제 1(선착순 우위)이 영구히 해소되지 않는다.
롤링은 과거 영광에 안주할 수 없게 만들고, 늦게 합류한 전략에도 동등한 기회를 준다.

**갱신 주기 — 주 1회 (v0.2에서 변경)**

v0.1은 갱신 주기를 명시하지 않았다. 매일 갱신하면 **캘린더 효과로 순위가 요동친다.**
1년 전의 큰 손실일이 윈도우를 벗어나는 순간, 실력이 전혀 변하지 않았는데도 순위가 급등한다.

v0.2는 **매주 금요일 장 마감 후** 갱신한다. 일별 자산 추이는 매일 기록하되 순위 산출만 주간이다.

#### ③ 보조 리그

**단일 순위를 강요하지 않는 것이 핵심이다.** 하나의 숫자로 줄이면 반드시 그 숫자를 겨냥한 조작이 생긴다.
§8.3이 정확히 그 사례다.

| 리그 | 기준 | 성격 |
|---|---|---|
| 명예의 전당 | 전 기간 누적수익률 | 절대 성과 |
| 낙폭 관리 | 낙폭 대비 수익 지수 | 직관적이고 조작이 어려움 |
| 최근 폼 | 최근 3개월 수익률 | 현재 상태 |
| 지속성 | 최장 생존 거래일 수 | 오래 살아남는 것 자체가 실력 |
| 신인 리그 | 참가 요건 미달 전략끼리 | 신규 참여자 동기 |

### 8.5 시장별 보드 분리

`KRX` / `US` / `Crypto`를 **섞지 않는다.** 벤치마크와 변동성 스케일이 달라 섞으면 비교가 무의미해진다.

v0.2에서는 **한 전략이 한 시장에만 속하므로**(§4.1) 이 분리가 자동으로 성립한다.
v0.1의 "다중 시장 전략은 시장별로 분해한다"는 계산 불가능한 요구였고, 이제 필요 없어졌다.

### 8.6 전략 카드 상시 병기 지표

순위와 무관하게 모든 전략 카드에 항상 노출한다. **조작을 순위가 아니라 가시성으로 억제한다.**

| 지표 | 드러내는 것 |
|---|---|
| **평균 투자비중** ⭐ | 현금 파킹 여부. v0.2 신규 |
| 제출 커버리지 | 선언 생략 |
| 회전율 | 거래비용 왜곡, 과매매, 체결 오차 미반영 효과(§3) |
| 최대 단일종목 비중 | 집중 위험 |
| 청산 완료 거래 수 | 표본 충분성 |
| 운영 거래일 수 | 트랙레코드 길이 |
| 최대낙폭 | 최악의 순간 |
| 벤치마크 대비 초과수익 | 시장 베타 제거 |
| 승률 · 손익비 · 평균 보유기간 | 전략 성격 |
| **같은 계정의 다른 전략 목록** ⭐ | 다중 등록. v0.2 신규 (§4.1) |
| **축소 수락 비율** ⭐ | 계산 기준 오류 진단. v0.2 신규 (§6.3) |
| 현재 보유 스냅샷 | 장부 재구성 결과 |

**벤치마크 초과수익은 반드시 평균 투자비중과 함께 읽어야 한다.**
현금 50%를 들고 있는 전략은 하락장에서 자동으로 벤치마크를 이긴다. 그것은 실력이 아니다.
두 지표를 나란히 놓아야 해석이 가능하다.

### 8.7 신뢰도 뱃지

운 보정 지표(Deflated Sharpe Ratio)를 **순위 산정에는 쓰지 않는다** — 참여자가 이해하기 어렵고 직관에 반한다.
대신 **뱃지**로 표시한다.

> ✅ **검증됨** — 표본이 충분하고 통계적으로 유의함
> ⏳ **표본 부족** — 성과가 운일 가능성을 배제할 수 없음
> 💤 **휴면** — 30일 이상 선언 없음
> ⚠️ **무효 구간 있음** — 키 유출 등으로 일부 기간이 채점에서 제외됨 (§7.3)

학술적 엄밀성은 순위가 아니라 라벨로 전달하는 편이 실용적이다.

## 9. 아키텍처

### 9.1 구성

```
[참여자 — 아무 시스템, 아무 언어]
   POST /declarations   (HTTP 한 방. SDK 불필요)
        ↓ 즉시 동기 응답: accepted / clamped / rejected
[Supabase Postgres]
   원장 3종: declarations, price_observations, system_events
   · 접수시각을 DB가 생성 (참여자 접근 불가)
   · INSERT만 허용. UPDATE/DELETE 정책 없음 → 누구도 불가
   · 해시체인 트리거
        ↓
[처리기 — PRISM 서버 또는 GitHub Actions]
   ① 시세 실측 → price_observations 에 INSERT
   ② 장 시작 전 기업행위 조회 → system_events 에 INSERT
   ③ 원장 재생 → 계산장부 갱신
        ↓
[계산장부]  fills, positions, daily_assets, scores — 전부 재생성 가능
[리더보드]  계산장부 뷰를 그대로 읽음
[조회 API]  GET /portfolio — 검산 및 리밸런싱 비율 계산용
```

**v0.1과의 결정적 차이**: 처리기가 `declarations`를 UPDATE하지 않는다. 오직 INSERT만 한다.
따라서 "UPDATE는 누구도 할 수 없다"가 예외 없이 성립한다.

### 9.2 Supabase를 선택한 이유

| 필요한 것 | Supabase가 제공 |
|---|---|
| 권위 있는 접수시각 | `received_at timestamptz default now()` — DB가 생성 |
| 수정 불가 강제 | RLS로 UPDATE/DELETE 차단 |
| 전략별 인증 | 인증키 + RLS로 "자기 전략에만 쓰기" |
| 읽기 API | PostgREST 자동 생성 |
| 실시간 대시보드 | 구독 기본 제공 |
| 인프라 | 서버·도메인·배포 없음 |

**대안 검토**: 텔레그램 봇은 참여자에게 텔레그램 계정을 강제하므로 시스템 무관성 취지에 어긋나 탈락.
메시지 큐는 하루 수십~수백 건 규모에 과잉. 자체 HTTP API는 정석이나 인프라를 전부 새로 만들어야 한다.

**정직한 단점**: Supabase 종속(순수 Postgres라 이전은 용이), 무료 프로젝트는 1주 무사용 시 일시정지.

### 9.3 스키마 초안

```sql
-- ─────────── 원장 (INSERT만 가능) ───────────

create table strategies (
  strategy_id   text primary key,
  display_name  text not null,
  author        text not null,
  author_proof  text not null,          -- github:username 등 검증된 신원
  description   text,
  market        text not null,          -- 단수. 한 전략 = 한 시장
  currency      text not null,
  api_key_hash  text not null,
  created_at    timestamptz not null default now()   -- 트랙레코드 시작의 유일한 권위
);

create table declarations (
  id            bigserial primary key,
  strategy_id   text not null references strategies(strategy_id),
  seq           bigint not null,

  -- 참여자 제출 (단가·시각 필드 없음)
  market        text not null,
  symbol        text,                   -- hold 는 null 허용
  action        text not null check (action in ('buy','sell','hold')),
  weight        numeric check (weight > 0 and weight <= 1),
  sell_ratio    numeric check (sell_ratio > 0 and sell_ratio <= 1),
  reason        text check (length(reason) <= 500),
  meta          jsonb default '{}'::jsonb
                check (pg_column_size(meta) <= 4096),

  -- 서버가 INSERT 시점에 확정 (이후 절대 변경 없음)
  received_at   timestamptz not null default now(),
  admit_status  text not null,          -- accepted | clamped | rejected
  admit_reason  text,
  effective_weight numeric,             -- 축소 수락 시 실제 반영값

  prev_hash     text,
  hash          text,

  unique (strategy_id, seq),
  check ((action = 'buy'  and weight is not null and sell_ratio is null and symbol is not null)
      or (action = 'sell' and sell_ratio is not null and weight is null and symbol is not null)
      or (action = 'hold' and weight is null and sell_ratio is null))
);

create table price_observations (        -- 사후 재조회 불가하므로 원장이다
  id            bigserial primary key,
  declaration_id bigint references declarations(id),
  market        text not null,
  symbol        text not null,
  observed_at   timestamptz not null default now(),
  price         numeric not null,
  source        text not null,           -- kis | fallback
  tradable      boolean not null,        -- 상한가 잠김·거래정지 판정 (§5.5)
  delayed       boolean not null default false,
  prev_hash     text,
  hash          text
);

create table system_events (             -- 기업행위·상장폐지
  id            bigserial primary key,
  market        text not null,
  symbol        text not null,
  event_type    text not null,           -- split | dividend | delisting | halt
  payload       jsonb not null,
  effective_at  timestamptz not null,
  created_at    timestamptz not null default now(),
  prev_hash     text,
  hash          text
);

-- ─────────── 계산장부 (언제든 DROP 후 재생성) ───────────
-- fills, positions, daily_assets, scores
-- 위 세 원장만으로 100% 재현 가능해야 한다. 이것이 유일한 불변 조건이다.

-- ─────────── 수정 불가 강제 ───────────

alter table declarations       enable row level security;
alter table price_observations enable row level security;
alter table system_events      enable row level security;

create policy decl_insert on declarations
  for insert with check (strategy_id = current_setting('request.jwt.claims', true)::json->>'strategy_id');

create policy decl_read on declarations for select using (true);

-- UPDATE / DELETE 정책을 만들지 않음 → 전면 차단.
-- 처리기도 INSERT만 하므로 예외가 필요 없다.
```

`received_at`, `admit_status`, `hash` 등 서버 필드는 **컬럼 레벨 권한**으로 참여자 쓰기를 차단한다.

> **인증 방식 주의**: 위 RLS는 JWT의 `strategy_id` 클레임을 읽는다.
> 따라서 요청은 `Authorization: Bearer <JWT>` 를 써야 하며,
> Supabase의 `apikey` 헤더(프로젝트 공용 키 자리)에 전략 키를 넣으면 안 된다.
> **v0.1의 예시 코드는 이 점이 스키마와 어긋나 있었다.**
> 구체적 발급 방식(Supabase Auth 매핑 vs 커스텀 JWT vs Edge Function 게이트웨이)은 구현 시 결정하되,
> 요구사항은 하나다 — **참여자는 자기 전략에만 INSERT할 수 있고, UPDATE·DELETE는 누구도 할 수 없다.**

### 9.4 조회 API — `GET /portfolio`

```json
{ "strategy_id": "prism-kr-gpt5",
  "as_of":       "2026-08-10T06:30:00Z",
  "last_seq":    43,
  "total_assets": 1.0998,
  "cash":        0.9998,
  "invested_ratio": 0.0909,
  "positions": [
    { "market": "KRX", "symbol": "005930",
      "avg_cost": 10000, "market_value": 0.1, "weight": 0.0909 }
  ] }
```

`last_seq`는 참여자 프로세스 재시작 시 일련번호 복구에 사용한다.
`invested_ratio`(투자비중)는 §8.3의 요건을 참여자가 스스로 확인할 수 있도록 v0.2에서 추가했다.

## 10. 법적 고려

이 설계는 다음 이유로 유사투자자문업 위험을 낮게 유지한다.

- 각 참여자는 **자기 시스템을 자기 계좌로만** 운용한다. 운영자는 매매에 관여하지 않는다.
- 서버는 **실적을 신고받지 않고** 공개 시세로 계산할 뿐이다.
- 인증키·계좌번호·잔고는 프로토콜에 존재하지 않으며 로컬을 떠나지 않는다.

### v0.2에서 추가된 고려

**① 실시간 공개는 사실상 매매 시그널 방송이다**

v0.1은 §8.1에서 실시간 구독을 기본 제공하고 `reason`을 공개했다.
이 조합은 **"어떤 전략이 방금 무엇을 왜 샀는지"가 실시간으로 방송되는 것**이며,
운영자가 자문 행위를 하지 않더라도 구조적으로 그 경계에 있다.

v0.2는 **선언 상세(종목·사유)의 공개를 T+1로 지연**한다.
집계 지표(자산 추이·순위·투자비중)는 실시간으로 공개해도 무방하다.
따라 하기에는 이미 늦은 정보이므로 시그널로 기능하지 않는다.

**② 타인 자금 운용**

참여자가 가족·지인의 자금을 운용하는 경우 성격이 달라진다.
등록 약관에 **"본인 자금만 운용한다"** 를 명시하고 동의를 받는다.

**③ 복사매매로의 확장은 명시적 제외**

리더보드가 특정 전략의 매매를 따라 하도록 유도하는 형태(전략 구독·복사매매 등)로 확장되면
성격이 완전히 달라진다. **v0.2 범위에서 명시적으로 제외한다.**

## 12. 로드맵

### Phase 0 — 자가 대결 (외부 참여자 0명)

**빈 리더보드에는 아무도 오지 않는다.** 그리고 이슈 #328의 가설 검증에는 **외부 참여자가 필요 없다.**

같은 코드에서 판단 에이전트의 **모델만 바꿔** N개 인스턴스를 등록한다.

| 전략 ID | 구성 |
|---|---|
| `prism-kr-gpt5` | 기본 |
| `prism-kr-sonnet46` | 판단 에이전트만 Claude |
| `prism-kr-gemini` | 판단 에이전트만 Gemini |
| `prism-kr-t09` | 동일 모델, temperature 상향 |
| `prism-us`, `prism-btc` | 이미 존재 |

사람이 섞이면 변수가 오염되지만, **모델만 다른 동일 코드는 LLM 확률성의 순효과를 정확히 격리**한다.
이슈 #328의 가설에 오히려 더 충실한 실험이다.

**Phase 0에서는 §8의 조작 방어가 사실상 불필요하다** (자기 자신과 경쟁하므로).
그러나 방어 장치를 처음부터 넣어야 하는 이유는, **Phase 2에서 규칙을 바꾸면
그때까지 쌓인 데이터가 전부 무효가 되기 때문이다.** 채점 규칙은 첫날 확정되어야 한다.

### Phase 1 — 데이터 축적

Phase 0을 수 개월 돌려 리더보드에 **실제 이력을 채운다.**
순서가 중요하다 — **콘텐츠가 먼저, 사람이 나중이다.**

이 기간에 §11의 임계값들을 실측 분포로 검증한다.

### Phase 2 — 외부 개방

6개월치 데이터가 쌓인 리더보드를 보여주며 참여를 유도한다.
진입장벽을 PRISM에서 분리한다 — 어떤 시스템이든 HTTP 한 방이면 참여할 수 있다.

### Phase 3 — 신뢰 강화

- 머클 루트 외부 앵커링 (§7.6)
- 원장 전체 공개 → 제3자 독립 재현 가능
- 전략 등록 승인 절차 강화

## 부록 B — 레퍼런스 참여자 코드

§4.4의 계산 규칙을 코드로 강제한 최소 구현이다.
**파라미터 이름이 곧 정의**이므로, 시그니처를 따르면 §4.4의 오류를 범할 수 없다.

```python
import requests


class OTDClient:
    """OTD 선언 클라이언트. 참여자가 하는 계산은 나눗셈 두 번이 전부다."""

    def __init__(self, endpoint, strategy_id, token, market):
        self.endpoint = endpoint.rstrip("/")
        self.strategy_id = strategy_id
        self.token = token
        self.market = market                # 한 전략 = 한 시장 (§4.1)
        self.seq = self._recover_seq()      # 재시작 시 서버에서 자동 복구

    def _recover_seq(self):
        """v0.1 레퍼런스 코드는 seq 를 0 부터 다시 시작해 전량 거부되는 결함이 있었다."""
        try:
            return self.portfolio().get("last_seq", 0)
        except Exception:
            return 0

    def buy(self, symbol, invested_amount, total_assets, reason=None, meta=None):
        """
        invested_amount : 이번 매수에 실제로 넣은 금액
        total_assets    : 운용자산 = 굴리는 현금 + 보유 종목 평가액 총합
                          (예수금만 쓰지 말 것. 다른 목적의 돈은 제외할 것)
        """
        return self._send(symbol, "buy",
                          weight=invested_amount / total_assets,
                          reason=reason, meta=meta)

    def sell(self, symbol, sold_qty, qty_before_sell, reason=None, meta=None):
        """
        sold_qty        : 이번에 판 수량
        qty_before_sell : 팔기 '직전' 보유 수량 (최초 매수 수량이 아님)
        """
        return self._send(symbol, "sell",
                          sell_ratio=sold_qty / qty_before_sell,
                          reason=reason, meta=meta)

    def sell_all(self, symbol, reason=None, meta=None):
        return self._send(symbol, "sell", sell_ratio=1.0, reason=reason, meta=meta)

    def hold(self, reason=None):
        """매매하지 않기로 판단한 날에도 보낸다. 커버리지 지표에 반영된다."""
        return self._send(None, "hold", reason=reason)

    def portfolio(self):
        """현재 보유·운용자산 스냅샷. 리밸런싱 비율 계산과 검산에 사용."""
        r = requests.get(f"{self.endpoint}/portfolio",
                         headers=self._headers(),
                         params={"strategy_id": self.strategy_id}, timeout=10)
        r.raise_for_status()
        return r.json()

    def _headers(self):
        return {"Authorization": f"Bearer {self.token}",
                "Content-Type": "application/json"}

    def _send(self, symbol, action, weight=None, sell_ratio=None,
              reason=None, meta=None):
        next_seq = self.seq + 1             # 전송 성공 후에만 증가시킨다
        body = {"protocol": "otd/0.2",
                "strategy_id": self.strategy_id,
                "seq": next_seq,
                "market": self.market,
                "action": action}
        if symbol:
            body["symbol"] = symbol
        for k, v in (("weight", weight), ("sell_ratio", sell_ratio),
                     ("reason", reason), ("meta", meta)):
            if v is not None:
                body[k] = v

        r = requests.post(f"{self.endpoint}/declarations",
                          headers=self._headers(), json=body, timeout=10)
        r.raise_for_status()
        self.seq = next_seq                 # 여기까지 왔을 때만 확정

        result = r.json()
        if result.get("admit_status") == "clamped":
            print(f"[OTD] 비중 축소됨: 요청 {weight} → 반영 {result['effective_weight']}. "
                  f"운용자산 계산 기준을 확인하세요.")
        elif result.get("admit_status") == "rejected":
            print(f"[OTD] 거부됨: {result.get('admit_reason')}")
        return result
```

사용 예:

```python
otd = OTDClient("https://<project>.supabase.co/rest/v1", "my-strategy", TOKEN, market="KRX")

# 운용자산 5,000만원 중 500만원어치 매수 → 투입비중 0.1
otd.buy("005930", invested_amount=5_000_000, total_assets=50_000_000,
        reason="20일선 눌림목")

# 100주 보유 중 50주 매도 → 매도비율 0.5
otd.sell("005930", sold_qty=50, qty_before_sell=100)

# 잔량 전부 청산
otd.sell_all("005930", reason="추세 이탈")

# 매매하지 않은 날
otd.hold(reason="관망")

# 검산: 서버가 계산한 보유·운용자산을 자기 계좌와 대조
print(otd.portfolio())
```

### v0.1 레퍼런스 코드에서 고친 것

1. **일련번호 복구** — v0.1은 `start_seq=0` 기본값에 영속화가 없어, 프로세스를 재시작하면
   1번부터 다시 보내 **전량 거부**되었다. 주석은 "복구하라"였지만 코드가 하지 않았다.
   v0.2는 생성자에서 서버 조회로 자동 복구한다.
2. **전송 실패 시 번호 유실** — v0.1은 POST **전에** `self.seq += 1`을 해서,
   예외가 발생하면 그 번호가 영구히 비게 되고 누락 경보가 잘못 울렸다.
   v0.2는 전송 성공 후에만 증가시킨다.
3. **축소·거부 즉시 통보** — 동기 응답을 그냥 버리지 않고 참여자에게 출력한다.
   계산 기준 오류를 가장 빨리 발견하는 지점이다.
4. **인증 헤더** — `apikey`에서 `Authorization: Bearer`로 교체 (§9.3 주의 참조).
