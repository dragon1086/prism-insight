# M0 사건별 미정산 격리: 오프라인 구현 후보

## 상태와 범위

이 변경은 복구 정책만 구현합니다. 배포, DB 전환, cron 변경, 실제 주문,
모델 호출을 수행하지 않았습니다. 운영 활성화는 OFF입니다. 진입 전략,
TP 비중, 부분손절 선호 변경과 분리합니다. 테스트 거래는 실제 수익 표본이 아닙니다.

대상은 `s_bd46ee3659f6ee1a5c630d1f`와 원 UNKNOWN
`sc_c25e58e9459f4bf7de1d0d718cb1afd8`뿐입니다. 기존 관리 승인과
원 요청, intent, child, 계약, 감축 복원 원장은 삭제하거나 종결 처리하지 않습니다.
기존 사건은 `HISTORICAL_UNSETTLED`로 별도 표시하고 성과 집계에서 제외합니다.
새 사건의 정확한 정산만 기존 settlements 원장에 들어갑니다.

## 구현 경계

- `scenario_incident_epoch.cutover`는 runner나 CLI에 노출하지 않습니다.
  별도 실행 승인, 원 사건 전체 행 해시, 현재 코드 해시, 계정/endpoint/DB,
  사용기한, 새 epoch, 숨은 원 주문 잔여 위험 수용을 결박합니다.
- 전체 계좌의 포지션과 주문 출처를 두 번 페이지 끝까지 읽습니다.
  선형 USDT/USDC, inverse, option, spot 주문 출처를 확인합니다.
  이는 derivative 포지션과 열린 주문의 조회 범위이며 spot 보유자산의 무잔고를 증명하지 않습니다.
  지원하지 않는 조회/필터, 페이지 누락, 범위 불확실은 빈 결과로 바꾸지 않고 거부합니다.
  열린 주문은 공식 문서의 기본 all-kinds 조회를 사용하며 spot도 한 번만 조회합니다.
  별도의 root GET-only probe가 9개 조회 범위의 현재 호환성을 확인했지만,
  이 구현의 테스트나 향후 지연·운영 quiescence 검증을 대체하지 않습니다.
- 일일 위험/입출금 갱신 및 외부 조회는 SQLite 전환 트랜잭션 **전에** 끝냅니다.
  전환 안에서는 원 상태, 행 해시, 일일 원장 버전, 신선도만 재확인하고
  append-only 영수증, 기존 관리 승인 종료, 새 OBSERVING 상태, control v2를 함께 저장합니다.
- 원 active는 영수증에 보존하고 관리 대상에서만 분리합니다. 과거 settlement는 만들지 않습니다.
  일일 손실, 자금 이동, 중단 latch, 연패 기록은 이어집니다.
- 모든 정상 POST는 같은 mutation mutex에서 epoch를 확인하고 전송이 끝날 때까지 잠급니다.
  BEGIN/RETURNED 전송 기록과 실행 중 배치를 확인합니다. epoch 읽기 실패는
  기존 reduceOnly/cancel fallback으로 넘어가지 않습니다. 옛 link/order 및 옛 broker 인스턴스는 거부합니다.
- control v2를 모르는 **기존 정상 runner**는 broker 생성 전 control 읽기에서 종료합니다.
  새 코드의 legacy 진입/관리는 v2에서 모두 거부됩니다. 임의 외부 프로그램이
  옛 모듈을 직접 호출하는 경우까지 이 DB 정책이 차단한다고 주장하지 않습니다.
- 새 위험은 기존 허용치와 0.5% 중 작은 값입니다. 10배/15분봉 제외/Full SL을 유지합니다.
  첫 자연 판단은 관찰이며, 다음 실제 시장 수치 변화와 반대 근거·실패 조건을 확인해야 진입합니다.
  자동 위험 단계 승격은 금지합니다. 새 거래가 정확히 정산되면 다시 관찰합니다.
- 보호 주기에 원 사건의 주문/체결/금융 증거와 전체 계좌 소유를 대조합니다.
  늦은 증거나 조회 공백은 append-only 중단 기록으로 남고 새 위험만 차단합니다.
  옛 원장은 수정하지 않습니다. 현재 Full SL 유지·기존 HALT/만료 진입 취소·
  명시적 EXIT·소유 수량의 emergency fallback이 과거 조회보다 먼저 실행됩니다.
  새 HALT를 발견한 같은 보호 주기에서도 남은 진입을 취소하고, 취소 중 체결된 잔량은 Full SL로 보호합니다.
  중단 기록은 기존 미체결 진입의 재승인도 거부합니다.
  과거 조회는 명시적인 관측 한 번으로 묶고 10초 안에서만 재사용합니다.
  context와 최종 POST guard는 과거 REST를 호출하지 않습니다.
  신원 GET 이후 실제 전송 직전에도 epoch/hash/HALT/관측 신선도를 다시 확인합니다.
  과거 조회가 제한 시간을 넘으면 새 위험을 거부하며 보호·취소를 그 뒤로 미루지 않습니다.
  계좌 손익은 equity/자금 흐름 원장에서 한 번만 반영하며 과거 거래 손익을 다시 더하지 않습니다.

## 운영 전환의 별도 필수 조건

제품 코드는 이미 실행 중인 **구버전** HTTP 요청을 취소할 수 없습니다.
전환에 앞서 운영자가 두 runner의 scheduler를 멈추고, 기존 worker의 종료와
진행 중 전송이 없음을 확인해야 합니다. 이 절차는 아직 수행하지 않았습니다.

전환은 신뢰하는 호스트 측 배포 probe를 요구합니다. 승인에 결박된 scheduler 전후 원문,
프로세스 전후 전체 목록, 종료된 worker의 PID·시작 시각·명령·종료 증거,
호스트/DB 및 호환 launcher 코드 manifest가 있어야 합니다. 실제 PID가 여전히 살아 있으면 거부합니다.
`no_inflight=true` 같은 단일 플래그는 이 증거를 대체하지 않습니다.
이 callback은 신뢰 경계이며, 외부 JSON의 진실성을 코드가 자동 인증한다는 뜻이 아닙니다.
PID 재사용/운영 증거 만료는 다시 확인해야 합니다.

공통 mutex가 다른 경로/다른 호스트에 걸친 요청까지 제어한다고 가정하지 않습니다.
기존 runner 프로세스가 살아 있거나 배포 probe를 제공할 수 없으면 전환을 실행하지 않습니다.
숨은 과거 Sell reduceOnly가 새 LONG을 줄일 위험은 여전히 남습니다.
빈 조회는 원 요청 거절의 증거가 아닙니다. 실제 재개 승인은 이 위험까지 별도로 수용해야 합니다.

금융 증거는 원 사건의 고정 구간과 현재 rolling 구간을 나누어 조회합니다.
고정 구간을 다시 읽어 과거 시각을 유지한 늦은 체결/수수료 정정을 확인하고,
rolling 구간은 완료된 coverage watermark와 하루 겹침 구간을 저장하여 이어 갑니다.
원 orderLinkId의 체결은 전환 이후 시각이어도 보존하고 중단 근거로 사용합니다.
사건이 7일 지났다는 이유만으로 중단하지 않습니다. 실제 관측 공백이 7일 조회 창을 넘거나
원 구간 조회가 불가능하면 누락 구간을 성공으로 채우지 않고 새 위험을 차단합니다.
정확한 종결 증거가 없는 원 UNKNOWN은 계속 미정산으로 남습니다.
거래소가 관측 때 제공하지 않던 체결을 rolling 범위 밖의 과거 시각으로 뒤늦게 공개하면 즉시 발견을 보장하지 못합니다. 유한 REST 관측의 잔여 한계이며, 실제 수량 불일치는 기존 current-account 소유 검증/정산 차단으로, 계좌 손익 변화는 일일 equity·자금 흐름 연속성으로 따로 다룹니다.
equity 변화는 모든 이상을 자동 중단시키지 않습니다. 일일 손익에 반영하고 기존 손실 한도에 도달하면 차단합니다. 작은 수수료 정정의 즉시 탐지·중단을 보장하지 않습니다.

공식 주문 조회 문서는 `orderFilter` 생략 시 모든 주문 종류를 반환한다고 명시합니다([Bybit 주문 조회](https://bybit-exchange.github.io/docs/v5/order/open-order)). 이를 사용해 spot 조회를 한 번으로 줄였습니다. 별도 읽기 전용 실제 데모 호환 검사에서 derivative 포지션/열린 주문과 spot 열린 주문 9개 조회가 모두 성공·페이지 완료·빈 목록이었고 합계 약0.708초였습니다. 이것은 한 시점의 호환성 근거이며 전환 승인·quiescence·미래 지연 보장이 아닙니다. [데모 API 제한](https://bybit-exchange.github.io/docs/v5/demo)을 고려해 지원하지 않는 응답은 계속 차단합니다.

## 되돌리기

새 진입을 중지하고 현재 버전에서 새 포지션 보호/정산을 이어갑니다.
원 active를 되살리거나 원 주문을 재전송하지 않습니다. control v2를 v1로
덮어쓰거나 격리 영수증을 삭제하여 구버전을 실행하는 방식은 금지합니다.
기존 코드로 돌아가야 한다면 먼저 모든 새 구간 포지션/주문을 정확히 대조하고
별도의 호환성 절차를 승인받아야 합니다.

## 검증 구분

테스트는 실제 broker/runtime 모듈에 기존 메모리 거래소 fixture를 연결합니다.
전환 원자성/승인 재사용/옛 worker POST/읽기 오류/새 OBSERVING→OPEN→정산/
지연 과거 증거 후 현재 보호를 확인합니다. 기존 코드의 fallback 우회 4개는
고정 기준 커밋의 실제 메서드를 읽어 별도 반례로 보존합니다.
테스트 fixture의 사건 ID 치환은 실제 사건 실행 승인이 아니며 loaded-code 검증으로 주장하지 않습니다.
전체 테스트, CI, 배포, 첫 자연 관찰, 자연 진입/정산, 수익성 입증은 각각 별도 상태입니다.

독립 재검토에서 초기3개 P1(HALT 후 대기진입 잔존, 원 link-only 지연 체결 누락, 반복 역사 조회)을 확인해 보강했다. 영향범위7파일322개 통과 후 rolling 경계1줄 보강의3개 테스트를 통과했다(network0). 구버전 반례는 원8be96d의 실제 함수와 SHA를 고정 fixture로 보존해 git 이력이 없는 archive·shallow CI에서도 동일하게 검증한다. source binding28개와 이식성 사전검증6개도 통과했다. 별도 전체 테스트는 최종 확정 커밋에 한 번 수행한다. 이 결과는 코드 검증 단계 진행 근거이지 활성화 승인이나 실제 손익 증거가 아니다.
