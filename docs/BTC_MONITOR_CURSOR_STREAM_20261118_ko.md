# BTC 과거 금융 감시 커서의 스트림 검증 (M0)

15:15 신규 위험 차단은 기존10초 관측 제한을 넘은 monitor_finance_deadline이었다. 커서읽기4.023초·검증2.101초·자식조회2.499초가 기록됐고 배포 전15:04에도 커서읽기8.544초의 실패가 있었다. 활성 영구 incident HALT는0이며 일일 손실 차단은false다. 연속손실/기존 회복 권한은 유지한다. 이 문제는 진입 메뉴 수정과 별개다.

기존 코드는 과거 금융 커서를 전부 파싱해 보관한 뒤 모든 해시/승인 epoch를 검사하고 계좌별 마지막 커서만 사용했다. 이제 기존 SQL의 covering index·rowid 순서를 그대로 읽는 iterator를 재사용하고, 모든 행을 순서대로 검증하면서 epoch별 마지막 값만 남긴다. `_events`의 기존 list 반환 계약은 보존한다. 과거 행 생략·최신 행만 검증·캐시·새 파서·DB변경·추가 의존성·시간/위험/복구권한 변경은 없다. JSON복원은 지연되므로 단계별 로그의 cursor_validate가 복원과 검증을 함께 포함한다. 관측 시작 시점과 전체10초 기준은 그대로다.

운영DB의 고정 읽기 전용 스냅샷89423행에서 원전체리스트/스트림/원warm을 각1회 비교했다. 전 행 검증 순서 SHA와 최종 값 SHA가 모두 일치했고 파싱 후 보관 커서는89423개에서2개가 됐다. 벽시계는1535.8/1065.3/1107.6ms, CPU는1101.9/1049.3/1093.0ms였다. 캐시가 데워진 원 대비 시간 이득은 작으며 메모리 보관을 줄이는 수정이다. 이결과로 모든 시간초과의 재발방지를 주장하지 않는다. 실험에서 원DB쓰기/모델/주문은0이었다. 별도 SQL정렬 변경과 GC일시중지는 이득이 작거나 없어 채택하지 않았다.

기존 호출자·과거 전체 행/순서·오래된 잘못된 해시/승인되지 않은 epoch 차단·단계별 시간초과·회복 권한을 검사했다. 지연복원 회귀검사가 변경 전 실패했고 수정 후 관련182건 성공/pybit없는 로컬에서 기존3건 제외다. 해당 cursor 회귀파일도 CI에 명시적으로 연결한다. CI·배포·운영스모크·첫정기실행은 별도 확인한다. 강제 모델 호출이나 주문으로 검증하지 않는다.
