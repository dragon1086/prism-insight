# BTC 연구 실행 절차

메인 에이전트가 가설·해석·다음 작업을 맡고, 스킬은 아래 절차로 연결한다. 계산·실행은 검증된 기존 도구를 재사용한다. 이 문서는 새 전략 규칙이나 추가 실행 권한을 부여하지 않는다. 수익성 판정 기준은 BTC_ROADMAP의 M5와 BTC_PROOF_GATES를 따른다.

## 실행 전에 고정할 것

- 새 필드나 검증 방법을 발견했다고 판단하기 전에 기존 연구 색인과 해당 필드의 사전 등록·결과·분석
  스크립트를 검색한다. 새 운영 자료의 가용성 확인과 이전 연구의 최초 발견을 구분하고, 같은 증거로
  끝난 비교를 다시 호출하지 않는다. 원본 세션 기록은 열지 않는다.
- 특정 사건을 새 원인으로 보고하기 전에는 slot·action·scenario 참조와 주요 키워드로 `docs/`, `tasks/`의
  기존 Markdown 결과를 확인한다. `tasks/`는 Git ignore될 수 있으므로 `rg --no-ignore -g '*.md'`를 사용한다.
  이미 수정된 사례면 현재 서버 코드에 수정이 포함됐는지 따로 확인하고 과거 오류와 현재 상태를 구분한다.
- 안쪽/바깥쪽의 **판단 시간축·확정/형성·가격 종류·원래 진입 목적**을 구분한다. 가격이 MA 바깥이라는 사실만으로 추세 표본이라고 부르지 않는다. 승패를 보고 고른 사례는 개발 반례이며 holdout이 아니다.
- 진입 목적은 해당 시점의 실제 계약 스키마와 원 결정을 대조한다. 현재 BTC entry contract의 분류 필드는
  `regime`이며 `style`만 찾아 MISSING으로 판단하지 않는다. 계약 목적과 MA 사이/바깥 가격 위치는 별개다.
- 원 입력·가격 자료·소스 버전·초기 상태·비용·비교안·평가 기간·실패 조건을 등록한다. 실제 호출 순서도 목록으로 고정하고, 실행기가 그 목록을 사용하는지 유료 호출 전에 확인한다. 등록서에만 ‘교대’라고 써두지 않는다.
- 실행 중인 호출 장부를 점검하려고 `CallGuard(...)`를 새로 생성하지 않는다. 생성자는 미완료 요청을 발견하면 `unfinished_attempt`로 영구 중단한다. 진행 상태는 프로세스/세션 핸들과 `CallGuard.inspect_existing(root, registry_sha256, max_calls)`의 읽기 전용 검증 결과로 확인한다. 이 메서드는 장부·앵커를 만들거나 고치지 않는다. 살아 있는 요청의 reserve만으로 실패·중단을 판정하지 않는다. 새 인스턴스의 snapshot은 실제 실행 종료와 마지막 요청 종료를 확인한 뒤에만 사용한다.
- 실제 HTTP 예산에 실패도 포함한다. 2026-10-26에 승인된 자율 BTC 목표는 비교 주기 최대48회, 재시도·봉인 장부 재개 금지다. 기술 수리 후 재검증은 새 버전으로 등록하며 원 실패를 보존한다. 반복 측정은 목적과 횟수를 먼저 정한다.
- 비용 절감 실험 전에는 기존 응답의 입력·출력·캐시 토큰과 호출 횟수를 집계하고, 실험별 사용량과 전체 계정 사용량을 구분한다. 공통 프롬프트가 길어도 캐시 적중을 가정하지 않는다. 프록시 전달과 실제 모델의 캐시 지원·적중은 각각 확인하며, 실거래 입력 없이 작은 모의 입력부터 검증한다.
- 과거 거래 자료를 합칠 때는 출처와 해시를 확인하고 중복 거래를 제거한다. 이미 확인한 결과·제한을 재사용하며, 같은 정책·같은 조건이 아니면 전후 개선으로 보고하지 않는다.
- 오프라인 재생·테스트는 공용 전송 파일을 사용하지 않는다. 기본 전송 경로를 `/dev/null`로 지정하고,
  전송 기능 자체를 검사할 때만 별도의 임시 파일을 명시한다. 실험 사건을 실제 매매 원장으로 보내지 않는다.
- 저장 형식을 추가할 때 운영 reader뿐 아니라 테스트의 직접 DB 조회·복원 보조 코드도 확인한다. 압축과 참조는
  다른 형식이므로 참조 본문은 slot·sequence·DB 연결을 가진 공용 reader로 복원하고 기존 형식 회귀도 검사한다.
- 운영 저장 공간 작업은 예상 회수량과 임시 공간부터 계산한다. 소량 전환을 반복하기 전에 전체 후보량을 표본으로 추정하고, 기존 검증 백업과 복원·참조 증거가 없으면 삭제하지 않는다. 백업의 정기 실행·원격 여유 공간·순환 보존은 각각 확인한다.
- SQLite 내부 재사용 공간과 파일시스템에 실제 반환된 공간을 따로 보고한다. 반복 전환의 총 작업량과 회수 효과를 먼저 비교한다. 백업에 부가 기능을 넣을 때는 import·초기화·실행 실패를 모두 격리하고, 부가 기능이 실패해도 백업 복원 검증이 끝나는 반례를 시험한다.
- 긴 PR CI를 시작하기 전 관련 변경과 반례를 한 번에 모아 작은 로컬 검사를 끝낸다. 이미 실행 중인 CI는 새 증거 없는 사소한 수정으로 재시작하지 않는다. 다만 안전 결함이 확인되면 즉시 고치고 이전 head의 결과를 새 head의 성공으로 사용하지 않는다.
- 문서 전용 직접 반영이 허용된 경우에도 원격 main에 PR·상태 검사 보호 규칙이 있으면 PR을 사용한다. 관리자 권한으로 보호 규칙을 우회하지 않는다.
- 최근 원장 집계에는 종료 시각도 지정한다. 허용 오차를 벗어난 미래 시각 사건은 실제 거래로 세지 않고
  별도 건수로 남긴다. 원본 사건은 지우지 않으며 실제 체결 여부는 거래소 근거로 확인한다.
- 원시 financial 수집 결과의 `executions_complete=False`는 시나리오별 주문·펀딩 검증 전의 의도된 값이다.
  이를 최종 정산 실패로 집계하지 않는다. 정산의 완결 플래그·감사·체결 ID를 따로 연결하고,
  저장 기록끼리의 일치와 독립 거래소 원장 재검증을 구분한다.
- 안쪽/바깥쪽 집계에서 과거 baseline의 `confirmed_position`과 `mark_vs_confirmed_ma`는 다른 값이다.
  한 집계는 같은 가격·시간 기준으로 통일하고, 중복 거래의 원본 위치와 합계 및 교차 기준 불일치를 검증한다.
- 여러 체결의 시간 구간을 합쳐 조회해도 각 체결에 호가를 연결할 때는 그 체결의 시간 경계를 다시 적용한다.
  표본 식별 해시는 정렬된 자료의 고정 표현으로 만들고, Python set 출력 순서에 의존하지 않는다.

## 기존 도구를 선택하는 기준

| 목적 | 먼저 확인할 경로 |
|---|---|
| 공개 과거 시세·Mark·펀딩·주간 접두부 | `prism-btc/analysis/scenario_dataset.py:create_bundle`, `prism-btc/backtest/scenario_data.py` |
| 진입부터 보유·보호·청산까지 재생 | `prism-btc/analysis/scenario_replay.py:run_replay`와 실제 runtime/broker/executor |
| 현재 목표 계약을 포함한 연구 | 명시적 `economic-reject-goal-v2` 프로필과 기록된 runtime_flags |
| 실제 모델 호출 한도·원 응답 보존 | `tools/btc_research_call_guard.py`, `tools/btc_research_model_call.py` |
| 등록 계약·원장 산술·성과 검증 | `tools/compare_btc_scenario_replays.py`, `prism-btc/analysis/profitability_gate.py` |

‘current’라는 이름만 보고 현재 운영과 같은 기능이라고 가정하지 않는다. runner의 실제 플래그와 재생 계약을 대조한다. 기존 연구 coordinator가 새 프로필을 지원하지 않으면 지원한다고 표시하지 않는다. 데이터 수집기의 기본 재시도/sleep 동작도 작업의 사용자 제약과 대조한다.

운영 정책 성과를 평가할 때 별도의 손익·익절 배분 모형부터 다시 만들지 않는다. 실제 executor의 revision 누적 quota·수량 내림·미체결 취소·native SL을 사용한다. 단순 모형은 탐색에 쓸 수 있지만, 생략한 동작을 명시하고 실제 정책의 성과로 합치지 않는다. 특히 내림 잔량을 마지막 TP에 임의로 더하면 안 된다.

## 실행 중·실행 후

- 사용자 정정(2026-10-27): 결과 보고는 **개선 경향 → 근거 → 남은 불확실성** 순서로 쓴다. 최종 입증이 부족하더라도 실행 안정성·진입 품질·손익 구조·수익성 각각의 개선/악화 신호를 설명한다. 같은 조건의 전후 비교가 없으면 방향을 단정하지 않으며, '미입증'만 반복해 관측된 문제를 숨기지 않는다. 미청산 평가이익이나 서로 다른 기간의 결과를 개선 효과로 쓰지 않는다.
- 전략 검증의 주 단위는 상태와 자본을 이어가는 연속 기간의 여러 거래 사이클이다. 짧은 실행 점검을 전략 성과 검증으로 대체하지 않는다. 사용자가 비용 때문에 기간을 줄이면 그 선택과 실제 종료 사이클 수를 보고하고, 사이클이 부족한 결과는 제한된 증거로 남긴다.

- 실제 체결과 코드가 보낸 요청/ACK를 구분한다. 정상 확인 대기도 완료가 아니다. 기술 오류가 나오면 등록한 중지 조건에 따라 호출을 봉인하고 원인을 분리한다.
- 저장된 기록을 **다른 프로세스**에서 재생해 전체 결과를 확인한다. 같은 프로세스에서만 맞는 결과는 PID 등 환경 차이를 놓칠 수 있다. 기존 기록을 고치거나 검사 항목을 빼서 맞추지 않는다.
- 완료 거래·미청산·미체결·MISSING을 따로 집계한다. 미청산 평가이익을 승리나 평균 실현이익에 넣지 않는다. 가격 접촉이나 거래 한 건의 정산 일치도 체결 예측 모형의 검증과 다르다.
- 지연은 입력·모델 단계·재조회·검증으로 나눠 측정한다. 문자 수를 토큰 수나 지연 원인으로 단정하지 않는다. 시간 제한이나 안전 검사를 먼저 완화하지 않는다.
- 결과를 정정하면 원 산출물을 보존하고, 정정된 결과·철회한 주장·영향받지 않은 근거를 함께 기록한다. 현재 상태 문서가 폐기된 결과를 계속 가리키지 않게 한다.

사용자가 승인한 다음 작업은 이어간다. 실행 중인 CI나 관측 작업은 실제 job/프로세스/타이머로 확인하며, 정상 진행 중인 CI를 곧바로 Goal 차단 사유로 삼지 않는다. 배포·첫 정기 실행·자연 발생한 변경 경로·24시간 관측·수익성 입증은 각각 보고한다. 이번 BTC 작업의 하위 에이전트 금지·sleep/wait 반복 조회 금지·원 세션 JSONL 금지·변경 부분 로컬 검사/전체 PR CI 제약을 유지한다. 다른 작업의 제약과 권한은 그 사용자의 지시를 따른다.
