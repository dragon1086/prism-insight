# BTC TP/SL 실행 개선 후속 기록

작성일: 2026-09-06 KST
대상: M0.3·M0.5 TP 실행 정합성 / M2.2·M2.5 오프라인 진단
상태: 코드·검증 작업, 운영 미배포. 수익성 입증 자료가 아닙니다.

## 핵심 결론

SL은 진입 주문에 동반하는 기존 PR #662의 경로를 유지합니다.
이번 후속 작업은 TP를 거래소에 맡기고, 실제 체결과 남은 물량을 정확히 관리하는 데 집중했습니다.
진입 주문에 Full TP까지 넣어 1R에서 전량을 팔도록 바꾸지 않았습니다.

- 메인: 기존 단일 aggregate TP1, 최신 트랜치 목표가, 전체 수량의 1/3을 유지합니다.
  수량은 기존 _qstr의 .001 BTC 반올림 규칙을 그대로 사용합니다.
- 남은 물량은 기존 BE·트레일·신호 청산 규칙을 유지합니다.
- TP2/TP3는 기존처럼 활성 청산 사다리가 아닙니다. 스윙에도 새 고정 TP를 넣지 않습니다.
- 메인 5%·스윙 1.5%, 기존 신호·SL·BE·트레일 시간대와 기준을 바꾸지 않습니다.

## 1. 실제 개선한 것

### 목표가에 닿았다는 이유만으로 익절 완료 처리하지 않습니다

기존 BookPartial 경로는 봉의 고가/저가가 TP에 닿으면 tp1_hit를 true로 바꿨습니다.
이제 가격 접촉은 관측일 뿐입니다. exact TP order/link와 연결된 Trade 체결을 확인하고,
해당 내부 배분 quota가 실제로 충족될 때만 완료 상태를 갱신합니다.

### TP1을 GTC reduce-only limit으로 관리합니다

기존 PostOnly는 제출 시 즉시 체결될 가격이면 취소될 수 있었습니다.
GTC limit은 같은 목표가를 유지하면서 이 자동 취소를 피할 수 있습니다.
매도 TP는 지정가 이상, 숏 청산 매수 TP는 지정가 이하에서 체결을 요청하되
호가·유동성에 따라 체결을 보장하지 않습니다. 진입 주문의 PostOnly는 바꾸지 않습니다.
[Bybit 주문 생성 문서](https://bybit-exchange.github.io/docs/v5/order/create-order)

GTC는 시장가처럼 체결될 때 taker 수수료가 발생할 수 있습니다.
따라서 항상 maker라고 간주하지 않고 실제 execution의 수수료를 기록합니다.
TP2/TP3나 전량 TP를 추가해 추세 수익을 임의로 제한하지 않습니다.

### TP intent와 체결 반영 기록을 영속화합니다

entry pending이 해제돼도 다음 정보가 남습니다.

- exact order ID/link, generation, 목표 수량·가격
- 원래 position-ID·수량과 고정 quota
- 이미 반영한 execId와 수량·가격·실제 수수료
- 종료된 generation과 내부 귀속 기록

확인된 체결량·원장 수량·체결 cursor를 함께 원자적으로 저장합니다.
수정 중 프로세스가 종료되면 rollback하거나 같은 receipt에서 재개하며,
같은 체결을 두 번 차감하지 않습니다.

### 주문·체결 정체성과 수량을 함께 검사합니다

- 전체 pagination, 실패·순환·상충 응답을 검사합니다.
- symbol·side·order/link·execType=Trade·execId를 확인합니다.
- 수량·가격·수수료의 유한성, 중복 ID, 누적 수량과 현재 노출의 일치를 검사합니다.
- ACK·가격 접촉·조회 결과 부재는 체결 증거가 아닙니다.
- 실제 음수 수수료 리베이트는 보존합니다.

### 부분체결·취소 후에는 남은 목표만 다시 주문합니다

정확한 terminal 상태와 전체 Trade 증거가 있어야 새 generation을 만들 수 있습니다.
일부 체결 후 취소되면 이미 체결된 물량을 제외한 잔량만 요청합니다.
응답 유실이나 제출 여부가 불확실하면 확인 없이 다시 내지 않습니다.

### TP가 불확실해도 SL 보호는 계속 확인합니다

30분 판단 경로와 10분 보호 경로에서 실제 남은 노출의 SL을 먼저 확인합니다.
기존 stop이 충분하면 유지하며, native/manual stop을 자기 소유로 바꾸지 않습니다.
TP 불확실성이 신규 위험 증가를 막더라도 SL 복구까지 막지는 않도록 보완했습니다.
부분 진입의 만료·취소도 TP 정산 성공 여부와 분리했습니다.

### 다른 청산과 TP가 경쟁하지 않게 처리합니다

강제 감축·일반 청산 전에 경쟁하는 TP를 종료 확인하고,
취소와 동시에 일어난 TP 체결도 반영한 뒤 실제 남은 수량으로 판단합니다.
확인된 자체 감축 후에는 살아 있는 position-ID의 잔여 quota만 복구하며,
사라진 트랜치의 quota를 다른 트랜치에 넘기지 않습니다.

취소를 기다리는 동안 청산 조건이 사라졌고 감축 주문을 제출하지 않았다면,
오래된 판단으로 시장가 청산하지 않고 잔여 TP를 복구합니다.
이미 제출한 감축이 미확정이면 재요청하지 않고 기존 확인 절차를 유지합니다.

### 포지션 종료 뒤 오래된 TP 상태를 남기지 않습니다

실제 flat과 exact TP terminal을 확인하고 주문 상태·보유 정리·재진입 대기 기록을 처리합니다.
실제 종료 가격이나 원인이 확인되지 않으면 남은 장부는 unpriced external exit로 보존합니다.
손절 체결가나 순손익을 만들어 넣지 않습니다.
오래된 TP ID가 다음 진입 receipt에 다시 들어가 진행을 막는 문제도 회귀로 고정했습니다.

## 2. 내부 배분의 의미와 검증 사례

거래소의 aggregate TP 체결에는 내부 트랜치 구분이 없습니다.
고정 snapshot의 수량 비율로 .001 BTC quota를 만들고, 반올림 잔여 lot은
position-ID 순서에 따라 배분합니다. 부분체결은 고정 quota를 순서대로 소비합니다.

이는 결정론적인 내부 장부 귀속 규약입니다.
각 트랜치가 자신의 1R 목표에서 체결됐다는 거래소 증거로 해석하지 않습니다.
실제 단일 aggregate 주문의 가격·기본 목표 비율은 유지합니다.

모의 거래 테스트:
- 0.030 BTC에서 TP 0.004 체결 → 0.026 잔량.
- 이후 0.006 추가 체결 → 0.020 잔량. 반복 조회·재시작으로 다시 차감하지 않습니다.
- 기존 0.030 + 확인된 추가 진입 0.030 − TP 0.004 → 0.056.
  이전 leg 0.026과 새 leg 0.030을 구분하고 새 TP는 기존 규칙에 따라 0.019로 계산합니다.
- TP 목표 0.010 중 0.004 체결 후 취소 → 새 요청은 잔량 0.006뿐입니다.
- 강제 감축·일부 leg 종료 후에는 확인된 남은 quota만 유지합니다.
- 모르는 외부 수량 변화나 증거 상충은 추정으로 맞추지 않습니다.

내부 누적 gross·수수료 기록은 기존 저장된 원가와 체결에 따른 장부 계산입니다.
완전한 broker 순손익·실제 펀딩·MTM NAV 일치까지 검증됐다는 뜻은 아닙니다.

## 3. 백테스트가 더 좋아지는가

**체결 재현성과 검증 수준은 개선할 수 있지만, 수익률이 자동으로 올라가지는 않습니다.**
기존 백테스트도 이미 TP1과 SL을 반영하고 있습니다. 이번에 그 엔진의 수익 숫자나
트레일 파라미터를 바꾸지는 않았습니다.

오프라인 진단은 다음 문제를 드러냅니다.

1. 진입 봉 안에서 고가/저가가 진입 전인지 후인지 모르면 TP·BE 수익을 확정할 수 없습니다.
2. 이미 열려 있던 포지션이 손절가를 건너뛰어 갭을 만들면,
   기존 모델의 손절가가 그 봉의 가격 범위 밖일 수 있습니다.
3. 같은 봉에서 TP와 SL을 모두 건드리면 OHLC만으로 실제 순서를 알 수 없습니다.
4. 기존 모델의 SL-before-TP는 TP/SL 사이의 모델 관례이지 전체 실제 실행 순서가 아닙니다.
5. GTC의 taker 가능성을 고려하면 기존 maker-only 비용 가정의 수익이 오히려 낮아질 수 있습니다.

합성 예시: 500달러 명목에 코드의 maker 0.02%와 taker 0.055%를 대입하면
수수료는 0.10달러와 0.275달러, 차이는 0.175달러입니다.
이는 현재 거래소 개인 계정의 요율이나 전략 수익 전망이 아니라 비용 민감도 예시입니다.

새 진단 모듈은 실제 체결·성과·intrabar 경로를 생성하지 않고
UNKNOWN·REVIEW_REQUIRED를 표시합니다. 갭 시가도 체결가가 아닌 비교 참고값입니다.
기존 core/backtest/shadow/swing 전략 코드는 변경하지 않았습니다.

## 5. 남은 한계·운영 전 조건

- TP ID만 있고 원래 allocation snapshot이 없는 기존 상태는 자동으로 귀속하지 않습니다.
  배포 전 legacy 보유·pending·TP/SL 상태를 읽기 전용으로 확인해야 합니다.
- 비정상·불완전·상충 broker 응답과 모르는 외부 감축은 계속 보수적으로 막습니다.
- 추가 진입 receipt commit 뒤 이전 TP에 더 늦은 체결이 끼는 복잡한 경우에는
  별도의 exact 복구가 필요할 수 있습니다. 수량을 역산해 맞추지 않습니다.
- 실제 수수료·펀딩·MTM NAV의 완전한 백테스트 패리티와 6개 시간대 비교는 남아 있습니다.
- 공통 위험 예약·직렬화는 이번 범위가 아닙니다. 이전 합산 한도·슬리피지 질문도 임의로 확정하지 않습니다.
- 실운영 성과나 자연 발생 native TP/SL 체결을 이번 합성 테스트로 대신하지 않습니다.
- 출금·이체·시험 주문·실자금 전환·app-server 작업·cron 변경은 하지 않습니다.

## 6. PR 승인과 반영 순서

이 작업은 기존 native SL PR #662 위의 후속 변경입니다.
사용자가 완료 후 관련 PR을 승인하겠다는 의사를 표시한 내용은 확인했습니다.
단, 대화의 승인 의사와 GitHub의 필수 리뷰 기록은 구분합니다.
self-approve, 관리자 우회, branch-protection 변경을 하지 않습니다.

승인·CI 조건을 충족하면 #662를 먼저 병합하고 후속 PR의 base·최종 diff·CI를 다시 확인합니다.
실제 demo 배포 전 legacy 주문 상태와 진행 중 프로세스를 확인하고,
병합·배포·자연 체결 관측을 각각 별도 근거로 남깁니다.
