# BTC 잔여 위험 교정과 수익 개선 입증 계약

## 이번에 해결한 범위

### 메인 청산 대기

체결·주문 이력의 pagination을 끝까지 확인합니다(최대100페이지).
실패·순환 cursor·잘못된 응답은 unknown이며 체결0건으로 해석하지 않습니다.
서로 연결되는 주문/체결 정체성과 중복 체결량도 확인합니다.
제출24시간 이내 의도에 대해 완전한 체결조회가0건이고 정확히 연결된 주문 이력이
Rejected/Cancelled 및 cumExecQty=0을 확인할 때만 보류를 해제합니다.
장부와 기존 스탑은 그대로 유지하며 같은 tick에 새 주문을 내지 않습니다.
부분체결·응답 유실·오래된 이력은 여전히 보수적으로 보류합니다.

### 스윙 보호와 정산

조회 실패/비정상 수량을 flat으로 해석하지 않습니다. 보호주문은 Market 유형,
방향·수량·트리거·positionIdx·주문 ID를 확인합니다. 조건부 지정가는 충분한
stop-market 보호로 인정하지 않습니다. 스탑이 없으면 기존 주문을 취소하지 않고
Full SL을 설정하며, 더 타이트한 스탑은 유지합니다. 반환 ACK만이 아니라
실제 생성된 보호주문 ID까지 조회해 저장합니다.

flat인데 exact closedPnl 정산이 없으면 청산대기로 저장하고 신규 스윙 진입을
차단합니다. 미확정 손익은 일반 거래 성과나 NAV에 넣지 않습니다.
정확한 주문 ID의 정산이 나중에 도착하면 재시작 후에도 다시 확인합니다.
시장가 reduce-only 요청은 자동 재시도하지 않습니다.
청산 client orderLinkId를 제출 전에 저장합니다. 명확한 검증/감축규칙 거절은
포지션이 그대로임을 재확인한 후 다음 tick 재시도를 허용합니다. 그 밖의
취소/거절은 주문 이력과 체결0건 증거를 대조합니다. 불명확 timeout은 중복
주문을 내지 않으며 HALTED 상태를 저장하고 운영 채널에 상태별 경보를 보냅니다.
이미 스탑을 침범한 부분체결 잔량에 미확인 청산이 겹치면 외부 확인이 필요하며,
이 예외까지 완전히 자동 해결했다고 주장하지 않습니다.

## 복구한 연구 데이터

로컬 btc_market.db의30m 실행 공백을 거래소 원본으로 복구했습니다.
실제 누락1,249개를 추가하고, 과거 미확정으로 남은2개를 원본으로 갱신했습니다.
기존 확정 봉은 덮어쓰지 않았습니다. 복구 후 연속성 공백0개,
스윙 기준선 거래 수187→189건을 재현했습니다.
연구 재생의 누적 +155.97%는 비용·순서·NAV 교정이 모두 끝난 검증 성과가 아니므로
승격 근거로 사용하지 않습니다. 거래 수 일치는 전체 가격·체결 패리티의 증명이 아닙니다.

재현 명령(로컬 연구 DB 전용):

```sh
PYTHONPATH=prism-btc .venv-bt/bin/python -m analysis.repair_execution_gaps --db prism-btc/state/btc_market.db
```

--apply를 명시한 경우에만 복구하며, 모든 필요한 데이터를 검증한 뒤 DB transaction으로
반영합니다. 불완전 응답이면 쓰지 않습니다. 5,000봉 초과 복구는 별도 검토합니다.

## 수익 개선을 입증하는 순서

### A. 비교를 허용하는 사전 조건

1. 모든 사용 TF의 연속성·확정시각·OHLCV·중복 검사, 데이터 hash/범위 manifest.
2. 변경 없는 기준선의 진입·청산·수량·수수료·펀딩을 exact 비교.
3. event-time 펀딩, 진입 전 봉 극값 제외, 갭 체결, 주문지연·부분체결 모델.
4. 공통 자본의 realized+unrealized-fees-funding NAV로 MTM 최대낙폭 계산.
5. 메인·스윙 gross/stop heat/예약 한도를 양방향 동일 적용.
6. 주문수락 뒤 응답 유실, 부분체결, 재시작, 스탑 거절의 fault injection.

하나라도 미완료이면 profitability_gate의 INSUFFICIENT입니다.

### B. 사전등록 실험

- 진입 조건은 먼저 고정하고 트레일만 한 계층씩 바꿉니다.
- trail 기준:30m/1h/4h/12h/1d/1w, 평가·집행 주기:5m/10m/30m를 분리합니다.
- 18개 조합과 기준선을 비교하되 데이터가 없는 조합은 보간하지 않고 MISSING입니다.
- 활성 R·ATR 배수·MA 길이를 동시에 대규모 탐색하지 않습니다. 추가 시도는
  trial registry에 전부 기록하고 불리한 결과도 남깁니다.
- 메인 단독/스윙 단독/공동 포트폴리오를 각각 보고합니다.
- 역사적 2020~2026 데이터는 이미 반복해서 봤으므로 진정한 untouched holdout이라
  부르지 않습니다. 과거 nested walk-forward는 탐색적 검증으로 분리합니다.
- 후보와 코드·데이터·비용 계약을 동결한 뒤 이후 forward 기간을 진짜 holdout으로 씁니다.

### C. 승격 검토 기준(운영 활성화 아님)

analysis/profitability_gate.py는 아래 계약을 fail-closed로 평가합니다.

- 역사적 OOS 거래60개 이상, 이후 확정 forward 거래30개 이상.
  이는 최소 운영 gate이며 통계적 검정력을 보장하는 숫자는 아닙니다.
- 동일 자본·비용 기준 순수익 증가, paired 일/주 수익률 차이의95% 신뢰구간 하단>0.
- bootstrap은 시간 블록을 사용하고 여러 후보를 탐색한 만큼 다중검정 보정을 합니다.
- 후보 MTM MDD가 기준선보다 나빠지지 않아야 합니다(양수 크기로 입력).
- 수수료·슬리피지2배 스트레스에서 기대수익>0.
- 적어도3개 OOS 분할 중2/3 이상 양수. 특정 사건·대형 수익1건 의존도를 별도 공개.
- 상위 추세 수익 보존율, 손익비, PF, 기대R, 노출시간, turnover, 청산 지연도 함께 보고합니다.

모든 조건을 통과해도 반환값은 REVIEW_READY이며 auto_activate=false입니다.
입력 evidence 자체의 진위는 독립 검토가 필요합니다. gate는 성과 계산기가 아닙니다.
표본·기간이 부족하면 기다립니다. 통과시키려고 기준을 사후 완화하지 않습니다.

## 관측 계약

ClickStack에는 intent_id→order_ref→exec_id→position_id→settlement_id와
각 event_time/observed_time/code_version/policy_id/data_hash를 연결해야 합니다.
ACK는 fill이 아니며, 미확정은 MISSING입니다. candidate/live/shadow의 ID는 분리합니다.
스탑 제안·수정 ACK·재조회 확인·실제 체결·최종 비용/펀딩과 MFE/MAE를 기록합니다.
0포지션/0거래는 heartbeat로, 수집 실패는 별도 실패로 구분합니다.
현재 배포된 exit snapshot만으로 이 계약 전체를 만족하지는 않습니다.

## 남은 위험과 작업

위험을 완전히 없앴다고 주장하지 않습니다. 부분체결 잔량 자동 처리,
정체성이 사라진 주문의 복구, 최초 진입 직후 보호 공백, 기존 통합 스탑 취소/교체,
양방향 합산 한도·동시실행 잠금, 메인/스윙 공통 재생기, event-time 펀딩·MTM NAV,
ClickStack exact chain과 수집 품질 알림은 계속 보완해야 합니다.
트레일 파라미터·위험 배수·cron은 이번 변경으로 바꾸지 않습니다.
수익률 개선은 아직 입증되지 않았으며 이 문서는 입증 절차와 거절 기준을 고정합니다.
