# BTC 단타 모드: 50% 선익절·잔량 추세 추종 계약

작성일: 2026-09-06 KST
범위: **M4.1 오프라인 청산·확인 주기 정책 후보**.
상태: 순수 정책 구현·로컬 단위/회귀 검증 완료. 운영 단타는 비활성입니다.
실제 신규 진입, SHADOW/DEMO 활성화, 운영 주기 변경과 수익성 입증은 이 문서의 완료 범위가 아닙니다.
기준선: main 6dc33ea4, 기존 메인·스윙 전략은 그대로 보존합니다.

## 1. 사용자 요구

- 30분봉 급등락 기회를 포착하고 1시간·4시간봉의 배경을 보고 진입 가능성을 판단합니다.
- 단타는 첫 목표에서 **최초 확정 체결 물량의 50%**를 빠르게 익절하는 것이 기본입니다.
- 배경 추세가 좋으면 나머지를 추가 분할 청산하며, 작은 잔량은 더 먼 추세를 추적합니다.
- 수익을 더 추구하면서도 SL을 유리한 방향으로만 이동해 반납을 제한합니다.
  롱 SL은 올라가고 숏 SL은 내려갑니다.
- 포지션을 보유한 동안 평소보다 자주 확인하며, 전량 청산 이후에도 잔여 주문 정리까지 확인합니다.
- 위험한 자리에서는 짧은 TP/SL을 선호합니다. 다만 구체적 계좌 위험 예산,
  SL·TP 거리, 보유 연장 시간, 체크 주기의 수치는 아직 지정하지 않았습니다.

50%는 목표 주문의 수량 규칙이지 매 거래에서 50% 익절을 보장한다는 뜻이 아닙니다.
TP 전에 SL이 체결되면 먼저 손실을 제한합니다. 가격 접촉·주문 ACK는 익절 완료가 아닙니다.

## 2. 기존 전략과 분리할 이유

현재 메인은 4시간봉 확정 기반 진입과 약 1/3 TP1, 잔량 보호/트레일을 사용합니다.
스윙도 4시간봉 진입과 일봉 배경을 사용합니다. 이 규칙을 단타의 50%로 덮어쓰지 않습니다.

단타 후보의 시간대 역할은 다음처럼 분리합니다.

- 배경: 1h/4h의 추세, 지지·저항, 과도한 이격을 판단합니다.
- 기회: 30m의 가격·거래량 급변을 포착합니다.
- 진입: 1m/5m 또는 실시간 관측으로 시점을 정합니다. 구체적인 추격/반전 조건은 미정입니다.
- 청산: 거래소 TP/SL과 가벼운 포지션 관리 판단을 사용합니다.
- 연구: 당시 이용 가능했던 데이터만 재생합니다. 진행 중 봉에 미래의 확정 OHLC를 대입하지 않습니다.

이번에는 **진입 신호를 새로 만들거나 과거 최고 수익 조합을 고르지 않습니다**.
청산 정책의 독립 계약을 먼저 검증하며, M0/M1/M2를 건너뛰어 M5/M6로 승격하지 않습니다.

## 3. 오프라인 청산 정책

### 고정된 TP 수량

진입 체결 정산을 마친 한 캠페인의 최초 수량을 정수 lot으로 동결합니다.
첫 목표의 quota는 그 수량의 절반이며, 매 확인 시점의 잔량에서 다시 50%를 계산하지 않습니다.
추가 TP는 명시한 수량·가격만 사용하고, 나머지는 runner로 남깁니다.
50/25/25 같은 추가 비율을 운영 기본값으로 임의 확정하지 않습니다.

- TP1 체결량 0이면 가격이 목표를 넘었어도 TP1 완료가 아닙니다.
- 일부만 체결되면 이미 체결된 수량을 빼고 미체결 quota만 남깁니다.
- 정산된 비TP 감축은 별도로 유지하며, TP 체결로 바꾸어 기록하지 않습니다.
- 남은 TP 전체 수량은 현재 잔량을 넘을 수 없습니다.
- v0는 정확한 50%를 표현할 수 없는 홀수 lot이나 최소 수량 미달 계획을 거절합니다.
  수량을 올려서 맞추지 않습니다. 실제 부분 진입이 홀수 lot이어도 보호를 미루면 안 됩니다.
  **기존 native SL로 즉시 보호하고, 정산·수량 정책을 해결한 뒤 단타 계획을 붙여야 합니다.**

### 작은 잔량을 길게 보유하는 조건

잔량이 작아졌다는 이유만으로 시간을 늘리거나 먼 목표로 바꾸지 않습니다.
**확정 TP1 quota 소진 + 명시적인 배경 추세 허용**이 함께 있어야 runner의 더 넓은
추적 폭을 선택할 수 있습니다. 손절·수동 감축으로 잔량이 작아진 것은 같은 근거가 아닙니다.

원래 확정 SL보다 불리한 스탑을 제안하지 않습니다.
넓은 runner 추적 폭으로 바꿔도 현재 SL을 되돌리지 않고,
새로운 고점/저점이 쌓일 때부터 그 폭을 적용합니다.
기존 확정 스탑 침범이나 최대 보유시간은 청산 의도를 우선합니다.
더 긴 보유시간 자체는 명시적 정책 입력이며, 잔량이 작다고 무기한 연장하지 않습니다.

정책 출력은 목표 상태/청산 의도일 뿐 주문·체결·실현손익이 아닙니다.
실제 주문 수량·가격 tick, 최소 주문금액, 실행 중 취소/변경, 중복 execution,
과거 상태 복구는 후속 어댑터가 검증해야 합니다.

## 4. 위험한 자리의 짧은 SL을 해석하는 방법

“변동성이 클수록 SL을 무조건 더 좁힌다”는 자동 규칙으로 만들지 않습니다.
짧은 SL이 시장의 평소 잡음·스프레드보다 작으면 잦은 손절로 비용만 늘어날 수 있습니다.

후속 진입 모듈의 필수 조건:
1. 틀렸다고 판단할 가격과 비용·슬리피지 버퍼를 먼저 계산합니다.
2. 짧은 목표의 기대 가격 차이가 왕복 비용 스트레스를 감당하지 못하면 거래하지 않습니다.
3. 수량은 손절 기준 위험 한도뿐 아니라 **독립적인 최대 수량/명목 노출 한도**로도 제한합니다.
   SL을 좁혔다는 이유만으로 주문 크기나 레버리지를 자동 확대하지 않습니다.
4. 그 경계 안에서 실행하기 어려운 급변·유동성 부족·오래된 데이터는 진입을 건너뜁니다.
5. SL은 손실 상한 보장이 아닙니다. 갭·슬리피지·수수료를 포함한 손실 스트레스를 별도로 검사합니다.

이번 청산 정책에는 신규 주문 수량 계산이나 위험 예산 기본값을 넣지 않습니다.
위 항목은 **미구현 후속 진입 계약**이며 구현 완료로 보고하지 않습니다.

## 5. 보유 중 더 자주 확인하는 방법

필요합니다. 다만 **자주 관측하는 것과 매번 주문을 바꾸는 것은 다릅니다**.

권장 구조:
- 1h/4h 배경은 새 유효 데이터가 생겼을 때 갱신합니다.
- 가격·체결 이벤트는 가벼운 코드로 처리하고, 매번 LLM을 호출하지 않습니다.
- 확인 주기는 유휴보다 보유/주문 대기 중에 짧게 합니다.
- 포지션 0이어도 TP/SL 취소나 정산이 미확정이면 빠른 확인을 유지합니다.
- 보호 미확인·조회 불명 상태는 긴 유휴 주기로 내려가지 않습니다.
- SL은 유효한 최소 가격 개선과 주문 상태 확인이 있을 때만 변경합니다.
  변경 중에는 새 변경을 겹쳐 보내지 않고, 기존 보호를 먼저 취소하지 않습니다.
- WebSocket 누락·재연결 후에는 REST snapshot/실행 원장으로 맞춥니다.
- API 한도·재시도 backoff를 지킵니다. 긴급 상태라는 이유로 무제한 조회하지 않습니다.

주기 후보 예시는 유휴 30~60초, 보유 5~10초 및 체결 이벤트 즉시 처리입니다.
이는 **연구·부하 검증용 예시이며 현재 cron이나 운영 기본값이 아닙니다**.
기존 10분 runner 전체를 이 속도로 반복하는 대신 시장 수집/분석과 포지션 관리를 분리해야 합니다.
새로운 병렬 주문 작성자를 추가하지 않고 계정별 단일 집행자·공통 잠금을 사용해야 합니다.

Bybit는 private execution stream에 orderId, execId, 체결 수량·가격·수수료를 제공합니다.
한 메시지에 여러 체결이 들어올 수 있으므로 모두 정체성에 맞춰 중복 없이 정산해야 합니다.
[공식 Execution 문서](https://bybit-exchange.github.io/docs/v5/websocket/private/execution)

Bybit 주문 변경 ACK는 비동기 접수이지 최종 변경 확인이 아닙니다.
[공식 Amend Order 문서](https://bybit-exchange.github.io/docs/v5/order/amend-order)

데모의 private stream은 stream-demo.bybit.com, public 시장 데이터는 stream.bybit.com입니다.
데모에서는 WS Trade가 지원되지 않으므로 이를 주문 제출 채널로 설계하지 않습니다.
[공식 Demo 문서](https://bybit-exchange.github.io/docs/v5/demo)

조회·주문 갱신은 계정/엔드포인트 한도와 응답 헤더를 반영해야 합니다.
[공식 Rate Limit 문서](https://bybit-exchange.github.io/docs/v5/rate-limit)

## 6. 기존 포지션과 섞기 전 필수 조건

- M1 공통 위험 예약에 메인·스윙·단타의 실제 보유와 미체결 위험을 모두 넣습니다.
  현재 공통 계산 코어는 main/swing만 받아들이므로 단타 이름만 추가한다고 완성되지 않습니다.
- 같은 Bybit one-way BTC 포지션은 거래소에서 합쳐질 수 있습니다.
  strategy_id만 나눈다고 거래소 SL의 소유·수량이 분리되는 것은 아닙니다.
- 별도 계정 구조 또는 단일 통합 집행자의 트랜치 배분 계약을 확정해야 합니다.
  이 작업에서 계정·키를 만들거나 기존 계정의 스탑을 단타가 덮어쓰지 않습니다.
- 빠른 루프와 기존 느린 루프가 동일 주문을 동시에 만들지 못하도록
  예약·잠금·orderLinkId·execution 원장·재시작 복구를 함께 검증합니다.
- 실패했을 때는 신규 진입을 제한하되 기존 거래소 보호를 유지합니다.
