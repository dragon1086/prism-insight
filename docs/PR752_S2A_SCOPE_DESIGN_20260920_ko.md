# S2a 설계: 내부 회계정책 제목의 명시적 범위 접두어

상위 PRD R1/R2, S1의 실제 원문 capture/replay 결과에 근거합니다. 다른 표·대형 문서·선택 알고리즘·매매 규칙은 변경하지 않습니다.

## 실제 실패 증거

- 기본 주석: receipt 20260813000255, 706,830바이트, SHA-256 `7e834191d788bfd3331ce7fe40bd78f137ffc2f0bf3127962385f64aa98d0ec6`.
- 연간 주석: receipt 20260312000217, 1,193,596바이트, SHA-256 `bc89dd05511d5a9d008f9759cbf7a3541f8dfec0d4b5645cb887896d48245259`.
- 두 원문 모두 `/html/body/p[2]`에 `3. 연결재무제표 주석`, `/html/body/p[5]`에 `2. 연결재무제표 작성기준 및 중요한 회계정책 (연결)`이 있습니다.
- 현재 파서는 회계정책 제목 앞의 `연결`을 인식하지 못해 level 3으로 처리하고 notes/scope를 초기화합니다. 이후 기본 424개, 연간 484개 기록이 모두 unknown이고 보고서 주석 후보가 없습니다.
- 원문은 S1 private fixture에서 검증한 동일 바이트이며, 전체 수집/보고서 요약도 network-free replay로 일치했습니다.

## 일반 규칙

1. `_ACCOUNTING_NOTE`의 좁은 작성기준/작성의 기초 문법에 선택적 명시 범위 접두어 `연결` 또는 `별도`를 허용합니다. 회사명·종목코드 분기는 넣지 않습니다.
2. 이미 확인된 상위 주석 범위가 있을 때만 내부 제목으로 유지합니다. 상위 범위가 없으면 접두어만으로 새 범위를 추정하지 않습니다.
3. 접두어와 기존 괄호 접미어 각각을 상위 범위와 비교합니다. 하나라도 충돌하면 level 3/unknown으로 끊고, 뒤의 일반 주석도 임의로 복구하지 않습니다.
4. 실제 최상위 `4. 재무제표`, `5. 재무제표 주석` 전환은 유지합니다. 장식된 미지원 최상위 제목이나 좁은 회계정책 문법에 맞지 않는 재무제표 제목도 기존 보수적 경계를 유지합니다.
5. 수치·문장·단위·각주·절 순서·원문 XPath는 변경하지 않습니다. 수정 대상은 제목 계층과 scope 상태입니다. 미지원 중첩 표를 이번 수정으로 해결했다고 표시하지 않습니다.

## 변경 파일

- `prism_core/filing_html.py`: `_ACCOUNTING_NOTE`의 범위 접두어와 reducer의 접두어/접미어 충돌 검사.
- `tests/test_filing_html_note_scope.py`: 일반화된 양방향 정상·충돌·상위 범위 부재·최상위 경계 회귀.
- `prism_core/report_insight_prefetch.py`: 파서 revision을 변경하여 이전의 scope 탈락 cache를 재사용하지 않도록 합니다.
- 신규 결과 기록: 같은 fixture에 대한 전후 scope/후보/최종 전달·위치 검증 결과. 원문 자체는 커밋하지 않습니다.

## 실패 테스트와 합격 조건

- 연결/별도 부모와 일치하는 접두어 및 접미어: 내부 주석 계층과 부모 범위를 유지합니다.
- 접두어만 충돌, 접미어만 충돌, 접두어/접미어 상호 충돌: unknown이며 다음 일반 주석까지 잘못 상속하지 않습니다.
- 부모 없는 회계정책 제목, 미지원 장식 제목, 실제 최상위 전환: 이전 보수적 동작을 유지합니다.
- 문장·표 값·단위·조건·원문 hash/위치가 변하지 않습니다. 테스트는 실제 회사 이름을 사용하지 않는 합성 문서로 고정합니다.
- 저장된 두 실제 주석에서 scope 복구와 최종 전달을 측정합니다. 이전 parser 결과와 raw hash·레코드 text/kind/path를 대조하고, 독립 full DOM 원문 위치 검사를 수행합니다. 네트워크 재조회는 하지 않습니다.
- capture의 초기 요약은 삭제/수정하지 않습니다. 수정 후 replay의 summary_equal이 false가 되는 것은 의도한 결과이며, 동일 원문에서 바뀐 필드와 최종 budget을 별도 결과로 명시합니다. 전체 요청이 같고 모두 소비됐는지는 유지해야 합니다.
- 기존 고정 3개 HTML 회귀·주석/표/streaming·report wiring을 다시 실행합니다. 전달 수 증가를 중요 사실 회수나 실제 모델 품질 합격으로 확대하지 않습니다.

## 검증·피드백·원복

설계 리뷰 → 실패 회귀 → 구현 → 관련 전체 회귀 → 독립 코드 리뷰 → 동일 fixture 전후/원문 위치 검증 순서입니다. 차단 지적은 수정 후 다시 검증합니다. 조건·범위가 잘못 붙는 반례가 나오면 이 좁은 변경을 원복하고 기존 미지원 상태를 유지합니다. cache revision 외 운영 설정·매매 정책은 변경하지 않습니다.
