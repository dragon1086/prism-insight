# BTC 공개 시세 제한 오류의 좁은 재조회

## 확인된 근거

PR #892 배포 후 10/04 00:40 KST 모델 판단은 검증된 WAIT로 완료됐다.
00:45 실패는 새 감사 기록에서 `snapshot_collection`으로 분리됐으며 같은 실행 로그에
Bybit 공개 시세 API의 `retCode=10006`이 있었다. 그 뒤 공개 시세만 읽는 제한된 점검은
0.772초에 valid=True로 성공했다. 모든 과거 일반 오류를 같은 원인으로 소급 확정하지 않는다.

[Bybit 공식 rate-limit 문서](https://bybit-exchange.github.io/docs/v5/rate-limit)는
10006을 API 호출 제한으로 정의한다. 같은 문서의 HTTP 403 제한은 즉시 재시도 대상이 아니다.

## 변경 범위와 조건

M0 입력 가용성 보완이며 전략·프롬프트·계좌·주문·위험 한도 변경이 아니다.
기존 `_get_klines` 공용 호출자의 기본 동작은 보존한다. 시나리오 시세 수집만 별도로
10006 응답에 한해 최대 3회(재시도 2회), 1초·2초 대기 후 공개 GET을 다시 요청한다.
HTTP 403, 다른 오류코드, 네트워크 예외까지 무차별로 재시도하지 않는다.
계속 제한되면 고정 코드 `public_rate_limited`를 기록하고 새 판단을 건너뛴다.

전체 수집 60초 한도·수집 중 봉 경계 교차 거부·입력 120초 신선도 조건은 그대로다.
과거 캐시를 현재 시세로 대체하거나, 입력을 못 얻었는데 LLM/주문을 실행하지 않는다.
이 대기는 기존처럼 거래소 변경 잠금 밖에서 수행하며 보호 루프를 멈추지 않는다.

## 검증 계약

### 후모델 잠금 대기 창의 운영 보정

00:50 자연 실행에서 제안 입력 시각은 :10.43, lock_busy 종료는 :25.17,
독립 보호 점검 완료는 :29.56이었다. 보호 cron은 매분 15초 뒤 시작한다.
보호 점검이 약 14.5초 걸린 관측에서 PR #892의 8초 대기는 먼저 끝났다.
따라서 획득 대기만 최대 20초로 늘린다. 보호 작업은 대기 동안 계속 잠금을 소유하며,
120초 입력 신선도·제안 만료·획득 후 재대조는 그대로 유지한다.
9초/14초 경합 후 획득 성공, 20초 지속 경합의 안전 종료를 별도로 검증한다.
모든 경합 해소나 연속 무중단을 보장하지 않으며 cron·주문·잠금 본문은 바꾸지 않는다.

- 10006 후 정상 응답의 실제 collector → collect_snapshot → runtime 경로.
- 지속 제한의 3회 상한과 정확한 대기 간격, 고정 오류 진단, LLM·주문 없음.
- HTTP 403·다른 응답 오류·전송 실패의 즉시 중단.
- 기존 호출자의 기본 동작 보존, 수집 지연·봉 경계·입력 노후 거부.
- 정확한 head 전체 격리 테스트·CI·운영 Python 검증 뒤 clean/ff-only 배포.
- 자연 예약 실행 성공과 실제 10006 재시도 회복 관측은 분리한다. 통과한 격리 테스트를
  미래 API 가용성 또는 수익성 보장으로 표현하지 않는다.
