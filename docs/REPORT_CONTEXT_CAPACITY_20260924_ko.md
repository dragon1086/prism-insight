# 보고서 → 매매 에이전트 입력 용량 점검 (2026-09-24)

## 결론

30쪽이라는 페이지 수만으로 용량을 판단하지 않는다. 현재 후보 PDF는 한국어 BUY 초기 입력에 전체가 들어갔고 마지막 문단도 유지됐다. 다만 **100만 토큰 설정은 확인되지 않았다.** 확인된 Codex 모델 목록은 `gpt-6-astra`, `gpt-5.6-sol` 모두 272,000 토큰, 유효 비율 95%였다. 이 값은 해당 설치의 캐시 메타데이터이지 모든 제품 경로의 보편적 보증은 아니다.

총괄 에이전트가 직접 열어 확인한 [OpenAI 공식 GPT-6 Astra 모델 문서](https://developers.openai.com/api/docs/models/gpt-6-astra)는 API 컨텍스트를 **1,050,000토큰**으로 안내한다. 이는 이 서버의 Codex 실행 경로가 현재 그 전체 크기로 설정됐다는 뜻은 아니다. 공식 제품 사양과 운영 설치의 모델 메타데이터를 구분해야 한다.

## 실제 후보 측정

대상은 배포 승인 전 `SKT_DART_DEPTH_CANDIDATE_20260923.pdf` 30쪽이다. 숫자 오류가 남은 당시 후보를 **용량 측정에만** 사용했으며 내용 정확성을 승인한 것이 아니다.

- 실제 `pdf_converter.pdf_to_markdown_text` 추출: **63,562자 / UTF-8 121,964바이트**.
- 실제 한국어 BUY 사용자 프롬프트: **64,149자 / 122,551바이트**.
- 실제 한국어 BUY 시스템 지침: **18,874자 / 32,530바이트**.
- 합계: **83,023자 / 155,081바이트**.
- 영어 지침으로 같은 PDF를 넣으면 합계 92,356자 / 151,160바이트였다.

기존 가상 계정 초기화 테스트를 이용해 실제 `_extract_trading_scenario`까지 실행했다. 시세·모델 응답은 대체했고 네트워크, 실제 계정, 주문은 차단했다. Codex 실패 후 기존 LLM으로 넘어가는 경로에서도 동일한 전체 보고서와 마지막 300자가 전달됐고 외부 호출 시도는 0건이었다. 포트폴리오는 비어 있고 매매일지·시장 자료는 제한된 테스트 입력이므로 이 수치는 운영 최대치가 아니다.

로컬 공유 가상환경과 DB Python에 `tiktoken`이 없어 정확한 토큰 수는 측정하지 않았다. 새 의존성을 설치하지 않았으며 문자 수를 토큰 수라고 부르지 않는다. 바이트 기반 BPE라면 위 문자열 부분의 보수적 상한은 155,081토큰으로 볼 수 있다. 272,000 × 95% = 258,400과 비교하면 103,319의 차이가 있으나 **메시지 프레이밍, 도구 정의·결과, 추가 운영 문맥, 출력과 후속 턴은 이 계산 밖**이다. 따라서 실제 전체 호출의 잔여 토큰을 보증하는 수치가 아니다.

## 최종 PDF 재측정

2026-09-24 최종 산출물 `SKT_REPORT_UPGRADE_20260924.pdf`는 **30쪽**이다. SHA-256은 `0d2975fd7fdb90e2bda20ab82160e6f1062ada7f6f56795ef47135e764e97425`다. 이전 후보와 구분해 실제 한국어 BUY 경로를 다시 측정했다.

- PDF 추출 전문: **63,783자 / UTF-8 121,072바이트**.
- BUY 사용자 프롬프트: **64,370자 / 121,659바이트**.
- BUY 시스템 지침: **18,874자 / 32,530바이트**.
- 합계: **83,244자 / 154,189바이트**.
- Codex 정상 응답 경로와 Codex 실패 후 기존 LLM fallback 경로를 각각 실행했고 **모두 종료 코드 0**이었다. 두 경로 모두 전문과 마지막 300자를 그대로 받았으며, fallback 전후 사용자 프롬프트가 동일했다.
- 실제 모델 응답은 대체했다. 네트워크·외부 호출 시도 **0건**, 주문 **0건**을 검사했다. 이는 실제 운영 매매 호출이 아니라 격리된 전달 경로 검증이다.

정확한 토큰 수가 아니라 바이트 기반 BPE의 문자열 상한을 사용하면 **154,189토큰 이하**에 해당한다. 운영 캐시 기준 유효 창 258,400과의 차이는 104,211이지만, 앞서 명시한 도구·메시지 프레이밍·추가 운영 문맥·출력 예약을 제외한 비교다. 전체 운영 호출의 여유 토큰으로 단정하지 않는다. 최종 PDF 전문 보존은 확인했으며, 모든 보고서의 용량 또는 내용 정확성을 이 검사로 보증하지 않는다.

## 설정 근거와 한계

- DB `/root/.codex-prism/models_cache.json`: 위 두 모델의 `context_window=272000`, `effective_context_window_percent=95`만 읽었다.
- DB `/root/.codex-prism/config.toml`: 기본 모델 `gpt-5.6-sol`; 명시적인 `model_context_window`, `model_auto_compact_token_limit` 없음.
- 로컬 Codex 모델 캐시도 같은 272,000/95 값을 제시했다.
- DB `.env`의 BUY 모델·effort·KR/US Fast 활성화 키는 미설정이었다. 점검 순간 프로세스 환경에서 해당 키를 가진 실행 프로세스는 확인되지 않았다. 별도 배치 실행 래퍼의 주입값까지 이 결과로 단정하지 않는다.
- 저장소 `prism_core/codex_config.py`의 BUY 기본 모델은 `gpt-5.6-sol`이며 명시적 환경변수로 변경된다. 보고서 집필 모델과 BUY 모델은 별개다.
- 인증 비밀값은 출력하지 않았고, 모델·용량 관련 허용 목록 필드만 확인했다.

## 경로별 보존과 제한

1. 한국 BUY: PDF 모든 페이지를 추출하고 공백만 정리한다. 시스템 지침과 별도로 보고서 전체를 사용자 프롬프트에 삽입한다. Codex와 기존 LLM fallback은 같은 프롬프트를 받는다.
2. 미국 BUY: 같은 전체 삽입 구조다. 기존 실제 PDF → 미국 BUY 테스트로 수집 한계 문구가 전달됨을 확인했다. 미국 30쪽 실제 PDF의 최대 입력을 측정한 것은 아니다.
3. Telegram `/evaluate`: BUY와 다르다. 기본 **40,000자** 한도에서 DART 장은 통째로 보존하고 일반 분석을 문단 단위로 줄인다. DART 장 자체가 한도를 넘거나 경계 표식이 깨지면 명시적으로 평가를 중단한다. 이를 40,000토큰 제한으로 혼동하지 않는다.
4. Codex 실행 래퍼: 초기 BUY 전체 입력과 도구 후속 결과를 합산한 응용단 토큰 한도 검사는 현재 없다. 모델/CLI의 오류나 축약 동작에 의존할 수 있으며 fallback 모델의 실제 컨텍스트 용량도 따로 확인해야 한다.

## 최소 후속 개선 권고

- 최종 PDF의 재측정은 위와 같이 완료했다. 이후 산출물 크기가 크게 바뀌면 반복하고, 페이지 증가만으로 모델을 바꾸거나 임의로 뒷부분을 자르지 않는다.
- 운영 실행 시 확정된 BUY 모델과 입력 길이, 가능하면 실제 tokenizer 토큰 수, 도구·출력 예약량을 함께 기록한다. 본문 또는 계정 정보는 로그에 남기지 않는다.
- 총 입력 초과 시 조용히 자르거나 더 작은 fallback으로 재시도하지 않는 명시적 입력 용량 오류를 설계한다. 모델별 한도와 실제 tokenizer를 확인한 뒤 적용하고, 이번 점검만으로 매매 정책을 바꾸지 않는다.
- 모델이 문서를 수용하는 것과 숫자·조건을 올바르게 이해하는 것은 별개다. 원문 대조와 숫자 정확도 검증은 계속 필요하다.
