# 대용량 공시 처리 개선과 보유기간 검토 방향

## 이번 결론

아모레퍼시픽 공시가 크다는 이유로 통째로 탈락하던 문제를 수정했습니다. **파싱 결과 0개 → 763개, 실제 보고서 입력 0개 → 15개**를 확인했습니다. RF·오스코텍과 함께 실제 Firecrawl 응답을 재수집해 검증했습니다. 세 문서 모두 필요한 일부 자료를 전달하지만 원문 복구·미지원 표·발췌 누락 경고가 있어 `PARTIAL`이며, 전체 사실을 독립 검증했다는 뜻은 아닙니다.

보유기간·손절·재진입·주문 비중은 변경하지 않았습니다. 이번 입증 대상은 공시 처리와 출처 보존이지 매매 성과가 아닙니다.

## ‘38,000글자 제한’의 정확한 원인

실제 실패한 저장 응답은 아모레퍼시픽 2026년 1분기 공시입니다.

- 정제 HTML: **1,738,575자 / 1,974,024 UTF-8바이트**.
- Markdown: **339,959자 / 565,566바이트**.
- HTML 구조 요소: **35,532개**, 기존 제한 **30,000개**.
- 최대 깊이: 10. body 직접 자식 1,609개 중 가장 큰 자식도 1,217노드였습니다.

즉, 38,000글자나 모델 문맥 한도 때문에 탈락한 것이 아닙니다. 작은 표·문단이 많이 쌓인 문서에 **문서 전체 노드 수 제한**을 적용한 것이 원인이었습니다. 더구나 기존 구현은 전체 DOM을 만든 뒤 제한을 검사했으므로 DOM 생성 시점의 메모리를 막지도 못했습니다.

## 적용한 방법

### 1. 한 번에 전부 붙잡지 않고 구조 단위로 읽기

HTMLPullParser로 입력을 작은 feed로 공급하고, 완료된 문단·표 등 구조 단위를 처리한 뒤 DOM을 해제합니다. 전체 이벤트 목록도 모으지 않습니다. `main`, `form`, `aside`, `header`, `footer` 같은 일반적인 감싸는 요소도 처리합니다.

전체 문서를 조각 문자열로 직렬화해 다시 파싱하는 방식은 사용하지 않았습니다. 그렇게 하면 섹션·연결 범위가 초기화되거나 조각의 경로를 전체 원문의 경로인 것처럼 잘못 기록할 수 있기 때문입니다.

### 2. 구조를 나누되 의미는 끊지 않기

섹션 경로·연결/별도·표 앞 단위와 기간·표 뒤 각주·조건 문구의 상태를 문서 전체에서 유지합니다. 물리적인 처리 경계가 문장의 의미 경계는 아닙니다.

- 표 내부는 임의로 나누지 않습니다.
- `1<span>,000</span>`은 어떤 feed 크기에서도 `1,000`으로 보존합니다.
- 닫는 태그 뒤의 텍스트가 다음 feed에 들어와도 누락하지 않습니다.
- 실패한 표의 각주를 이전 표에 붙이지 않습니다.
- 뒤늦게 중복 주요 제목이나 치명적인 한도 초과를 발견하면 일부 주장만 내보내지 않고 임시 결과를 폐기합니다.

### 3. 원문 위치를 잃지 않기

앞 DOM을 지우면 일반 `getpath()`의 형제 번호가 바뀝니다. 그래서 시작 이벤트에서 원본 기준 순번을 확보합니다. 전체 입력 해시는 그대로 유지하며, 문서 전체 기준 XPath로 연결합니다. `o:p` 같은 태그도 namespace 이름을 임의 추정하지 않고 검증된 `name()` 경로로 표현합니다.

보고서 입력에는 반복 경로 접두어를 **손실 없이 압축**합니다. 숫자·기간·단위·조건 문장을 줄인 것이 아닙니다. 원래 경로로 정확히 복원되는지 별도 검사하고, 압축·원본 두 표현이 충돌하면 거절합니다. 작아지지 않는 경우 압축하지 않습니다.

### 4. 안전 한도와 모델 예산은 유지

- 입력 2MiB, 깊이 100, 활성 구조 노드 30,000, 레코드 2,000, 개별 표 제한은 유지했습니다.
- 전체 표 확장이 누적되는 문제를 발견해 문서 전체 grid 120,000칸·원본 셀 60,000개 제한을 추가했습니다.
- 깊은 구조에서 경로 문자열이 증폭되는 문제를 발견해 문서 전체 경로 생성량도 16MiB로 제한했습니다.
- 초과 시 조건 없는 앞부분만 전달하지 않고 임시 레코드를 모두 폐기합니다.
- 최종 `section_notes`는 기존 **담당 섹션별 6,000바이트**를 유지했습니다. 모델에 거대한 원문을 밀어 넣지 않았습니다.

이 방식은 모든 크기의 문서를 무제한 수용한다는 뜻이 아닙니다. 2MiB 초과 문서는 다음 단계에서 공시 원문의 섹션별 수집으로 해결해야 하며, 비정상적으로 큰 단일 표·미지원 custom wrapper·원문 손상은 여전히 명시적으로 실패할 수 있습니다.

## 검증 결과

### 동일 저장 응답의 파서 전후 비교

기준 파서는 fe151e39의 실제 코드를 메모리에서 불러와 비교했습니다. 같은 adapter·평가기를 사용한 파서만의 A/B입니다. 기존 3개 회귀 문서이며 미사용 holdout이 아닙니다.

- RF: **1,241개 파싱 유지**, 최종 입력 7개.
- 오스코텍: **1,250개 파싱 유지**, 최종 입력 9개.
- 아모레퍼시픽: **0 → 763개 파싱**, 최종 입력 **0 → 15개**.

RF·오스코텍의 기존 파싱 내용·순서·연결 범위·표 셀은 유지됐습니다. 다만 이전 단계 전체 산출물은 입력 8개·10개였고 이번에는 7개·9개입니다. 새 경로·엔진 식별 정보까지 같은 예산에 넣으면서 일부 큰 레코드가 제외되는 차이가 남았습니다. 손실 없는 경로 압축으로 메타데이터 중복을 줄였지만, 이전 전달 개수가 모두 복구됐다고 주장하지 않습니다.

### 원문 위치와 처리 규모

별도의 전체 DOM은 **오프라인 평가용 원본 대조**에만 사용했습니다. 운영 파서의 fallback으로 쓰지 않았습니다.

- RF 16,503개, 오스코텍 13,742개, 아모레퍼시픽 21,708개의 서로 다른 원문 위치를 확인했습니다. 합계 **51,953개**, 오류 0건입니다.
- 표 좌표·병합 범위·셀 문자열·각주도 원본 문서와 대조했습니다.
- 모델 입력에 전달된 압축 경로를 다시 풀어 원래 후보와 대조한 오류도 0건입니다.
- 아모레퍼시픽은 전체 35,532노드 중 계측한 활성 노드 최대 **1,219개**로 처리했습니다. 이는 RSS나 전체 프로세스 메모리 측정값이 아니며 libxml의 feed 한 묶음 lookahead를 포함하지 않습니다.
- 저장 응답의 순수 파싱 시간은 RF 약 0.28초, 오스코텍 약 0.20초, 아모레퍼시픽 약 0.28초였습니다. 한 로컬 실행의 실측이지 지연시간 보장이나 모델 비용 측정이 아닙니다.

### 실제 공급자 재검증

새 코드로 동일한 알려진 공개 문서 3건을 Firecrawl MCP에서 재수집했습니다. 최종 실행에서 RF 7개·오스코텍 9개·아모레퍼시픽 15개가 최종 패킷에 들어갔고 각 섹션은 6,000바이트 이내였습니다. 이번 단계에서 중간·최종 공급자 검증 각 3회, 총 6회의 MCP 호출을 했으며 실패·중간 결과를 보존했습니다. 보고서 모델·주문 호출은 없습니다.

이는 기존 과거 문서의 현재 조회 검증입니다. 해당 문서가 오늘의 최신 정기공시라는 뜻이나 과거 분석 시점과 동일한 본문이라는 보증은 아닙니다.

### 회귀·공격성 입력 검사

- 1바이트·7바이트·일반 feed, UTF-8 경계, inline 숫자, 숨김 요소·주석 뒤 텍스트, 표·각주 경계, 뒤쪽 중복 제목, 일반 wrapper와 콜론 태그를 시험했습니다.
- 별도 구조 검토에서 3,000개의 고정 시드 조합을 전체 DOM 의미 해석과 비교했습니다. 관측한 차이는 없었고 navigation 처리는 더 엄격하게 제외합니다.
- 표 64개로 grid가 크게 증폭되는 반례와 깊은 구조의 빈 span 경로 증폭을 발견해 추가 한도로 막았습니다. 계측 활성 노드 수 하나만 보고 메모리가 안전하다고 판단하지 않았습니다.
- 기존 Markdown 고정 38개 항목 결과는 **8/38로 유지**됐습니다. 대용량 HTML을 읽을 수 있게 됐다는 사실을 곧바로 중요한 사실의 회수율·최종 보고서 정확도·매매 성과 향상으로 환산하지 않습니다.

연구·보고서 회귀 1,197개와 별도 공급자·PDF·BUY gate 회귀 74개가 통과했습니다. Ruff·compileall·diff 검사도 통과했고 새 테스트를 CI에 연결했습니다. 기존 KR 매매 프롬프트 hash 스냅샷 2개 실패는 앞선 기준 커밋에서도 같았던 별도 문제이며 이번 작업에서 기대값을 바꾸지 않았습니다. 모델 생성 품질, 최신 공시 선정, 큰 파일의 섹션별 수집, 새 SELL 근거 전달 등 기존 미완료 게이트도 남아 있습니다.

## 보유기간에 대한 현재 판단

**펀더멘털을 더 깊게 본다고 손실 종목의 보유기간을 늘릴 이유가 자동으로 생기는 것은 아닙니다.** 기업의 질과 진입 타이밍을 분리하는 편이 오닐식 원칙에 더 가깝습니다. MarketSmith의 공식 설명도 손실 통제와 강한 승자 보유를 구분합니다. [MarketSmith 원칙](https://www.marketsmith.hk/principles/)

좋은 기업이더라도 기존 손절 조건에 해당하면 위험을 제한하고, 이후 새로운 적절한 매수 조건이 형성되면 독립된 거래로 재평가할 수 있습니다. 이는 손절 직후의 보복성 재매수나 이전 매수가 회복을 기다리는 물타기와 다릅니다. 공식 교육 Q&A에도 성장하는 기업의 손실 통제와 조건이 다시 갖춰졌을 때의 재진입을 구분한 설명이 있습니다. [MarketSmith·IBD Q&A](https://shop.investors.com/Images/promotional/Wizards-QA.pdf)

말씀하신 평균 5일은 이번 작업에서 새로 검증한 통계가 아닙니다. 평균을 목표로 늘리거나 줄이기 전에 다음을 나눠 확인해야 합니다.

1. 수익 거래와 손실 거래의 보유기간, 거래일/달력일, 부분청산/전체청산.
2. 아직 보유 중인 승자가 제외되어 평균이 짧아지는지.
3. 손절·추세 훼손·목표가·기간 제한 중 실제 청산 이유.
4. 청산 후 추가 하락을 피한 정도와 수익을 일찍 놓친 정도.
5. 같은 종목 재진입의 당시 조건·쿨다운·비용·시장 국면. 사후 최적 시점을 골라 성과를 만들지 않기.

후속 분석은 기존 sanitized Evidence Packet 계약을 사용해야 합니다. 현재 DB 값을 과거 판단 당시 사실로 복원하거나 확인되지 않은 체결을 수익으로 세지 않습니다. 이번에는 그 성과 분석을 수행하지 않았고 보유기간·손절·재진입 정책을 바꾸지 않았습니다.

## 변경 파일과 배포 판단

변경은 `filing_html.py`, `filing_html_tables.py`, `filing_report_evidence.py`, report prefetch 두 모듈, 신규 스트리밍·압축·평가 테스트, `evaluate_large_filing_html.py`와 고정 manifest, CI에 한정됩니다. 전체 DOM/event 목록을 없애고 기존 의미 해석·표 파서를 재사용했습니다. 새로운 DB·SDK·의존성은 추가하지 않았습니다.

opt-in의 파서 revision으로 캐시를 분리하여 이전의 크기 초과 결과를 새 구현의 결과로 재사용하지 않습니다. 기본 OFF·미사용자 경로와 매매 정책은 유지합니다. 같은 Draft PR #752에 이어서 반영하며, 전체 작업이 끝났다고 보거나 운영에 배포하지 않습니다.
