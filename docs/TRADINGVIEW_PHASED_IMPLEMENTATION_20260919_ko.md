## 최신 사용자 요구

OHLCV의 지연 표시만으로 TV를 부적합하다고 배제하지 않는다. KIS/yfinance도 포함하여
같은 용도·판단시점·완료봉·수정주가 기준에서 실제 지연과 결측을 비교한다.
모든 공급자의 지연이 같다고 가정하는 것도 금지한다.
기본 OFF이며 사용 옵션을 명시적으로 켠 경우에만 작동해야 한다.
보고서는 매매 판단에 큰 영향을 주는 핵심 입력이므로 스크리닝 개선 뒤로 품질 검증을 미루지 않는다.

## 단계와 완료 판정

각 phase는 PRD → 설계 → 테스트 → 구현 → 검증 → 독립 리뷰 → 피드백 수정 → 재검증으로 진행한다.
테스트 통과, 실제 공급자 검증, 소비 경계 통합, 배포, 정규 배치 관측은 별도 상태다.

1. **P0 요구사항과 경계:** 최신 사용자 요구·기존 코드 경로·단계별 수용 기준 고정.
2. **P1 시점 품질 모듈:** 공급자 중립 관측 계약. 지연 자체가 아닌 용도별 적합성 평가.
3. **P2 선택형 수집 모듈:** 기본 OFF, 순차 공용 읽기, 호출·시간·바이트 예산과 실패 격리.
4. **P3 실제 연결·필드 검증:** 무인 OAuth·권한·실제 스키마·KR/US 동일 기준 응답 확인.
5. **P4 자료 선택:** 최신 공시·실적·사건·가격 정보의 출처/기간 검증과 제한적 재수집.
6. **P5 보고서·BUY·SELL:** 서술과 감사 기록 분리, 요약/PDF/실제 매매 입력 연결 검증.
7. **P6 스크리닝 대조:** 기존 후보·순위 보존하에 같은 시점/모집단 대조 후 변경 타당성 평가.
8. **P7 릴리스 검증:** OFF 동등성, ON 실패 복구, 정확한 HEAD CI, 운영 권한·스모크·첫 배치.

## 기존 전략과의 관계

초기 P1/P2는 경제적 매매 판단을 변경하지 않는 독립 기반 모듈이다.
매매 후보·점수·국면·손절·주문·비중 변경 및 운영 hook 없음.
P5/P6에 들어가기 전 실제 screening → report → BUY → gate → order → SELL을 같은 후보로
검토하고 `TRADING_CHANGE_REVIEW_HARNESS.md`의 여섯 항목을 확장한다.

검토 가설은 정보 결측/시점 오류가 줄면 판단 입력이 개선된다는 것이다. 실제 수익 개선은 미입증이다.
동일 자료에서 해석을 검증하며, 수집 실패가 기존 정상 후보를 탈락시키거나 같은 근거가
보고서와 보강 입력에서 중복 가점되면 실패다. 검증 전 기존 경로를 유지한다.
초기 모듈 롤백은 호출되지 않는 신규 파일 제거이며 운영 설정/데이터 복구가 필요하지 않는다.

## 피드백 반영 기록

- 아키텍처 검토: 기존 TV 정규화기는 임의 screener 열을 모두 보존하지 않는다.
  P2 수집 성공을 풍부한 스크리닝 데이터 통합 완료로 부르지 않는다.
- 기존 연구 cache는 일자 단위다. P1/P2에 재사용하지 않으며 P3 이후 캐시는 정확한
  판단 경계·도구 인자·정책 버전·권한을 포함해야 한다.
- 기존 `usable_for_report`는 수집 자료 존재 의미다. 시간 적합성이나 사실 인증과 구분한다.
- 보호매도 경로 앞에 신규 TV 대기를 추가하지 않는다.

## 상태

P0: 초기 계획은 시각 판정식·예산 수치 부족으로 검토에서 반려됐다. 필드·판정식·우선순위·
한도와 실패 처리를 명시한 뒤 P1/P2 설계 승인을 받았다.

P1: `prism_core/source_observation_quality.py` 구현. `tests/test_source_observation_quality.py`
50개 통과. 처음에는 모듈 미구현으로 RED를 확인했다. 추가 검증에서 뉴욕 DST 중복 시각을
벽시계로 비교하는 오류를 재현했고 UTC 변환으로 수정했다. 거대한 정수 입력의 OverflowError도
계약대로 ValueError로 바꾸고 회귀를 추가했다. 공급자별 고정 차별 없이 같은 지연은 같은 판정이다.

P2: `prism_core/tradingview_collection.py` 구현. `tests/test_tradingview_collection.py`
39개 통과. 기본 OFF에서는 None을 반환하고 요청 평가·transport 생성·normalizer import가 없다.
ON에서 순차 수집·제한된 공용 읽기·timeout·부분 실패·원문 전체 생략을 검증했다.
최신성·내용 확인과 수집 성공은 분리한다. 이 모듈만으로 실제 인증이나 앱의 사용 옵션이 연결되지는 않는다.

P1/P2 코드 리뷰 승인, 보안 리뷰 LOW/승인. 기존 TV 정규화 29개 포함 118개 통과.
관련 보고서 프롬프트/실제 factory/근거 전달/PDF 소비 경계를 포함한 208개 회귀도 통과했다.
Ruff 통과. Python 전용 타입 검사기는 미구성이고, TypeScript 기반 LSP의 무진단은
Python 타입 안전성 증거로 사용하지 않는다. pip-audit 미설치로 의존성 감사는 미실행이다.

P3a: `prism_core/tradingview_transport.py`에 고정 endpoint의 lazy HTTP 어댑터를 구현했다.
`tests/test_tradingview_transport.py` 32개 통과. 초기 설계는 SDK 내부 원문 로그와
자동 SSE 재연결을 놓쳐 반려됐고, 컨텍스트별 로그 정제와 프로토콜 재연결의 한계를 반영해 승인받았다.
공식 참고: [고정 MCP SDK 구현](https://github.com/modelcontextprotocol/python-sdk/blob/v1.26.0/src/mcp/client/streamable_http.py),
[HTTPX AsyncClient](https://www.python-httpx.org/api/#asyncclient).

구현 후 검토에서 인증 만료시각의 DST 오류와 호출자 오류를 공급자 오류로 바꾸는 문제가
발견됐다. 각각 실패 회귀를 먼저 만들고 UTC 비교·호출자 예외 원본 보존으로 수정했다.
실제 설치된 MCP SDK + MockTransport로 정상 수집, 잘못된 JSON/SSE, 초기화 실패,
OFF 무호출, 로그의 비밀 표식 비노출, 동시 비사용자 로그 유지, 종료/취소를 확인했다.
실제 TradingView 서버를 조회한 시험이 아니라 네트워크를 대체한 통합 시험이다.

최종 새 모듈 테스트는 50+39+32=121개, 기존 TV 정규화 29개를 포함해 150개 통과했다.
CI에 등록한 전체 연구/보고서 회귀를 같은 명령으로 로컬 실행해 **715개 통과**, 기존 경고 3건.
별도의 실제 KR/US 공급자 모양·배치 소비 회귀 **46개 통과**. 네트워크·주문 없이 실행했다.
최종 코드 리뷰 미해결 진단 0, 보안 리뷰 LOW/승인, Ruff·compileall·diff 검사 통과.
GitHub의 새 HEAD CI와 운영 스모크/정규 배치 관측은 로컬 테스트와 구별한다.

P3b~P7: 미완료. 실제 무인 인증 갱신·라이브 필드/원문 검증·운영 보고서/BUY/SELL 통합·
스크리닝 선택 변경·배포·첫 배치 성공은 위 테스트의 통과 범위가 아니다.

변경 파일은 신규 순수 품질 모듈·수집 모듈·HTTP 어댑터와 대응 테스트, CI 테스트 등록,
이 설계/검증 문서다. 기존 normalizer를 재사용하고, stdio registry·agent 도구 목록을
확장하거나 새 필수 의존성을 추가하지 않았다. 기존 source/report/BUY/SELL 실행 코드는 그대로다.

## 초기 모듈 사용 계약

아래는 라이브 앱 설정이 아니라 **주입형 collector API의 옵션**이다. 아직 일반 설정 파일에
추가하거나 운영에서 켜지 않는다. 명시적 `{"enabled": true}`만 수집을 허용한다.
잘못된 설정·미설정은 OFF이며 기본 함수 호출/프롬프트를 바꾸지 않는다.

- 기본 예산: 최대 4회, 호출당 15초, 전체 45초, 원 응답 256KiB,
  근거 12,000B/전체 36,000B. 호출자는 검증된 상한 안에서 값을 선택한다.
- 상한: 8회/호출당 30초/전체 90초, 원 응답 1MiB, 근거 24,000B/전체 72,000B.
- 이는 디코딩 후 처리·근거 반입 예산이다. 네트워크 수신 메모리나 전체 LLM 토큰 상한이 아니다.
  과거 호출 지연보다 짧을 수 있으므로 운영 기본 예산의 타당성은 P3 실측에서 다시 평가한다.
- 현재 지원은 원문/뉴스/재무 이력/전망/일정/OHLCV의 기존 정규화 지원 10종이다.
  전체 35종이나 임의 스크리너 열을 이미 연결했다고 하지 않는다.
- P1은 보존된 가격 관측의 원래 수집 시각을 비교한다. 배치 시작 시각 뒤에 새로 읽은 자료를
  시작 당시 확보한 snapshot으로 자동 인증하지 않는다. 실제 연결에서 cutoff와 수집/판단 시각의
  관계를 정의해야 하며, 역사적 공시의 사후 조회·정정본 검증은 P4의 별도 계약이다.

## 운영 연결 전 확인해야 할 이용 범위

2026-09-19 공식 페이지를 다시 대조했다. [MCP 출시 안내](https://www.tradingview.com/blog/en/tradingview-mcp-server-public-beta-60864/)는
AI 대화·스크리닝·문서 분석뿐 아니라 코드에서 데이터를 받아 분석하는 사용례도 소개한다.
따라서 모든 자동 조회나 코드 분석을 일괄 금지로 해석하지 않는다.

한편 [일반 약관 3절](https://www.tradingview.com/policies/)에는 비표시 용도와 자동 매매·
알고리즘 의사결정에 관한 명시적 제한이 있다. 공식 MCP의 제공만으로 PRISM의 무인 BUY/SELL
판단·주문 및 배포 보고서 재사용까지 허용됐다고 확정할 근거는 확인하지 못했다.
이것은 법률 결론이 아니라 운영 승격에 필요한 권한 확인 사항이다.
단순히 사람이 읽는 보고서를 중간에 생성했다고 뒤의 무인 매매 이용이 자동 승인되는 것도 아니다.

서면으로 확인할 범위:
- 개인 계정의 공식 MCP 데이터를 무인 분석 배치와 BUY/SELL 판단에 사용할 수 있는가?
- 사람이 읽는 보고서 생성과 같은 보고서를 매매 에이전트가 다시 읽는 이용은 어떻게 구분되는가?
- 원문/발췌·파생 수치·캐시 보관과 Telegram 보고서 전달은 어느 범위까지 허용되는가?
- 거래소/뉴스/문서 공급자별 별도 허가가 필요한가? 필요한 상품/계약은 무엇인가?

이번에는 실제 TradingView 데이터의 무인 매매 연결·운영 ON·신규 주문을 하지 않았다.
독립 기반 모듈과 모의 응답 검증은 진행하되, 권한 미확인을 기존 승인으로 덮어쓰지 않는다.
