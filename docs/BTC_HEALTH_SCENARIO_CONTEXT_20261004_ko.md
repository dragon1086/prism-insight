# BTC 누적 오류 경보의 판단·보호 상태 구분

## 사건 확인

사용자가 전달한 2026-10-04 00:15:01 KST demo 경보의 최근 2시간 오류 6건은
운영 DB에 실제 존재한다. 각각 10/03 22:30, 23:00, 23:15, 23:30, 23:45,
10/04 00:00의 `scenario tick blocked: reconciliation_or_proposal_failed`였다.
마지막은 00:00:16이며, 해당 관측 구간의 판단 원장에는 00:05·00:10 회차의
lock_busy가 있고 검증 완료 WAIT는 없다. 따라서 당시 정규 판단 완료 미확인은 맞다.
반면 독립 보호 점검은 00:00:24부터 매분 00:14:22까지 protection_checked로 완료됐다.
전 시스템 중단이나 보호주문 제거를 의미하는 경보는 아니었다.

## 별도 표시 결함

기존 `_completion_context`는 마지막 heartbeat 한 건이 옛 엔진의
`tick ok: protection=`로 시작하는 경우만 완료로 인식했다. 새 엔진의 검증된
`scenario tick: wait`는 무시되고, 뒤에 온 보호 heartbeat가 판단 기록을 가리기도 했다.

M3 관측 수정으로 최근 시나리오 실행, 검증된 판단 완료, 보호 확인을 구분한다.
protection_checked는 판단 완료로 간주하지 않고, lock_busy·blocked·intent_pending은
거래·정산 완료의 근거로 삼지 않는다. 특히 과거 heartbeat의 lock_busy/blocked는
두 루프가 같은 문자열을 쓰므로 그 기록만으로 판단 루프의 실패라고 단정하지 않는다.
시각·mode·최신성·미래 기록 여부를 검사하며 옛 엔진의 완료 인식도 보존한다.

누적 오류 기준(2시간에 5건 초과)과 경보 등급은 그대로다. 이후 정상 판단이 있더라도
오류 이력을 삭제하거나 모든 문제가 해결됐다고 표시하지 않는다. 실제 10006 수집
제한과 후모델 잠금 보완은 PR #893의 별도 변경이며 본 문구 변경이 장애를 숨겨서는 안 된다.

## 검증

실제 00:15 패턴, WAIT 뒤 보호 heartbeat, 이후 실패, 부분 진행·미확정 상태,
오래됨·미래·다른 모드·기존 엔진을 주문·전송 없는 격리 테스트로 검증한다.
과거 메시지 재발송, 수동 운영 healthcheck 전송, 거래·cron·계정 변경은 하지 않는다.
CI와 배포·스모크·실제 정규 점검 경보는 따로 기록한다.
