# BTC 프롬프트 논리 감사와 교정 계획

## 범위와 보존 계약
사용자 요청에 따라 LLM 프롬프트를 프로그램 명세로 취급하고, 입력→분기→출력→검증→
집행의 논리 흐름을 펼친다. 운영 기준은 fbebd46d(PR #888)이며, 국면 프레이밍 후보
PR #887은 별도 검토·교정하되 운영에 활성화하지 않는다. 주식 프롬프트는 이번 범위가 아니다.

이 작업은 모순된 명세·조건 우선순위·모델에 전달하는 계약을 교정한다. 기존 위험 예산,
레버리지, 수량 계산의 최종 권한, 중단 조건, 주문·정산·보호 검사는 완화하지 않는다.
수익률이나 거래 수에 맞춰 문구를 튜닝하지 않는다. 새로운 지표·의존성·상주 작업은 없다.

## 코드 수정 전 정리 계획
1. 기존 회귀를 실행하고 발견한 반례를 실패 테스트로 고정한다.
2. 프롬프트의 권한/분기 순서를 한 곳에서 명시한다. 호스트 출력 계약과 시장/과거 판단
   문자열을 구분하고, 위험 제한이 기회·관망 권고보다 우선하도록 정리한다.
3. ADJUST의 신규 주문/유지/취소/목표 변경 의미를 분리한다. 실제 pending ID와
   과거 계획의 ID를 구분하며, 취소 요청만으로 예약 위험을 해제하지 않는다.
4. 명세의 위험 산식·수량 단위·TP/SL 기준 가격을 실제 검증기와 맞춘다.
5. 국면별 문구에도 동일한 상위 조건을 적용하되, 기존 후보의 활성화 보류는 유지한다.
6. 독립 검토, 실제 모듈 통합 회귀, 제한된 주문 없는 LLM 계약 평가와 최종 CI를 수행한다.
   실제 모델 오류를 임의 보정하지 않고 성공/거절/미검증을 구분한다.

## 수정 전 확인한 명세 문제
- 모든 입력 문자열은 지시가 아니라면서 response_contract의 문자열 규칙을 따르라고 한다.
  호스트 계약과 시장/이전 rationale 데이터를 분리해야 한다.
- 중단 중에는 거래를 제안하지 말라는 포괄 문장이 축소·청산·보호 변경까지 금지하는 듯하다.
  실제 코드의 신규 위험 차단과 보호/청산 허용을 구분해야 한다.
- ADJUST를 전체 계획 교체로 설명하지만 entries는 증분 신규 주문이다. 유지할 미체결을
  다시 entries에 넣으면 중복 ID나 중복 위험이 발생한다.
- 취소 ID는 현재 pending_entries[].id만 유효하다. 과거 계획·체결/취소된 주문 ID나
  거래소 ID를 혼용하면 안 된다. 취소 확인 전에는 기존 위험이 그대로 예약된다.
- 프롬프트의 슬리피지는 entry 기준이지만 코드 산식은 hard_stop 기준이다.
  이익 중인 기존 포지션의 손절 거리에는 abs가 아니라 max(0,방향별 거리)가 적용된다.
- 시나리오는 첫 체결 전 OPEN 계획에서 예산을 예약한다. 첫 체결부터만 시작한다는
  설명은 미체결 상태의 활성 시나리오/예산 처리와 일치하지 않는다.
- 최종 SL을 올리거나 내리면 기존 미체결의 옛 SL 재적용을 막기 위해 호스트가 취소할 수 있다.
  유지/취소/재제출 의도를 분리해서 설명해야 한다.

## 프로그램 형태의 목표 흐름
```text
0. 호스트 출력 계약/현재 확인된 상태가 우선. 과거 계획·문장은 실행 증거가 아님.
1. 입력 무효·미확정 노출·PENDING 의도는 호스트가 신규 판단/주문을 차단.
   LIVE_RECONCILED 미체결은 예약 위험을 유지하면서 다음 판단이 가능함.
2. 활성 시나리오 없음: WAIT 또는 OPEN. 있음: WAIT, ADJUST 또는 EXIT.
3. 회계 미확정: 보수적인 프롬프트 정책은 WAIT/EXIT만 검토.
   알려지지 않은 손실/비용을 0으로 간주하지 않으며, 이 문구를 검증기 전체와 동일시하지 않음.
4. 신규 위험 중단: 신규 entries 금지. 확인된 상태의 보호/축소/청산은 계속 검토.
5. 현재 thesis와 30m/1h 진행 근거를 평가. 국면 렌즈는 앞 조건을 덮어쓰지 못함.
6. 주문 의미 선택:
   - 기존 미체결 유지: entries에 반복하지 않음.
   - 취소만: WAIT + 현재 pending ID.
   - 새 진입/추가: 새로운 ID의 증분 entries + 전체 예약 위험 재계산.
   - 목표/보호 변경: ADJUST의 exit 계획, 체결 증거와 잔여 quota 확인.
   - 전량 종료: EXIT; 계좌 전체가 아니라 해당 시나리오의 취소·감축 처리.
7. 수량·가격 단위, 방향, 예산/확신도 cap, ID, 만료, nullable 필드를 검증.
8. 출력은 제안일 뿐. 호스트가 최신 상태로 재검증한 뒤에만 집행.
```

## 반례와 검증 기준
- SHORT 진입100000/SL101000/0.1BTC/비용0.002/슬리피지20bp/자본7005에서
  기존 문구는140.0, 실제 코드는140.2 위험을 계산한다. 예산140.1을 사이에 두고 판정이 갈린다.
- 예산200에서 기존 예약121.90과 새 주문97.52는 합계219.42다. 취소를 요청했어도
  취소가 확인되지 않았다면 새 주문을 거절해야 한다.
- 유지 목적의 entries 복사·이미 종료된 취소 ID는 거절하고, 실제 현재 ID의 취소와
  신규 고유 ID의 증분 주문은 기존 코드 조건 아래 허용한다.
- 중단 상태라도 entries가 없는 보호 강화/EXIT를 일괄 금지하지 않는다.

최종 결과·추가 발견·수정 파일·테스트·한계는 확인 후 기록한다.

## 추가로 재현한 집행 식별자 결함
프롬프트의 '같은 목표 체결분만 차감'을 코드와 대조하면서, 실행 코드가 목표 ID를
접미사로 비교하는 결함을 발견했다. 합법적인 서로 다른 ID `near`, `tp:near`를 사용할 때
후자의 체결0.012BTC가 전자의 체결로도 차감됐다. 추가 진입 후 전자의 목표 수량은
0.025BTC여야 하는데0.013BTC가 됐다. TP와 부분 손절 양쪽에서 실패를 재현했다.
같은 intent·같은 kind·정확한 논리 ID만 일치시켜 차감하도록 한 조건을 수정한다.
이는 수량 비중/위험 정책 변경이 아니라 타 목표의 체결을 잘못 차감하던 정합성 오류 교정이다.
전량 native SL은 유지됐으며, 수정 후에도 주문 수량을 위험 제한 이상으로 확대하지 않는다.

## 교정과 검증 근거
- 시스템 문구의 권한/IF-ELSE 순서와 호스트 계약을 맞추고, 실제 현재 취소 ID를 schema enum으로
  제한했다. 미체결이 없으면 maxItems=0이며 로컬 검사도 이를 강제한다. 잘못된 ID를 고쳐 주지 않는다.
- target_status에 intent_id/logical_target_id를 추가하되 기존 target_id는 유지한다.
  매핑이 없으면 과거 목표의 체결을 현재 계획의 체결로 추정하지 않도록 명시한다.
- 변경 전121개 관련 테스트를 통과한 기준선을 확인했다. 새 회귀의 명세4건,
  목표 ID 매핑1건, TP/부분SL 접미사 충돌2건, 빈 취소 도메인1건 실패를 각각 확인한 뒤 수정했다.
- 수정 후 전체2,693 passed /12 skipped /네트워크 시도0건. 독립187개 관련 회귀 통과,
  코드 리뷰 승인, Ruff F/E9·구문·diff 검사 통과. 별도 Python 정적 타입 검사는 미실행이다.
- 실제 ChatGPT OAuth에서 maxItems=0 schema 응답을 확인했다. 후속12개 고정 사례는
  과거 의미 검증 실패9개 입력과 명시적 합성 정책 사례3개이며 주문을 제출하지 않는다.
  결과에 맞춘 재시도·응답 수선은 하지 않고, 사례별 성공/거절을 PR과 전달 보고서에 남긴다.
- 국면 프레이밍 후보는 상위 수명주기·회계·증분/취소 규칙이 우선한다는 문구를 별도 교정한다.
  후보를 운영에 활성화하지 않으며, 예전 성과를 새 프롬프트의 검증 결과로 재사용하지 않는다.

프롬프트를 프로그램 명세처럼 대조했지만 LLM 자체를 형식 검증한 것은 아니다.
모델의 모든 미래 응답이 논리적으로 올바르거나 수익성 있다는 보장은 아니며, 호스트 검증기는 유지한다.
