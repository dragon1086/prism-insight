# 간밤 복기: 보호 강화 ADJUST의 회복 상태 검사 수리

대상: M0.2 실행 안전 / M3 복기. 기준선92cfd0a3이며 운영 BTC 판단 소스는 #1408을 포함한 a9fcfdbc다.

## 변경 전 최소 검토

1. **유형:** 이미 모델과 호스트가 승인한 보호 강화가 실행 전 검문에서 거절되는 오류 수정이다. 진입·목표가·수량·위험 예산·모델·프롬프트·시간 제한을 바꾸지 않는다.
2. **원인·반증:** 11/20 02:20 SHORT ADJUST는 SL63368.6→62768.8, 추가 진입0, 미체결 진입0이었다. `fresh_safety_rejection/context_changed/recovery_hard_blocked`로 막혔다. 앞선 #1408은 REDUCE만 보완했으므로 ADJUST 경로에는 같은 입구 상태 동등성 검사가 남았다. 보호를 더 강하게 하는 ADJUST를 같은 방향·확정 잔량·추가 진입/예약 갱신/취소/부분스탑 변경 없이 확인할 때만 신규 위험 차단·회복 상태·손절 확대 허가의 변화만으로 거절하지 않는다. 다른 상태가 바뀌면 계속 거절한다. 감축과 엄격한 보호 강화는 입구/손절 확대 허가를 소비하지 않도록 역할을 분리하며, 진입·증액·확대는 원래 검문을 유지한다. 허용 시 달라진 입구 상태의 필드명만 receipt.entry_only_state_changes에 남기고 값·계좌 자료는 추가하지 않는다.
3. **실제 연결:** 입력/계좌→DRAFT/SELECT→정확한 테이프 재생→guard_review 두 호출자→코어 위험·가격·목표 계약 검증→broker fresh preflight→네이티브 SL amend/재조회→보호/정산. 기존 `core.scenario_stop_policy.is_widening`을 재사용한다. WAIT/EXIT의 기존 처리와 REDUCE의 확정 잔량·수량 검증, OPEN·증액·손절 확대·예약 갱신·동시 계좌 변경·미확정 정산·보호 불명확 검사는 유지한다.
4. **같은 조건·반례:** 실제02:20 테이프와 원래 의미를 고정해 기존 거절을 재현한다. LONG/SHORT×입구 상태 양방향 및 세 입구/확대 허가 검문, 같은 SL/확대/추가 진입 및 계좌·잔량·정산·보호·위험 상태 변경 반례를 검사한다. 별도 모델 호출과 주문은 없다. 원래 fresh broker 전체 관측은 보존되지 않았으므로, 원계획이 없거나 기존 부분 손절·미확인 intent가 있으면 이 예외를 허용하지 않는다. 그 밖의 당시 상태까지 재구성하거나 실제 체결/피할 수 있었던 손실을 확정하지 않는다. 시간/신선도 오류에는 기존의 고정된 내부 코드만 failure_detail로 추가 보존한다. 판정 조건과75초/120초/유효기간 제한, 공개 메시지는 유지한다.
5. **원인 분리:** 11/19 18시 이후 종료2건, 0승2패, 순손실−5.86554363USDT. 첫 거래는 TP1 후 보호 강화가 막혔고, 다음02:25 REDUCE는 별개 시간/신선도 제한으로 폐기됐다. 원본 failure_code는75초 검토·120초 입력·유효기간 등을 합친 분류이므로 정확한 조건을 추가 증거 없이 단정하지 않는다. 둘째 거래의07:05/15/25 REDUCE는 체결됐다. 진입 품질·이익 반납·검토 지연은 별도 연구 질문이며 이 수정으로 모두 해결됐다고 하지 않는다.
6. **결론:** 원래 선택한 보호 강화의 실행 가능성을 복원한다. 관련 회귀·실제 테이프 검사·정확한 최신 PR head CI 후 데모에 배포한다. 첫 정기 실행, 다음 자연 보호 강화 체결, 비용 후 수익 개선은 별도로 판정한다. ClickStack BTCUSDT2일 조회는 MISSING이므로 운영SQLite의 읽기 전용 결정·자식 주문 체결·확정 정산으로 보완했다.
