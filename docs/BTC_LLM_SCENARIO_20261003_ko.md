# BTC LLM 시나리오 전환 계획

## 승인 범위
2026-10-03 사용자는 기존 메인·스윙 신규 진입을 대체하는 데모 메인계좌 전략과
텔레그램 메시지 개편을 승인했다. 모델은 gpt-6-luna/high/fast, 판단은 5분 주기다.
레버리지는 10배 고정하고 확신도에 따라 수량을 조절한다. 시나리오 첫 진입 전
계좌 순자산의 2%가 비용 포함 계획 손실 예산이다. 분할/재진입으로 초기화하지 않는다.
이익으로 위험 예산을 확대하지 않는다. 하루 4% 손실 또는 전량 정산된 시나리오
3개 연속 순손실이면 신규 위험을 중단하고 운영자 검토 전 자동 재개하지 않는다.
실자금·타계좌·KR/US 전략 변경은 범위 밖이다.

## 로드맵 연결과 선행 조건
M0.1 부분 체결 즉시 보호, M0.2 보호 공백 방지, M1.1 미체결 포함 공통 위험,
M3 판단/체결/알림 관측을 선행한다. M4 신규 전략 및 M5 전진 검증 후보이며
수익성 입증이나 실자금 승격을 뜻하지 않는다.

## 구현 순서 및 단순화 계획
1. 기존 코드를 먼저 삭제하지 않고 새 전략의 입출력·불변조건을 격리 테스트한다.
2. MA10/35·가격 구조·거래량 및 진행봉의 남은 시간을 입력으로 만든다.
   다중 TF 정렬점수·상대강도·추세강도 하드 게이트는 새 판단에서 사용하지 않는다.
3. LLM에는 시나리오 제안 권한만 주고 수량·위험·주문 검증은 결정론 코드가 담당한다.
4. 시나리오/주문 의도/체결/정산을 영속 연결한다. 불명확 주문의 재제출은 금지한다.
5. 기존 포지션/미확정 주문은 보호를 유지하고 새 전략과 혼합하지 않는다.
6. 메시지는 계획/접수/체결/보호확인/정산을 구분하며 원시 계좌·주문 식별자를 노출하지 않는다.
7. 주문 없는 통합 테스트와 장애 주입, PR CI 이후에만 데모 배포를 검토한다.
8. 서버 검증·첫 5분 실행·실제 체결 관측은 각각 별도로 보고한다.

## 필수 검증
미확정봉 lookahead, stale LLM 결과, 잘못된 JSON/수치, 예산 초과, 부분 체결,
재시작·중복 tick, 취소 UNKNOWN, 보호 실패, 비용 누락, 연속 손실 잠금,
LLM 실패 중 보호 유지, 기존 포지션 인계, Telegram 전달 불명확을 검사한다.
시장 급변/슬리피지로 실제 손실이 2%를 넘을 수 있으며 절대 상한으로 표현하지 않는다.

## 현재 상태
**비활성 개발 구현이며 운영 전환은 미완료다. 주문을 켜면 안 된다.**

구현한 파일과 책임:
- `core/llm_scenario.py`: 엄격한 JSON/수량/2% 예산/연속 손실 검증.
- `engine/scenario_snapshot.py`: 30m/1h 중심 MA10/35·진행봉·거래량 관측.
- `live/scenario_oauth.py`, `scenario_llm.py`: 기존 호스트 OAuth Responses 프록시를 통한
  gpt-6-luna/high/priority(빠른 처리) 호출. 도구 목록 없음, 도구 실행기 없음,
  로컬 프록시만 허용, HTTP 프록시/리다이렉트 차단. API 키 대체 경로 없음.
- `live/scenario_runtime.py`: 영속 5분 슬롯/의도/판단/정산/중단 상태.
- `live/scenario_notice.py`, `scenario_outbox.py`: 사건별 새 한국어 공지, 전송 ACK와
  UNKNOWN 구분, 자동 중복 재전송 금지. 운영 채널에는 이번에 보내지 않았다.
- `live/scenario_preview.py`: 공개 실시간 시세→모델→검증 주문 없는 실행.
- `live/scenario_broker.py`: MAIN 데모 UID/계좌/주문/재무 증거 조회 경계.
  **읽기 전용이다. capabilities는 비어 있고 execute는 실패한다.**
- `live/scenario_runner.py`: 명시적 활성화·계좌 바인딩이 필요한 진입점.
  보호를 실제 관리하지 않는 adapter의 조회 성공을 보호 성공이라고 보고하지 않는다.

단순화: 새 판단에는 기존 상대강도·다중 TF 점수·추세강도 하드 게이트를 넣지 않았다.
기존 전략 코드는 아직 지우거나 운영 경로에서 교체하지 않았다. 무검증 전환을 막기 위해서다.

## 2026-10-03 검증 결과
- 지정 `.venv-bt` Python 3.12.12 전체 BTC 격리 테스트:
  **2,506 passed / 12 skipped / 0 failed / 네트워크 시도 0건**.
- 기본 Python 3.14에서는 기존 수치 재생 호환성 검사 9건이 실패했다.
  해당 검사들이 지시한 고정 연구 런타임으로 전체 재실행해 통과를 확인했다.
- Ruff 핵심 오류 검사, compileall, git diff --check 통과.
- 별도 안전 검토에서 WAIT/EXIT 손절선 오염, 미체결 취소 누락,
  도구 권한 상속, 순차 시세 수집 관측시각 문제를 발견해 회귀 테스트로 수정했다.
- 초기 CLI 모델 호환성 호출은 8.87초, 최종 도구 없는 OAuth 프록시 호출은
  1.59초에 성공했다. 속도 보장이나 매매 능력 입증은 아니다.
- 공개 시세의 진행봉을 사용한 주문 없는 preview는 유효한 WAIT JSON을 반환했다.
  자본은 테스트용 10,000 가상값으로 실제 계좌가 아니며 주문 0건이다.
- CI 대상에 신규 안전 테스트를 추가했다. 로컬 테스트와 원격 CI/운영 검증은 별개다.

## 반드시 끝내야 하는 운영 차단 항목
1. 시나리오 자식 주문의 영속 제출·ACK 유실 복구·취소/체결 경합 처리.
2. 부분 체결 즉시 보호와 부분 TP/SL 교체의 실제 브로커 통합.
3. 정확한 execution↔transaction 연결 및 펀딩 시간표별 정산 완전성.
   빈 응답 또는 페이지 소진을 최종 펀딩 0의 증거로 삼지 않는다.
4. 입출금/미실현 변동을 구분한 KST 일손실 기준 및 명시적 운영자 재개 절차.
5. 제출 직전 실제 마진·청산 거리·불리한 체결 가격·수량 step 재검사.
6. 레거시 MAIN/SWING의 신규 진입 차단과 기존 포지션 보호 인계.
7. 독립 보호 작업과 5분 판단 스케줄, 실제 Telegram 전달 연결의 배포·첫 실행 확인.

기존 DemoAdapter의 임의 부분청산 및 종결 원장 경로를 그대로 재사용하지 않는다.
가변 부분청산에 전량 행 삭제가 적용될 수 있고, 누락 비용을 0으로 취급하는 경로가
새 시나리오 예산/연패 판정의 근거가 될 수 없기 때문이다.

이번 변경으로 실자금/주문/cron/운영 DB/기존 전략 설정은 변경하지 않았다.
검증된 브로커 구현·PR CI·인계·스모크 전에는 병합/배포/자동 거래 전환하지 않는다.

## 재현 (주문 없음)
```sh
PYTHONPATH=prism-btc:. python -m live.scenario_preview --equity 10000
python tools/run_btc_safety_tests.py
```
preview에는 기존 호스트 OAuth 프록시가 필요하며 주소는
`PRISM_BTC_SCENARIO_OAUTH_URL=http://127.0.0.1:<port>/v1/responses`로 지정한다.
프록시가 없으면 실패하며 자동 설치·API 키 전환·주문 재시도하지 않는다.
