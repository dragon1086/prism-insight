# BTC LLM 출력 계약과 관망 판단 교정

## 변경 전 계약 (M0/M3 출력 안정성, M4 판단 일관성)
- 기준선: PR #884 병합 `3ad8254f`. 원본 288회 응답은 보존한다.
- 순수 오류: 출력 계약 위반 41건(추가 필드23, 빈 scenario_id8, input_id6, revision4).
  identity/version을 현재 context에서 그대로 복사하라는 프롬프트가 신규 ID·revision+1
  요구와 충돌한다. 자유 JSON 대신 명시적 구조 계약과 로컬 재검증을 적용한다.
- 판단 변경은 따로 구분한다. 30m/1h 추세가 주 판단이고 고시간봉은 배경이다.
  5m 시작 경계의 합성 진행봉은 새 관측이 없다는 뜻이지 약세나 확인 실패가 아니다.
  미확정이라는 사실만으로 관망하지 않고, 작은 탐색 비중과 명확한 무효화 조건을
  검토한다. 거래 강요·승률 목표·위험 한도 완화는 하지 않는다.
- 입력→판단→검증→실행: scenario_snapshot / scenario_llm / core.llm_scenario /
  ScenarioRuntime→ScenarioDemoBroker. 원래 위험·체결·정산 검사는 그대로 보존한다.
  최근 유효 WAIT 근거를 제한적으로 전달해 이전 조건 충족 여부를 다시 보게 한다.
- 가설: 모델이 구조/버전 생성에 실패하거나 새 봉 경계를 확인 부족으로 오해하는
  문제를 줄일 수 있다. 여러 프레임을 제공했다는 것만으로 판단 품질을 입증하지 않는다.
- 비교: 기존 저장 구간을 주문 없는 검증에 재사용한다. 이미 본 구간이므로 holdout이나
  수익성 입증이 아니다. 출력 정상화와 OPEN 증가를 같은 성공 지표로 삼지 않는다.
- 완료 기준: 오류별 거절 회귀, WAIT/OPEN/ADJUST/EXIT 정상 경로, 경제적 위험 차단
  보존, 실제 OAuth 구조 응답, 전체 BTC 격리 테스트, 정확한 PR head CI.
- 운영 적용 전 코드·테스트·서버 상태·정규 실행을 구분한다. 보호 실패나 유효하지 않은
  출력은 여전히 거절한다. 오류를 임의 수선하거나 과거 tape를 덮어쓰지 않는다.
- 판정: 사전등록 비교. 수익성·높은 승률·오류 영구 소멸은 보장하지 않는다.

## 구현 및 검증 근거
- `scenario_contract.py`에서 호스트가 요청별 ID와 다음 revision을 결정한다.
  `scenario_oauth.py`는 strict JSON Schema를 요청하고 `scenario_llm.py`는 원응답을
  로컬에서도 검사한다. WAIT/EXIT의 명시적 null 보호 필드만 검증 후 기존 프로토콜의
  필드 부재로 변환하며, 틀린 식별자·추가 필드·경제 수치는 고쳐 주지 않는다.
- `scenario_runtime.py`는 같은 시나리오의 최근 30분 이내 유효 WAIT 최대3개를
  과거 관측으로 제공한다. 거절된 응답·미래 슬롯은 제외한다. 새 주문 권한은 아니다.
- `scenario_data.py`는 합성 경계를 각 진행봉에 표시하고 실제 관측과 구분한다.
- LLM 형식/호출 실패는 고정 코드로 원장에 구분한다. `scenario_replay.py`도 같은
  실패 분류를 재생한다. 거래소 체결·보호 문제와 모델 오류를 합치지 않는다.
- `scenario_runner.py`, `scenario_notice.py`, `scenario_outbox.py`는 별도 모델 오류
  사건과 비공개 메시지를 사용한다. 보호 정상 heartbeat는 모델 오류를 해소하지 않는다.
  후속 검증된 판단만 MODEL_RECOVERED를 만들며 체결·보호·정산 확인을 뜻하지 않는다.
- 실제 loopback OAuth에서 단순 enum schema와 전체 시나리오 schema가 성공했다.
  전체 응답은 기존 경제 검증까지 통과한 WAIT였다. 테스트 주문은 제출하지 않았다.
- 합성 strict-wire OPEN→EXIT 및 잘못된 ID 실패를 실제 runtime으로 실행한 뒤 frozen
  재생해 결과 해시와 거절 사유가 일치하는 회귀 테스트를 추가했다.
- 별도 Python 정적 타입 검증은 완료하지 않았다. LSP 도구는 tsc를 사용하므로
  Python 타입 검증 증거로 삼지 않는다. Ruff F/E9·구문 검사·격리 테스트로 검증한다.
