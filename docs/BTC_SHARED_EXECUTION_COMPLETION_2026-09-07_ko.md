# BTC 비단타 실행 안전성·공통 위험관리 완성 작업

작성일: 2026-09-07 KST. 상태: 코드·격리 검증 완료, 공통 위험 정책 비활성.
병합·실제 배포·전진 관측은 아래 검증과 별도로 확인합니다.

## 범위와 보존

사용자가 단타를 제외한 남은 항목을 완성한 뒤 배포하도록 요청했습니다.
기준은 `BTC_ROADMAP_ko.md`의 M0.3/M0.4/M0.5/M1.1입니다.
새 단타, 신호·트레일 최적화, 위험 예산 확대, 실자금 전환은 포함하지 않습니다.
기존 ROOT의 사용자 journal·미완료 BTC 연구·HTML을 그대로 두고
`557cc9e7`에서 분리한 깨끗한 작업 트리에서 구현합니다.

## 구현 순서와 검증 기준

1. M0.4: 시세 수집·지표·선택적 연구가 실패해도 거래소 상태에 근거한 기존
   포지션 보호·정산 점검을 수행합니다. 임의 가격/봉으로 신호나 신규 진입을 만들지 않습니다.
2. M0.3: 전량 종료 후 보조 SL의 취소 ACK를 완료로 처리하지 않고,
   exact order identity의 terminal 조회까지 영속 정리 상태를 유지합니다.
3. M0.5/M1.1: 실제 두 주문 경계의 공통 잠금·위험 예약·응답 유실 복구를 연결합니다.
   미체결 예약과 실제 노출을 중복하거나 누락하지 않고, 반대 방향을 상쇄하지 않습니다.
4. 회귀·장애 주입·동시 프로세스·재시작·원장 보존식 테스트를 실행합니다.
   테스트는 격리 DB와 fake broker를 사용하며 실제 주문을 만들지 않습니다.
5. 독립 검토와 정확한 PR head의 CI를 확인한 뒤 정상 병합·clean 서버의 ff-only
   배포·자연 heartbeat 확인을 수행합니다. 운영 DB·기존 cron·자격증명은 보존합니다.

## 명시적으로 미확정인 설정

합산 손절위험 한도와 허용 진입 슬리피지는 앞선 계약에서 사용자 결정 대기였습니다.
현재 요청만으로 이전 제안 6.5% 등을 승인된 운영 기본값으로 바꾸지 않습니다.
2026-09-07 사용자에게 두 수치를 질문했으며, 답변 전에는 관련 신규 정책을
활성화하지 않습니다. 그 외 독립적인 보호 안전성 보완과 미활성 구현·검증은 진행합니다.

## 완료 판정 경계

코드 구현, 합성 테스트, 서버 코드 배포, 정책 활성화, 실제 체결 관측은 따로 기록합니다.
모든 M0/M1/M2 체크박스나 수익성 입증을 이번 변경만으로 완료 처리하지 않습니다.
특히 실제 새로운 체결·부분익절·손절 표본이 없으면 전진 관측은 미확인입니다.
롤백은 배포 전 서버 커밋으로 되돌리는 검증된 수정 PR을 기본으로 하며

## 구현한 실행 경로

- `live/runner.py`, `live/broker_recovery.py`: 선택적 연구·시세 수집·지표 계산보다
  거래소 보호/정산 확인을 먼저 실행합니다. 두 계정을 독립적으로 확인하며, 미확정이면
  신규 전략 실행을 막고 다음 tick에서 복구합니다. 실제 제출 시각에 따른 진입 만료를
  처리하므로 수집 장애 중에도 미체결 주문이 방치되지 않습니다.
- `live/order_retirement.py`: 보조 SL의 정확한 주문 ID와 제출 link를 보존합니다.
  미해결 진입이 없고 거래소의 미체결 진입 주문·포지션도 없을 때만 취소합니다.
  ACK나 조회 부재가 아니라 정확한 종료 상태가 확인돼야 기존 제출 잠금을 해제합니다.
- `live/closed_entry_recovery.py`: 최초 체결을 기록하기 전에 연결된 거래소 SL까지
  체결된 경우를 복구합니다. 부모 주문, SL 연결, 전체 체결 수량·가격·수수료·시각,
  거래소 정산액이 맞을 때 거래와 영수증을 원자적으로 기록합니다.
  과거 포지션을 현재 열린 포지션으로 만들어내지 않으며 같은 체결을 다시 기록하지 않습니다.
- `live/swing_entry_recovery.py`: 접수 후 응답 유실, 부분체결 후 잔량 취소,
  영수증 저장 중 재시작을 처리합니다. 정확한 근거가 없는 수량은 채워 넣지 않습니다.
- `live/shared_entry_coordinator.py`, `live/entry_reservations.py`: 실제 DB 경로를
  기준으로 메인·스윙의 상태 변경과 주문 경계를 직렬화합니다. 파일 DB 잠금은
  새 위험 정책을 켜지 않아도 적용하며, SQLite transaction 밖에서만 거래소를 조회합니다.
  새 위험 정책을 켜면 두 계정의 정체성·자본·보호·미체결 주문을 함께 확인하고
  예약을 영속화한 뒤 주문을 한 번 제출합니다. 체결 원장과 예약 최종화는 같은
  transaction에서 처리합니다.

## 공통 위험 정책의 설정과 정확한 의미

다음 환경 설정은 운영 활성화 시에만 명시적으로 필요합니다. 문서의 테스트 fixture 값은
운영 권장값이나 사용자 승인값이 아닙니다.

- `BTC_SHARED_ENTRY_ENABLED`: 기본 `false`입니다.
- `BTC_SHARED_ENTRY_COMBINED_HEAT`: 합산 진입가 대비 손절 위험을 자본의 비율로 표시합니다.
- `BTC_SHARED_ENTRY_SLIPPAGE`: 허용하는 불리한 진입 가격 차이를 비율로 표시합니다.
- `BTC_SHARED_ENTRY_MAIN_UID`, `BTC_SHARED_ENTRY_SWING_UID`: 거래소가 반환한 서로 다른
  실제 데모 계정 UID를 지정합니다. 값 자체를 Git·로그·보고서에 노출하지 않습니다.

기존 개별 전략의 위험 계산과 8배 합산/5배 스윙 명목노출 기준을 보존합니다.
합산 위험 정책값이 누락되거나 잘못되면 정책 활성화를 거부합니다.
유효한 정책에서도 스윙 IOC 지정가를 남은 위험 예산 안으로 더 좁힐 수 있습니다.
수량이나 위험을 늘리지 않는 대신 주문이 체결되지 않을 수 있습니다.

명목노출은 **새 주문 승인 시점의 거래소 mark 가격으로 평가하는 한도**입니다.
가격 변동 후에도 항상 유지되는 상한이 아닙니다. 숏 지정가는 최소 매도가이지
최대 매도가가 아니며, 이익 방향 체결·시세 변동으로 평가 명목노출이 달라질 수 있습니다.
SL 가격도 실제 청산 가격을 보장하지 않으므로 손실 최대치 보장으로 표현하지 않습니다.

## 검증·운영 경계

- 실제 서버에서 두 세션 모두 데모 API를 사용하고, API가 반환한 UID가 서로 다름을
  읽기 전용으로 확인했습니다. 당시 두 계정의 포지션·미체결 주문과 로컬 미확정 상태는
  모두 없었습니다. 새 시험 주문은 만들지 않았습니다.
- `tools/run_btc_safety_tests.py`는 개발용 검증 도구입니다. 부모와 Python spawn
  자식의 인터넷 접속을 차단하며, 네트워크 접근 시도도 실패로 처리합니다.
  운영 루프나 추가 상주 프로세스에는 연결하지 않습니다.
- 기록 전 즉시 SL 종료의 자동 복구는 24시간 이내의 완전한 단일 연결 증거를 대상으로 합니다.
  여러 주문이 섞이거나 링크·체결·수수료가 누락되면 운영자 확인 상태를 유지합니다.
  시간이 지났다는 이유로 미확정 위험을 지우지 않습니다.
- `funding_source=settlement_residual`은 거래소 정산액과 가격 손익·수수료의 차이입니다.
  실제 펀딩 이벤트 원장을 모두 대조했다는 뜻이 아닙니다. 기존 일반 체결 보고와
  메인·스윙 전체 백테스트/실행 패리티의 완성도 이번 작업으로 주장하지 않습니다.
- 파일 잠금은 같은 호스트·같은 로컬 파일 DB용입니다. 분산 호스트나 NFS 잠금이 아닙니다.
  메모리 DB는 합성 테스트 호환 경로일 뿐 공통 위험 운영 설정에서는 허용하지 않습니다.

## 확인한 거래소 계약

주문 접수와 체결을 구분하고, 진입 동반 SL 및 지정가의 가격 제한을 구현할 때
[Bybit 주문 생성 문서](https://bybit-exchange.github.io/docs/v5/order/create-order)를 확인했습니다.

사용합니다. 종료 복구의 가격·수수료·정산 근거는
[Trade History](https://bybit-exchange.github.io/docs/v5/order/execution)와
[Closed PnL](https://bybit-exchange.github.io/docs/v5/position/close-pnl)에서 확인합니다.
