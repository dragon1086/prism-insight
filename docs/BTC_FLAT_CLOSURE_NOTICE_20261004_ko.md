# Flat 응답의 빈 SL과 종료 공지 누락

## 실제 전진 관측

펀딩 정산 교정 뒤 정상 예약 실행에서 진입 0.1 BTC, 청산 0.1 BTC의 정산 기록이 생성됐지만,
대응하는 종료 공지는 없었다. 최신 flat 계좌 관측 8건에서 stopLoss와 avgPrice는 빈 문자열이었다.
기존 알림 생성기는 이미 공지한 과거 fill까지 다시 보강하며 float(stopLoss)를 호출했다.
빈 문자열 변환이 실패해 선택적 알림만 rollback됐고, 경제적 정산은 정상 진행됐다.

이후 새 시나리오가 생긴 상태에 과거 계좌 값을 붙이거나, 종료되지 않았다고 표현하면 안 된다.
경제적 원장과 공지 전송을 분리해 검증하고, 실제 원장/주문을 바꾸지 않는다.

## 수정 계획과 범위

M3 공지 증거 경계의 순수 결함 수정이다. 전략·수량·손절·계좌·스케줄은 그대로다.

1. 실제 빈 문자열 flat 응답으로 실패를 재현한다.
2. 이미 존재하는 fill 공지는 다시 보강하기 전에 건너뛴다.
3. flat/오래된 체결에 현재 SL·레버리지를 억지로 숫자화하거나 과거 값으로 대체하지 않는다.
4. 정산이 완료된 마지막 청산은 PARTIAL과 CLOSED 두 개가 아닌 CLOSED로 요약한다.
   이미 기록된 과거 부분 청산은 지우지 않는다. 첫 비교 스냅샷 무알림도 유지한다.
5. 실제 runtime 청산 흐름·재시작·증거 누락·출력 검사를 회귀로 고정한다.

## 누락 공지 한 건의 명시적 복구

`tools/recover_btc_closed_notice.py`는 기본값이 읽기 전용이며 `--scenario-id` 한 건만 검사한다.
저장된 정산과 해당 시나리오의 의도·주문·체결을 exact ID, 수량, 가격, 비용, 순손익으로 대조한다.
현재 계좌나 새 활성 포지션을 사용하지 않는다. 과거 정산의 펀딩 값은 확인된 저장 원장을
사용할 뿐, 미보존 당시 일정을 독립 재계산했다고 주장하지 않는다.

기존 `scenario-closed-<scenario_id>` 식별자를 재사용하며 notice/outbox 어느 곳에든
같은 식별자가 있으면 상태와 무관하게 건너뛴다. UNKNOWN/SENDING도 재전송하지 않는다.
모든 과거 시나리오를 자동 훑거나 과거 FILLED/PARTIAL을 재발송하는 기능은 없다.

`--apply`는 명시적인 운영자 승인 후에만 사용한다. 알림 두 테이블에 원자적으로
대기열 등록만 하며 직접 전송·주문·위험/정산 장부 변경은 하지 않는다.
문구는 **BTC 데모 이전 매매 정산 확인 · 지연 안내**이며 새 주문이 아님을 명시한다.
사용자에게 이번 누락 종료 한 건의 복구 전송을 질문했으며, 답변 전에는 apply하지 않는다.

## 검증·완료 구분

기본 dry-run DB 불변, 다른 새 포지션 존재, native SL의 늦은 로컬 저장시각,
미확정/무체결 정산 거부, side·수량·금액·ID 충돌, 반복 복구, SENDING/UNKNOWN 차단,
원자적 rollback을 주문·전송 없는 격리 테스트로 확인한다.
코드 배포, 실제 누락 건의 dry-run 적격, 사용자 승인, 큐 등록, Telegram 영수증은
각각 별도 단계이며 한 단계를 다음 단계 성공으로 간주하지 않는다.
